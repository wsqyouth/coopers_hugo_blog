<h2 id="摘要">摘要</h2>
<p>OpenCode
的设计师终于不用等工程师排期，自己就能修好界面细节，产品也因此更精致。但
Dax Raad
发现，一些让系统变脆弱的实现也进来了，工程团队往往后来才察觉。同样的变化出现在开源社区：身处
Azure
澳洲节点等特定环境的用户，能帮团队复现平时接触不到的问题；也有人让模型生成补丁，没运行便提交。AI
降低了参与门槛，却没有一并解决谁理解影响、谁验证结果、谁承担长期维护的问题。</p>
<p>在这场 Baseten 对谈中，Madison Kanna 与 Dax
从旧金山和迈阿密谈起，逐步走到开放客户端、模型权重、推理服务和工程能力，再回到公司为什么值得继续做下去。Dax
支持更广泛的技术可及性，也承认开放会带来滥用，推理商可能拿不到硬件，便宜模型未必够用，自己的团队同样会偷懒。他看重的小团队优势，是多年开源经验、直接使用产品、倾听具体反馈和持续公开工作；这些积累帮助团队找到机会，也不能保证下一次下注正确。</p>

<a id="第一部分--哪里能做成一家技术公司"></a><h2 id="哪里能做成一家技术公司">哪里能做成一家技术公司</h2>
<a id="00000528旧金山的密集人脉为什么仍没让他搬家"></a>
<h3 id="bay-area-network">旧金山的密集人脉，为什么仍没让他搬家？ <span class="picks-episode-time">（00:00–05:28）</span></h3>
<p>走在旧金山街上，竟有人认出 OpenCode 团队。Dax
觉得自己像走进了现实版的互联网：平日在网上接触的人，仿佛都住在这座不大的城市里。在迈阿密，他出门后几乎没人知道、也没人想知道他做什么；到了旧金山，线上科技圈一下变成了触手可及的社交生活。</p>
<p>如果搬过去，他相信自己每天都能约到认识的人，技术活动和机会也会更多。Dax
并不否认旧金山是技术中心：重要公司、人物和事件聚在一起，靠近它们有实际收益。他甚至说，正在创业、又有条件去旧金山的人，大概应该去。OpenAI
和 Anthropic 这样的公司，并不会在每座城市都出现。</p>
<p>但对他个人，密度也意味着工作与生活继续混在一起。他在线上已经得到足够多的技术交流，未必希望线下生活也被同一件事填满；他喜欢热天，连旧金山的天气都觉得冷。迈阿密盛夏约两个月过热，其余时间却很合他的偏好。两人开头还争论了旧金山和纽约有没有异味，恰好说明这些城市感受有多主观。</p>
<p>他更想保留的是另一种可能：互联网本来就让人从世界各地向数百万人发布产品，为什么做技术产品的人反而一定要聚在一处？OpenCode
做的是很有旧金山色彩的 AI
编程工具，团队却没有人住在那里。他为此感到骄傲，也提到自己使用的一些热门
AI 产品同样不在旧金山。</p>
<p>这不是地点无关紧要的证明。Dax
明确承认，总体数字大概仍偏向旧金山；有意思的是，例外也确实存在。承认聚集优势，与选择在别处生活、做成产品，可以同时成立。</p>
<a id="05281452有工程师的城市怎样才算技术中心"></a>
<h3 id="miami-community">有工程师的城市，怎样才算技术中心？ <span class="picks-episode-time">（05:28–14:52）</span></h3>
<p>大约五年前，Dax
为了靠近家人搬到妻子的家乡迈阿密，恰好遇上加密货币热潮。风险投资人迁入，城市被描述成下一个硅谷。他并非为这股热潮而来，但既然身边有技术活动，便去看看；结果遇到一些上周才学会
NFT、这周已经成立公司并上台演讲的人。几次浮夸而业余的体验之后，他决定少参与，专心做自己的事。</p>
<p>在他的观察里，那轮热潮退去后，许多人和投资机构又搬走了，没有留下相称的长期成果。采访时，加州、纽约的一些税收提案似乎又推动了一轮迁入，他担心“让迈阿密成为技术中心”的叙事会再次先于实际建设。这是他的在地经历与判断，不能据此推算整座城市的迁移或投资规模。</p>
<p>他主张从大约五位优秀创始人开始，而不是先凑出一千家公司。早期社区最好由本来就能做事、不依赖社区救助的人搭起来；等到有真实能力和资源，才更有条件服务职业初期、希望从活动中获得帮助的人。当地并非没有好创始人，而是大家都忙于各自公司，缺一个愿意长期组织的人。照搬旧金山成熟阶段的活动形式，未必能完成这个起步过程。</p>
<p>“技术中心”的标准也不该只是富豪和工程师数量。事业有成的人在后半生迁居，不自动给当地带来技术影响力；石油公司、营销公司同样会雇软件工程师。Dax
真正在意的是，这里的人和公司是否影响了外界怎样开发软件、向谁学习、采用什么方法。按这个标准，他认为迈阿密还差得很远。</p>
<p>他不排斥先建立信心的做法，却反对把一个小成果吹成城市崛起的证明：越急着说服所有人“这里已经成功”，越可能暴露没有多少东西可展示。他那篇文章本来写给想在当地建设社区的人，网上却有人争论迈阿密永远不行、有人坚持早就成功、还有人讲自己的搬迁失败经历。他说这些都偏离了自己的重点：既然要投入时间，怎样做才更有效。他也承认自己可能看错。</p>
<p>生活选择有另一套具体条件。他喜欢的是自己住的街区：有院子，孩子多，步行就能吃饭，适合三十多岁、开始安定成家的阶段。税负对可能获得大额回报的创始人有吸引力，但他不赞成人生只围绕哪里缴税最少来安排。这些条件说明他为什么住在这里，并不能替所有人作决定。</p>
<p>至于“迈阿密太好玩，所以无法专心创业”，他的反例非常日常：大部分时间在家工作、在邻里走路，并不会被迫去夜店。真搬到旧金山，每天都有熟人活动，反而更难拒绝。城市的小优化最终绕不开产品与市场的匹配——必须找到真实需求，才谈得上公司成功；把自己安排到一个据说更不容易分心的地方，并不能替代这件事。</p>
<a id="第二部分--opencode-的开放做对了什么"></a><h2 id="opencode-的开放做对了什么">OpenCode 的开放做对了什么</h2>
<a id="14522150先用上-claude-code再找到开放客户端的位置"></a>
<h3 id="open-client">先用上 Claude Code，再找到开放客户端的位置 <span class="picks-episode-time">（14:52–21:50）</span></h3>
<p>Claude Code 是团队第一次真正持续采用的 AI 编程工具。此前他们试过
Cursor 等产品，却没有留下使用习惯，甚至不确定 AI
编程究竟有没有那么有用。Claude Code
让他们理解了这种工作方式；随后才有那个创业问题：既然自己认可这类体验，凭已有经验还能提供什么？</p>
<p>这个机会背后是一段很长的寻找。Dax
说，公司的法律实体已经存在十六年，投资人与实体一路延续，不断尝试，每次似乎比上次好一点，却又没好到真正做成。他自己不是最初的创始人，而是约五年前加入，后来成为联合创始人。十六年属于公司，不能全部算成他的个人创业年数。</p>
<p>团队看见的空位，是一个可以连接不同模型和基础设施的开源客户端。Claude
Code 与 Anthropic
绑定，客户端闭源；他们的积累则在开源社区，以及那些很难靠内部团队穷尽的适配长尾。支持更多模型并非只是在菜单上多放几个名字，每种真实环境都可能藏着独有的故障。</p>
<p>Azure 的澳大利亚数据中心就是 Dax
给出的例子：某种环境要额外设置一个参数，提示缓存才会正常工作。小团队未必接触得到该环境，也就难以发现、复现和修复；实际在那里用
OpenCode
的贡献者却能做到。开源的价值首先在于让分散的现场知识进入产品，让工具能够触达团队自己看不见的角落。</p>
<p>另一个理由来自他对开发工具历史的判断。他早年使用微软 .NET
技术栈，编辑器和部署都涉及授权费用；再往前，编译器也曾是需要购买的专有工具，数据库的默认选项可能是
Oracle。他认为，商业公司往往先投入资源，把一类产品做出来；等客户成功到比供应商更大、更有钱，长期支付巨额授权费就会产生另一种激励：资助自己的替代方案。Amazon、Facebook
在这里是他说明大客户动机的例子，并非节目逐一考证的开源项目史。</p>
<p>这套推理仍为专有产品留下空间。Dax 称赞 JetBrains
是好产品、好生意，同时口头估计开放编辑器占约七成市场。他要说明的是开放选项可能成为默认基础，不是闭源产品必然消失；七成也只是他的无出处估计。</p>
<p>OpenCode
最初几个月最明确的目标，是让人们把它认作那个开源的编程代理选项。团队既有社区经验，也愿意处理繁琐的长尾，终于觉得自己的能力与一个有价值的位置对上了。但这段讲的是团队为什么做产品，不能直接回答首批用户为什么来：字幕没有早期用户动机调查，无法证明便宜、开放权重或规避某家限制究竟哪一项最重要。</p>
<a id="21022459社区带来真实环境也带来未经验证的-pr"></a>
<h3 id="verify-prs">社区带来真实环境，也带来未经验证的 PR <span class="picks-episode-time">（21:02–24:59）</span></h3>
<p>刚解释完开源贡献不可或缺，Dax
给新贡献者的第一句建议却是一个玩笑：“别贡献。”随后的请求更准确：“请别只给模型下提示，就把结果发过来。”（译自
“please don't just prompt and send.”）</p>
<p>他估计 OpenCode 仓库差不多每隔几分钟就收到一个新
PR。有人碰到问题，让模型生成修复，看到模型说已经完成，甚至不运行一下就提交；有时连提交也交给模型。维护者于是得接住大量尚未验证的工作。他说一些开源项目已关闭外部贡献，正说明这种压力会改变社区的运作方式。</p>
<p>优秀贡献者仍然会被看见。通常他们持续关注团队把时间花在哪里，理解产品正在往哪走，再自己找到有用的工作。维护者不会替每个人安排任务、做产品管理，贡献者需要主动判断什么值得做。Dax
说，他们隔几周仍会发现很出色的人，并常常将其招进团队；除了原先共事过的人，后来招聘的成员大概都来自社区。</p>
<p>问题在于，生成补丁很快，确认它值得合并却未必快。团队曾有过一段宽松合并的时期，结果不断破坏已有功能，后来只能变得谨慎。有人抱怨一个简单
PR 三个月才合并；Dax
的解释是，产品服务着他所说的数百万用户，小改动出错也会影响很多人。理解修改、验证行为、承担影响的成本，不会因为补丁更容易生成而自动消失。</p>
<p>他还调侃，低质 PR 居然有人用 Claude Code 写，仿佛给 OpenCode
再补一刀；团队一度开玩笑地怀疑竞争者故意来消耗时间。这不能当成恶意攻击的证据。更实际的经验已经足够明确：社区扩大了小团队能解决的问题，合并权仍要求团队自己掌握验证与取舍。</p>
<a id="24593111理解安全动机为什么仍反对集中控制"></a>
<h3 id="access-and-control">理解安全动机，为什么仍反对集中控制？ <span class="picks-episode-time">（24:59–31:11）</span></h3>
<p>Dax 不接受网上把自己描述成对 Anthropic
怀有极端敌意的人。他可以尊重对方的出发点：AI
很有影响力，也可能被滥用、带来严重后果，因此希望严格控制谁能使用、怎样使用。他相信这些担忧可能是真诚的，并未把限制都归结为恶意。</p>
<p>分歧在于，同样因为技术影响重大，他更希望世界各地尽可能多的人能获得它，包括彼此竞争甚至冲突的公司与国家。在他的理解里，长期稳定来自力量之间持续的相互制约。把规则交给少数组织，即使它们最初善意、判断力很好，也不能指望它们几十年如一日替全世界作出正确决定；权力本身会改变持有者。</p>
<p>他没有回避开放的成本：广泛传播模型，会帮助一部分想做坏事的人得到工具，他们也可能真的作恶。他愿意接受这一代价，因为认为过度集中权力的替代方案更差。这是他的价值排序，而不是两种治理方式已经有可比较的总伤害数据。他把双方目标视为存在真实冲突，同时保留对安全动机的尊重。</p>
<p>这里也需要分开几层开放。客户端开源，使人能参与检查和改进工具；模型可换，使工作流不必绑定一家模型；开放权重，使不同主体有机会部署同一个模型。前者不能自动带来后两者，权重可下载也不等于所有人都有训练或推理资源。Dax
主张各层都应该存在开放、可自由取得的选项，同时欢迎专有模型和专有工具提供优秀产品。他还特意澄清，自由可及并不是计算服务必须免费。</p>
<p>他相信开放模型会持续出现，理由也不只在道德。一些国家无法使用美国公司的模型，大企业不想把全部预算绑定给极少数供应商，Baseten
这样的公司则需要开放模型来做推理生意。这些主体即使都在维护自身利益，也有动力资助和使用开放替代品；单靠“应该开放”的愿望，反而不足以让供给长期持续。</p>
<p>不过，模型训练投入很大，硬件可得性很有限。美国 AI
大公司与大型科技公司大量吸收 GPU
容量，留给开放项目的资源可能成为瓶颈。因此，他对长期激励有信心，却不能确定开放模型何时出现、按什么顺序发展。这里关于
Anthropic 的说明，也只是 Dax
对其立场的解释；本段没有核验具体封禁、合同或政策事件。</p>
<a id="第三部分--从权重开放到真正能用的模型"></a><h2 id="从开放权重到真正能用的模型">从开放权重到真正能用的模型</h2>
<a id="31113853权重开放之后硬件和资金仍可能卡住竞争"></a>
<h3 id="gpu-supply">权重开放之后，硬件和资金仍可能卡住竞争 <span class="picks-episode-time">（31:11–38:53）</span></h3>
<p>同一个开放模型可以由许多家公司提供服务，用户才有机会在它们之间选择。Dax
用一百家托管商作示意：不必只能向一个卖家购买，竞争才可能推动推理价格下降。他认为闭源模型销售
token
的毛利很高，但没有给出财务证据；这里可靠保留下来的，是他对竞争机制的解释。</p>
<p>主持提出的算力所有权问题，正好指出了这种竞争的物理前提：权重可以开放，真正掌握数据中心和算力的主体，却仍可能掌握入口。训练首先需要有人投资，推理市场也只有在新公司拿得到硬件、建得起服务时，才谈得上充分竞争。一家优秀创业公司能融资十亿美元已经很惊人，Google、Amazon
这类云巨头却能每年动用数百亿美元。开放推理商很难以同样规模争夺资源。</p>
<p>Dax 从伙伴和业内熟人那里听到的紧张，覆盖了部署的整条链条：不只是
GPU，还有其他硬件，以及把这些东西真正部署起来的劳动力。大家担心半年后没有容量，便尽量提前锁定；这种囤积又加剧当下短缺。他们试着分辨传闻是否夸大，却发现问到的人大多已经进入囤容量的状态。这是他当时收集到的行业反馈，尚非全面供给调查。</p>
<p>资金也可能紧张。他提到一个没有给出处的估计：基础设施建设或许需要约
1.5
万亿美元借债；期限说成未来大约五年，随即又表示不确定。他还设想，一家推理商即使有客户愿意下
1
亿美元的订单，也得先借钱建设，借不到钱仍无法交付。这个订单是说明融资约束的情境，不是一份已披露的合同。</p>
<p>主持随后问，企业该怎样准备 token 成本在几个月后翻倍。Dax
立即收窄了前提：“我没有说它们一定会。”（译自 “I'm not saying they
will.”）价格可能上涨，也可能持平，或只是没有像大家期望的那样继续下降。他自己也没有确定答案；团队当时正尝试购买超过眼前需要的容量，以便支撑约六个月后的扩张。这个应对动作带着摸索性质，并非已经验证过的采购公式。</p>
<p>他同时保留短缺转为过剩的路径。疫情期间，人们囤积厕纸、纸巾，一度像是供给严重不足；随后全球动员生产，实际消耗又没有预期大，就可能出现过量供给。短缺产生赚钱机会，吸引更多资源来填补，因此未必永久持续。但
GPU
不像纸巾或小麦：生产复杂，牵涉多个国家、资源与政治条件。他希望类似的供给反应发生，却不敢保证结果相同。</p>
<p>这种不确定性也解释了团队为什么少围绕精确预言安排公司。Dax
说，一个预测往往不是猜对一件事，而是六个假设叠在一起，还要分别在正确时间成立。相比押注某个六个月后的情境，他们更愿意先占住一个有用的产品位置，每天听用户抱怨、修正问题、交付有价值的东西。半年前，他甚至没想到自己会进入推理业务、开始关心
GPU；今天的工作，是一路处理用户实际需要走到的。</p>
<a id="38534156反感核武器比喻却用制衡解释开放"></a>
<h3 id="power-balance">反感核武器比喻，却用制衡解释开放 <span class="picks-episode-time">（38:53–41:56）</span></h3>
<p>Dax 首先反对把 AI
描述成核武器。从传播上说，一群科技从业者宣称自己正在制造同等级别的武器，会招来公众恐惧与政府审视；从判断上说，他认为
AI
将非常强大、非常有用，却仍觉得这个比喻夸张，夹杂着人们想把自己想象成曼哈顿计划参与者的心理。</p>
<p>接着，他接受这个前提继续推演：即使 AI
真有那么大力量，也更不能把它只交给少数主体。一个人可能有善意、道德感和判断力，但要连续几十年替全世界判断每一个难题，仍然非常不可靠。竞争、差异和持续调整，在他看来才是更可信的结构。</p>
<p>他区分了两种看起来不同的稳定。一种平时十分平静，却偶尔被灾难性的巨变打断；另一种始终有摩擦、冲突和不舒服，却限制了一次失控带来的整体崩塌。如果一定要沿用核武器类比，他认为核威慑时代多个国家相互牵制更接近后一种状态：并非每个参与者都被认为是善意行动者，持续张力却使各方难以迈出极端的一步。</p>
<p>所以他既反感“我们在造核武器”的自我形象，又用核威慑说明自己心中的分散制衡。这能让读者看清他的政治历史直觉，不能直接证明开放模型的安全结果：节目没有把两种技术的治理机制逐项对应，也没有比较事故率。</p>
<p>Dax 说，这些并非他的原创，而与十年前读《黑天鹅》《Skin in the
Game》等书时接触的思想有关。他记住的要点是，稳定往往看起来并不整齐。这里保留的是他的阅读回忆与类比，没有把提到的书籍当成本次另行核验的证据。</p>
<a id="41564811开放模型追近之后工作流能否只换模型"></a>
<h3 id="open-weights">开放模型追近之后，工作流能否只换模型？ <span class="picks-episode-time">（41:56–48:11）</span></h3>
<p>通常被外界认为更封闭、更自上而下的中国，却持续发布重要的开放权重模型，让美国公司也能在其上发展业务——Dax
觉得这个反差很有意思。他起初说得像是只有中国在做，随后马上补充，美国也已有实验室投入。保留这个补充，才能避免把一段观察摘成绝对判断。</p>
<p>他的解释仍是竞争激励。按他的理解，中国实验室在追赶领先的美国闭源模型，要获得注意力，就有动力开放权重，让领先者的产品变得更像可替代的商品。这不必出于无私的道德愿望，也能帮助其他国家的开发者和推理商。即使所有参与者都考虑自身利益，合适的激励结构仍可能带来公共收益。</p>
<p>他认为，美国早期资金不太理解开放模型的商业模式，中国先出现可指认的实例之后，投资者才更容易看见它如何运作，相关融资也开始出现。不过，规模仍远不及领先大厂。他还看见资源压力的另一面：钱和算力较少，可能迫使团队寻找更有效率的训练方式。他称一些中国模型已做出令人印象深刻的结果，节目却没有展开模型、训练成本和实验条件的一一对照。</p>
<p>主持说自己读到开放模型原先落后约十八个月、后来缩短到约三个月。Dax
认可的是差距缩小的感受，而没有验证这两个数字。他关注这个领域还不到一年，早先觉得闭源新模型能占优约半年，开放模型刚追近，领先者又发布下一代；到了采访当年前几个月，两边差不多同期更新，表现却仍然接近。</p>
<p>他随即保留了另一个重要条件：自己并没有说开放模型更强，仍然认为领先闭源模型最好。变化在于，开放模型对他的日常工作已经足够好，让他可以经常使用，也不太想念闭源选项；他把这种变化放在当年二月附近。这是个人使用体验，没有任务集、版本清单或统一成功率，不能据此制作性能榜单。</p>
<p>对 OpenCode
而言，模型之间的竞争让一个稳定的客户端更有价值。如果这周用 Claude Code
建立工作流，下周听说另一款模型更好，又换去
Codex，用户可能连工具习惯都得重建。Dax
想让其余环境保持不变，只改变所选模型。领先者持续轮换、不同模型又适合不同任务时，这种选择能力会更有用。</p>
<p>他本人通常在两个模型之间切换：一个处理大部分日常工作，另一个处理较长、较大、适合放在后台异步进行的任务。节目没有给出一个可以照抄的具体组合。他也承认，很多人选定工具后就一直用，完全没有问题。可换模型服务的是确有这种需要的人，并不是要求每个人追逐每次发布；它解决的是工作流的选择成本，开放权重解决的则是部署和供给问题。</p>
<a id="48115512先保住模型能力再谈速度价格和多数份额"></a>
<h3 id="model-economics">先保住模型能力，再谈速度、价格和多数份额 <span class="picks-episode-time">（48:11–55:12）</span></h3>
<p>OpenCode 最初几个月收到不少愤怒反馈：工具不好用，结果不对。Dax
原以为，用户想用某个模型，随便选一家推理商接上就行；排查后才发现，有的供应商根本没有把模型正确服务出来。用户不知道问题在托管端，最后怪罪的是
OpenCode。</p>
<p>同一个模型为什么会表现不同？团队逐渐认识到，新模型不是下载到硬件上就算部署完毕。服务商需要调优，与模型开发者和
Nvidia
协作，再根据工作负载做优化；编程代理的使用方式也不同于其他应用。因此，OpenCode
开始筛选可靠伙伴，集中提供模型选择和路由，持续反馈问题、一起改进质量。Dax
强调，他们依靠专业推理伙伴，并不自称已经掌握全部推理技术。</p>
<p>他的第一项标准，是部署不能削弱模型本来拥有的能力。有些服务会让模型显得很笨，用户容易误以为是模型自身不行。第二项是速度：慢模型用久了会习惯，换到快模型时，整个交互体验却可能像换了一种工具。速度与成本又常常需要权衡，低价格可能以更慢的响应为代价。</p>
<p>可用性也重要，但他们相对宽容，原因很具体：同一模型会接多家供应商，有替代路径；推理行业又在早期，还不能要求它拥有经营数十年的云计算那样的成熟度。这个取舍依赖冗余和行业阶段，并不是说宕机对用户不重要。</p>
<p>服务质量保住之后，才有“是否值得总用最强模型”的问题。Dax
承认，人们愿意为最聪明的模型付费，这种想法并非全错；但当最强与次强的差距缩小，企业开始审视账单，支付意愿就可能变化。他提到一些公司看到编程代理每月花掉百万美元，开始想办法优化；这只是访谈中的转述，未展示账单。</p>
<p>他用一个假设解释选择：如果次优模型便宜十倍，也许已经够用，<strong>也许仍然不够</strong>。更具体的例子来自客户
CTO：公司不仅工程师用 OpenCode，营销团队也用，而营销同事总选择 Opus
和极高思考档位，花了很多钱。CTO
判断这些任务不需要那么强的模型，希望给他们能力接近、或足以完成工作的便宜选项。节目没有讲最后换成了什么、成本省了多少，也没有给出任务质量对照。</p>
<p>从这些例子可整理出的选择顺序是：先确认托管没有损害能力，再看模型能否完成自己的任务，随后把等待时间与费用放进实际工作衡量。这是对节目判断方式的归纳，并非嘉宾提供了一张统一评分表。营销团队的案例支持按任务分档的需要，不能替任何团队完成具体测试。</p>
<p>Dax
长期看好开放模型占据多数推理使用量，因为控制成本、避免单一供应商和让更多供给者竞争，都有经济动力。但他承认，“多数”可能很遥远，本身就是下注，也不意味着专有模型消失。他用
iPhone 和 Android
类比：一个产品最有名、最具标志性，不代表它一定占整体市场多数。这个类比帮助解释他的判断，不能作为模型市场份额的证据。</p>
<p>价格的未来还有相反的两条路径。一位投资人给他的框架是：<strong>如果</strong>
token 需求指数增长，GPU
部署能力却只线性增加，供给就跟不上，价格会有上涨压力。Dax
没把这个前提当成必然；他同时考虑过度建设。公司若投入不足、错过市场，可能直接出局，因此战略上更倾向多建而不是少建；几年后供给可能超过需要，再推动价格下降。他不知道转折发生在何时，只认为短期会相当混乱。</p>
<a id="第四部分--ai-写快以后工程还剩什么"></a><h2 id="ai-写快以后工程还剩什么">AI 写快以后，工程还剩什么</h2>
<a id="551210259设计师能自己修界面工程团队怎样接住"></a>
<h3 id="designer-ships">设计师能自己修界面，工程团队怎样接住？ <span class="picks-episode-time">（55:12–1:02:59）</span></h3>
<p>设计师看到一个普通工程师没有注意的界面问题，过去要请求工程师帮忙，现在可以自己用编程代理修好，产品因此越来越精致。但
Dax
的团队也发现，设计师未必能判断某种实现是否会让整个系统变脆弱；一些代码进入产品时工程师没有察觉，后面才发现问题。新参与能力带来的收益和长期风险，发生在同一件事里。</p>
<p>这个例子是 Dax
回应“软件工程师会被自动化吗”的主要依据之一。他们自己就在做编程代理，也大量使用自己的工具；把团队结果放在一起看，却很难维持一个长期可靠、好改、令人愿意工作的代码库。他担忧的并不只是模型偶尔写错代码，而是许多看似完成任务的小选择，逐步改变了系统。</p>
<p>工程选择本来就有一条光谱。一端是容易做、却很粗糙的办法，另一端是极其正确、但可能耗时过久的办法，中间还有许多方案。工程师必须理解业务、当前目标和约束，决定应该停在哪里。AI
出现以前，人也会不断选择省事方案，让今天好用的代码库半年后变得难以忍受；团队往往靠几个人反复恳请大家多想一点，必要时多花一天，才没有彻底失去秩序。</p>
<p>代理放大了其中的心理距离。自己亲手写一个丑陋实现，会直接感到不舒服；让模型去写，人可以不仔细看那段代码，却马上得到“事情做完了”的满足感。短期收益变得更容易获得，后续维护的代价仍要稍后支付。Dax
认为，这正在影响包括自己在内的人的判断。</p>
<p>他特别说明，设计师的例子不是对设计师的指责。理解这些系统后果，并非设计师的职责；工程团队才需要回答，怎样保留他们修产品的能力，又防止代码长期腐化。团队喜欢编程代理，认为它有生产力，但距离弄清如何有效使用、岗位如何变化、护栏怎样建立，还很远。Dax
没有把尚在摸索的问题包装成已经解决的流程。</p>
<p>他的取舍光谱也不意味着永远拒绝临时实现。业务约束可能要求暂时接受不完美的方案；关键是理解代价后作选择。但字幕没有给出一次性脚本、限时实验、重写期限或清理责任的具体标准，也没有一例可以直接照搬的临时代码批准规则。不能把这段访谈扩成团队已经实行的操作规范。</p>
<p>对于生产力，他更希望先看结果。一个人同时运行七个 Claude
Code，本身说明不了实际价值；应该观察是否有小团队持续压倒更大的团队，或者某个竞争者因为更会使用代理而彻底击败自己。只有看到这样的变化，才值得追问它怎样发生。他尚未在自己面对的竞争中看到这种程度的力量重排，因此怀疑某些数量级的提升宣称，觉得实际收益可能更渐进。</p>
<p>他没有把自己的视野当作全世界：也许已经有公司出现了重大变化，只是自己不知道；他可能判断错。为了最终作出正确判断，他认为必须反复检查自身假设和偏见，而不是靠“明年模型会更好”跳过今天的困难。至少在当时，架构、系统设计，以及过去十到十五年积累的编程技能，仍然每天派得上用场。</p>
<a id="1021411046我们也在这样做外包思考与模仿赢家"></a>
<h3 id="engineering-craft">“我们也在这样做”：外包思考与模仿赢家 <span class="picks-episode-time">（1:02:14–1:10:46）</span></h3>
<p>Madison 说，自己手写代码时会认真思考，用 AI
时却很容易直接接受改动，把思考也交出去。她听完前面的回答，以为 Dax
的团队可能没有这样做。Dax 当即纠正：“我们的团队也在这样做。”（译自 “our
team is doing that”）连他自己也每天面临同一种诱惑。</p>
<p>这种变化不需要一次明显的放弃。每天稍微懒一点，一年后回头看，工作习惯已经很不一样。以前不曾抱怨的手工操作，如今显得异常缓慢、琐碎，可其中一些仍然必须亲自做。他把这种又获得好处、又在某些方面受到损害，必须重新理解人与工具关系的体验，比作在应付一种上瘾。那是个人感受，不是临床诊断，更不是要求放弃
AI。</p>
<p>恐惧落后还会制造另一种捷径：模仿想象中的赢家。人们相信大变化会产生赢家和输家，却不知道自己究竟该做什么，于是猜测赢家一定把
AI 用到极致、并行运行很多代理、掌握复杂工作流，再照着展示这些行为。Dax
指出两个漏洞：没人知道最后的赢家是否真长这样；即使猜对了，复制外表也不等于得到对方的能力与结果。</p>
<p>Mitchell Hashimoto 是他想到的反例。HashiCorp 的开发工具影响过 Dax
的早期职业生涯；Hashimoto 后来继续打磨精致的产品，也积极使用 AI。Dax
看见的却是：对方本来就是非常好的程序员，也有很强的产品能力和经验，自己今天仍很难与之竞争。AI
可能让这样的人进一步拉开差距，而不是让其他人只凭“用得更狠”就追上。他需要提升的是自身基础能力。这是
Dax 对同行的评价，并非两人的生产率实验。</p>
<p>Madison 转述另一次采访里的设问：如果 AI 写了 95% 的代码，剩下那 5%
人类工作是什么？Dax 的回答是：“那 5% 可以就是编程。”（译自 “that 5% can
be
coding.”）即使大部分代码由模型写，优秀程序员仍可能在关键部分体现优势。这里的百分比是讨论前提，不是本节测出的行业现状。</p>
<p>他也不接受一句“以后人人都是代理管理者”就概括职业变化。自己做过中层管理，知道带真人团队要让人愿意做事、激发动力、克服困难；给代理下提示不需要同样的工作。Madison
承认自己也常用管理者比喻，却没有真正做过管理者。对 Dax
而言，键盘上输入的内容确实变了，工作中最费心、最消耗精力的部分，却和十年前很相似。</p>
<p>这关系到学习者今天怎么分配注意力。Madison 用自己学习 GPU
内核工程的例子说，期待 AI
越来越聪明，可能让人觉得无需再学困难知识；如果这个预期没有兑现，就会给自己留下能力空缺。Dax
则认为，竞争与努力不会凭空消失：一百年前杰出者的日常与今天不同，投入的精力、动机和心态却未必不同。具体技能会变，但仍要做困难的事。</p>
<p>他还把投入本身看作生活意义的一部分，无法想象永远只度假的状态有何吸引力。这里既有职业判断，也有鲜明的个人生活观。它支持继续打磨能力的理由，却不是对所有岗位未来的确定预测。</p>
<a id="第五部分--在行业共识之外找机会"></a><h2 id="在行业共识之外找机会">在行业共识之外找机会</h2>
<a id="1104611834十六年的公司为何还想继续留在场上"></a>
<h3 id="stay-in-the-game">十六年的公司，为何还想继续留在场上？ <span class="picks-episode-time">（1:10:46–1:18:34）</span></h3>
<p>让公司尽量活下去，是 Dax
认为人人都听过、真正做到却很难的建议。公司已经存在十六年，意味着经历过觉得一切都做错、几次尝试全部落空的日子，还得继续保持动力，每天回来工作。听起来简单的“留在场上”，落到人身上并不简单。</p>
<p>有些人能力很强，又赶上合适的时机和想法，很快成功；Dax
自嘲，其他人没有那么聪明、那么幸运，可以用更多尝试机会来补偿。他见过一些公司一度走得比他们远，最终却消失了，他们还在继续。长期存活增加遇到机会的次数，这是他坚持的理由，不能反过来当成“只要活得久就必然成功”的保证。</p>
<p>OpenCode
获得进展之后，他想要的是一家可以一直承载兴趣的公司。未来某天，团队也许对另一件事着迷，仍能在同一实体里做下去。他把
OpenCode
称为他们最后一项开发者工具：不论它最后是巨大成功还是中等成功，希望再做的东西能面向更广泛的人群。那是什么产品、何时开始，他都不知道，可能五年后才发生；这是长远愿景，不是已公布的转型时间表。</p>
<p>一个收购邀约让这种心态变得具体。某家公司 CEO 联系
Dax，表示想收购、邀请团队加入。他把消息贴到团队
Discord，其他人却继续讨论工作，几乎没有理会。大家正兴奋于用户增长和可以为这些用户做的事情。主持回忆时说的是
Slack，Dax 自述为 Discord，这里以他的叙述为准。</p>
<p>Dax
为这个反应感到高兴。刚成为创始人时，他也想象过卖掉公司、赚到很多钱，那像是最终目标；现在好不容易找到能服务很多人的机会，马上出售，反而像结束了多年挥棒落空之后终于有机会做的事。但他随即保留了现实条件：如果有人愿意付出足够高的溢价，他当然会考虑。节目没有披露买方、金额或正式交易条款，也没有一条“永不出售”的誓言。</p>
<p>持续做下去，也要持续判断什么值得做。团队全是程序员，为程序员造工具，自己就能使用产品，知道喜欢什么、不喜欢什么。这是
Dax
认为比闯进一个陌生行业、只凭看见空缺就做产品更容易的地方；他把为自己解决问题作为经验建议，并未证明其他创业路径都无效。</p>
<p>他们仍会花很多时间和用户、付费企业交流。正在准备的下一阶段产品，未来若成功，外界可能会说团队准确预见了趋势；按
Dax 的说法，实际过程朴素得多：他们大约与三位 CTO
谈过，三人提出不同的具体问题，细听之后却发现指向同一个需要。</p>
<p>所以每条反馈都有价值，因为它是真实发生的数据点；但用户未必能直接给出问题的根源。团队的工作是理解不同表述背后究竟意味着什么，再决定要解决哪一个共同问题。“会听用户”在这里不是照单全收，也不是神奇的预测能力，而是一项需要自己完成的理解工作。</p>
<a id="1183412221三十分钟零现金成本的后院发布视频"></a>
<h3 id="launch-in-backyard">三十分钟、零现金成本的后院发布视频 <span class="picks-episode-time">（1:18:34–1:22:21）</span></h3>
<p>发布 Zen 时，Dax
拿着手机在自家后院走路，直接讲正在做什么、为什么做。视频约花三十分钟，现金制作成本按他的说法是零美元；他和
Madison
都认为效果很好。这些是节目里的自述，没有播放量、转化率或收入数据，零现金支出也不等于没有时间成本。</p>
<p>选择这种形式，并非他一直只会做简陋视频。营销现在是分配给他的公司职责，几年前他还觉得自己是程序员，只管造产品，营销该由别人负责。为了让产品被看见，他不得不开始学习，逐渐形成一项习惯：持续观察别家公司怎样宣传，识别谁在模仿谁，以及某种形式如何从新鲜变成惯例。</p>
<p>他看到的变化是，最初科技发布内容普遍不够精良，忽然有人把视频做好，很令人兴奋；随后大家照着做，连非常普通的小更新也配上大制作，观众开始疲劳。如果别人花一万美元做了一次，自己再花一万美元复制，最好也只是相近的结果，更可能因为重复而效果变差。他还推测一些视频花了五万美元，公开的观看和互动却不理想；这些金额是他的假设与猜测，不是对方披露的预算。</p>
<p>因此，他想改变观众当时的预期：少一点包装，用最直接的方式解释动机，保持简短，不用推销口吻。后院散步适合完成这个动作，也符合他对观众情绪的理解。</p>
<p>他说完零成本，立即补了一层限定：不是以后每件事都要低预算，重点也不是复制这支视频。重要的是察觉那些还没有被说出口的疲劳或期待，再为它作出回应。下一次有效的做法可能完全不同。可以学习的是观察和判断，不能把“手机、后院、三十分钟”当成通用的传播公式。</p>
<a id="1213612615公开构建把真实工作变成持续交流"></a>
<h3 id="build-in-public">公开构建：把真实工作变成持续交流 <span class="picks-episode-time">（1:21:36–1:26:15）</span></h3>
<p>每天至少花八小时认真思考、学习和实现东西，到一天结束时，便有了值得分享的内容：今天做了什么，想到什么，学会什么，原来哪里错了。Dax
所说的公开构建，首先就是把这些真实工作讲出来的习惯，每周做几次，长期持续。</p>
<p>他觉得“公开构建”这个词已被一些表演式实践弄得空洞。有人看见它有效，就照搬表面动作，把工作记录写成“今天我在开发这个产品——附购买链接”。读者很容易看出每句话都在推销。对他的团队，分享并不以每次直接导流为目标；真实的学习、实现与认识变化，本身就应该有交流价值。</p>
<p>分享首先帮助他们保持动力，因为谈刚做出的东西很有乐趣。它吸引兴趣相投的人，其中有些人成为同事；把问题讲出来，也会收到别人掌握的知识，修正自己的认识。招聘、反馈、学习和继续工作的兴趣，就这样互相帮助，而不只是一串营销点击。</p>
<p>Dax
说，他们每周这样做已经五六年，后来能做成的很多事情都建立在这层积累上。这不是隔夜改变人生的技巧。代码本来就开放，也让他们更容易谈论工作，而无需额外制造一场“展示过程”的表演。</p>
<p>他允许新人寻找榜样，却不认为复制榜样今天的动作，就能到达同样的位置。可以明确自己想要的结果，但如果最终抵达，路径也会有自己的特点，别人无法替你写好全部指令。要持续分享有意思的东西，先得真的做过、学过有意思的东西。</p>
<p>这也是他反对过度追求每分钟效率的原因。如果创始人觉得每天必须直奔产品，任何绕路都算浪费，生活与工作可能越来越无聊。他希望允许游走、偶尔做点奇怪的事、留下一些不规则日程，给创造性一点空间。这个建议接在长期认真工作的经验之后：持续投入与允许探索并不矛盾，探索也可能成为以后值得分享的内容。</p>
<a id="1261512952播客给不了那一项属于你的下注"></a>
<h3 id="asymmetric-bet">播客给不了那一项属于你的下注 <span class="picks-episode-time">（1:26:15–1:29:52）</span></h3>
<p>好的建议往往并不隐藏，只是很难照着生活。Dax
说，历史上的一些创造者有古怪、迂回的日程，不是每一分钟都服从刚性的效率安排；他借此说明创始工作需要创造性，没有提供一份经研究验证的名人作息表。</p>
<p>Madison 则指出，AI
让创始人和工程师感到恐惧，人们于是更希望从播客里找到一套让自己安全的策略。Dax
理解，自己也会寻找这种安慰。但听完一套说法，当下感觉舒服，与最终真的获得想要的结果，是两件事。</p>
<p>在他看来，创业多少包含非对称下注：很可能判断错了，但如果正确，收益会很大。他用百倍的差异作形容，不是在承诺某种回报率。基本原则、工作方式可以公开讨论，具体要做什么、把机会押在哪里，却不可能由一期播客替某个听众确定。真正有价值的位置，可能正是别人忽略、甚至明确认为错误的东西。</p>
<p>OpenCode 对 AI
编程的保守态度，就是他自认的一项下注。他觉得同行普遍更相信快速加速与未来替代，而自己的团队反复讨论维护、工程能力和今天尚未解决的困难。如果这种判断得到事实支持，公司会显得站在合理的位置；如果趋势走向另一边，他们就可能错。这是
Dax
对行业及自身位置的理解，不能扩写成每家竞争公司的共同声明，更不能提前替这次下注判胜。</p>
<p>他最后没有再给一条保证安全的路线。属于自己的机会，仍要自己去发现，也不会一夜出现。保持一点古怪，去做些不在惯常日程里的事，让新的观察有机会发生——这是他留给听众的方向，而那个可以被押错、也可能值得押的具体选择，要由听众自己承担。</p>
