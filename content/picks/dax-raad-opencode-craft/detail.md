## 摘要

OpenCode 的设计师不用再等工程师排期，自己就能修以前顾不过来的界面。Dax Raad 很高兴看到产品变得更细致，也发觉一些脆弱的实现就这样进入了系统。同样的变化出现在开源社区：有人能在团队从没接触过的环境里找到真问题，也有人让 AI 生成一个没验证过的 PR，转手就交给维护者。

Madison Kanna 的对谈从旧金山和迈阿密开始，谈到团队为什么做一个可以换模型的开源客户端，随后追问谁有资源部署开放权重、同一模型为什么在不同托管商那里表现不一。最后回到两件很具体的事：工程师怎样决定什么代码可以留下，创始人怎样在别人都做相似选择时找到自己的机会。长版按英文原访谈的顺序展开。

## 第一部分 · 哪里能做成一家技术公司

### 在街上被认出，为什么仍不想搬去旧金山？ {#bay-area-network}

**原访谈时间：00:00–05:28**

开场先剪入一段关于 AI 应当广泛可及的主张，正式对谈却从 Dax 家里的闲聊开始。两人对旧金山有没有奇怪气味意见相反，对纽约的感受也不同。这个轻松开头恰好提醒读者：接下来的城市比较包含强烈的个人体验，不能读成宜居排行榜。

Dax 刚去过旧金山，觉得像走进了现实版的互联网。他在迈阿密主要在线上接触科技圈，出门后没人关心他做什么；到了旧金山，团队走在路上就有人认出 OpenCode。城市不大，平时在网上认识的人仿佛都住在同一片地方。若搬过去，他相信几乎每天都能约熟人见面，社交会很丰富。

吸引力也正是他犹豫的原因。他已经在线上获得足够多的技术交流，不一定希望线下生活继续被技术填满。他偏爱热天，甚至觉得旧金山太冷。迈阿密对他而言除盛夏约两个月过热外，大部分时间很合适。这里谈的是他的生活偏好，不是创业成功的解释变量。

谈到事业，他并不否认旧金山是技术中心：重要事件、公司和人聚集在那里，能靠近它们确有收益。他甚至说，如果正在创业且有条件去旧金山，大概应该去。他同时为团队无人住在旧金山、却能做 AI 编程工具感到骄傲。互联网本来就让人从任何地方触达全球用户；OpenCode 是这个可能性的一个实例。

因此，这段话的分寸是承认聚集优势，同时保留反例。它既不能证明地点毫无作用，也不能推出必须搬去旧金山才能做成产品。Dax 自己承认，总体数字可能仍偏向旧金山；值得观察的是，例外如何成立。

### 一个地方有工程师，不等于已经形成技术中心 {#miami-community}

**原访谈时间：05:28–14:52**

Dax 约五年前搬到迈阿密，直接原因是妻子来自这里，两人想靠近家人。那恰好赶上加密货币热潮，风险投资人迁入，城市被赋予承接硅谷的想象。他曾试着参加活动，却发现有人上周才学到 NFT，这周已经开公司并站上台演讲。他形容那种体验浮夸而业余，几次之后便决定专心做自己的事。

在他的观察里，热潮退去后，许多人和投资机构又离开了，没有留下相称的长期成果。采访时他看到另一轮迁入，部分与加州、纽约讨论中的税收政策有关。他担心同样的叙事会再来一遍。这些都是个人经历与当时判断，节目没有提供迁移人数、投资规模或城市发展数据。

他提出的替代路径很小：无需先凑出一千家公司，先有大约五位优秀创始人认真做事就够了。社区早期最好由那些并不依赖社区才能成功的人搭起来；如果尚未形成真实能力，就急着面向职业初期、希望从活动中获益的人群，组织者未必能提供应有价值。当地确有他欣赏的创始人，但大家忙于公司，仍缺愿意持续组织的人。

他衡量技术中心的标准也更严格。退休或事业有成的富豪搬来，不自动产生技术影响力；各行业都雇软件工程师，工程师数量本身也不足以说明问题。关键是当地的人和公司有没有影响外界怎样开发软件、向谁学习、采用什么方法。按这个标准，他认为迈阿密尚未做到；把一个小成果夸成城市崛起，反而会暴露底气不足。他不反对建立信心，只反对让包装远远走在事实前面。

围绕他那篇文章，网上有人说迈阿密永远不行，有人坚持它早已成功，也有人讲自己的搬迁失败经历。Dax 说，这些并非他真正想讨论的事。他写给的是打算在当地做事的人，希望他们把时间花得更有效，并承认自己可能看错。

生活选择则有另一组前提。他喜欢的具体街区有孩子、有院子，步行就能吃饭，适合三十多岁、开始安定成家的人。他把税收称为潜在好处，尤其对可能获得较大回报的创始人如此，但并不赞成人生只围绕最低税负安排。这些条件不能外推为整座城市适合所有人。

对谈还拆解了一个常见说法：迈阿密太好玩，所以无法专心创业。Dax 大多在家工作、在邻里散步，不觉得夜店会迫使自己少干活；反而旧金山每天都有认识的人组织活动，更难拒绝。城市小优化终究替代不了产品与市场的匹配。对读者而言，这段最有用的区分是：生活阶段、社交资源与产品需求是不同问题，不能用一个地点的名声同时回答它们。

## 第二部分 · OpenCode 的开放做对了什么

### OpenCode 从一次真正用上 Claude Code 的体验开始 {#open-client}

**原访谈时间：14:52–21:50**

OpenCode 的故事没有从一家刚成立的公司开始。Dax 说，承载它的法律实体已经存在十六年，投资人与公司一路延续；他并非最初的创始人，而是在约五年前加入，后来成为联合创始人。此前公司不断尝试，每一轮似乎比上一轮好一些，却又没好到足以真正做成。这是寻找机会的长期背景，不能写成 Dax 亲自连续创业十六年。

真正让团队理解 AI 编程的是 Claude Code。此前他们试过包括 Cursor 在内的工具，但没有形成持续使用习惯，甚至对 AI 编程本身仍有疑问。Claude Code 是第一款真正留下来的工具。团队先确认了自己喜欢这种体验，才问：凭已有经验，还能做出哪一种有价值的产品？

答案来自两项积累：长期做开源，以及处理适配的“长尾”。Claude Code 与 Anthropic 绑定，客户端闭源；他们看见另一个位置——做一个能接不同模型、不同基础设施的开放工具。这里的难处并非只是在菜单里多列几个模型名称，而是处理无数不常见、却会真实阻断用户工作的环境差异。

Dax 用 Azure 澳大利亚数据中心举例：某种部署要求额外传入一个参数，否则提示缓存不能正确工作。小团队很难自己接触那个环境，再完成复现、调试和修复；身处其中的用户却可能准确发现并解决问题。开源让这些局部知识进入产品。因此，社区对小团队的帮助首先是扩大能看见、能验证的现实范围。

他的第二个理由是对开发工具历史的判断。早年他用微软技术栈做开发，编辑器与部署涉及付费许可证；更早时，编译器也可能是专有产品，数据库的默认选项曾包括 Oracle。商业公司先把新概念做出来，随后使用它们的客户可能变得更大、更富有，不愿长期向一个供应商支付巨额授权费，于是有动机资助替代方案。他以 Amazon、Facebook 等大客户说明这种激励，而没有在节目中展开每个开源项目的完整历史。

这一判断保留了商业产品的空间。他称赞 JetBrains，认为专有编辑器能成为很好的生意；同时口头估计开放编辑器占据约七成市场。这个比例没有出处，应当作为他说明趋势的估计。论点是开放选项有望成为默认基础，并非所有闭源公司都会消失。

OpenCode 最初几个月的一项明确目标，就是让人们把它认作开源的编程代理选项。团队认为自己的社区经验与这个位置匹配得很好，甚至觉得终于找到了最适合出手的机会。

至于“用户最早为什么来”，字幕提供的证据止于团队的产品动机、初期定位以及之后出现的使用反馈。它没有首批用户访谈、渠道数据或动机统计，不能证明大家主要为了便宜、为了开放权重，或为了躲避某家公司的限制而来。可以确认的是，团队先被 Claude Code 的可用体验说服，再以开放和广泛适配寻找自己的位置。

### 社区扩大了能力，也把验证成本带进门来 {#verify-prs}

**原访谈时间：21:50–24:59**

刚说完社区不可或缺，Dax 被问到新人怎样参与，便开玩笑地劝人不要贡献。矛盾随即落到具体工作上：编程代理让提交 PR 变得太容易，他估计仓库差不多每隔几分钟就会收到一个新 PR。有人遇到问题后让模型生成修复，模型宣称完成，自己甚至没有运行，就把修改发给维护者。

他求的是不要只提示模型、随后直接提交。他还说，部分开源项目已经因为这种压力关闭外部贡献。对他来说，交一个补丁只是第一步，贡献者还得验证自己的改动。

真正优秀的贡献者仍会出现。他们关注团队最近在做什么，判断产品方向，自己找到能提供帮助的地方，而非等维护者替自己安排任务。Dax 说，除了过去工作中已经认识的人，团队后来招聘的人大概都来自社区。开源于是同时提供了适配能力与识别人选的长期过程。

负面的经验也很具体。团队一度比较宽松地合并修改，结果不断出现破坏，后来不得不收紧。有人抱怨一个简单 PR 花了三个月才合并；Dax 的回应是，产品服务的用户已达到他所说的数百万规模，一个小改动出错也会影响很多人。生成补丁的速度，并不能消除维护者理解影响面、验证行为和承担后果的工作。

中间还有两句不能当作事实报道的玩笑：他抱怨有人用 Claude Code 生成低质 PR 来投 OpenCode；团队甚至曾怀疑竞争对手故意来消耗时间。字幕没有提供恶意攻击的证据。真正成立的经验，是宽松合并曾造成问题，以及团队因此更谨慎。

这个场景揭示了小团队的双重边界。社区能够补足团队没有的知识，但团队仍要决定什么值得进入系统。开放带来的提交越多，判断与验证越可能成为瓶颈。

### Anthropic 分歧：尊重安全动机，仍反对权力过度集中 {#access-and-control}

**原访谈时间：24:59–31:11**

Dax 先澄清，网上对他的概括常常比本人立场极端。他与 Anthropic 有分歧，但能够尊重对方的出发点：AI 影响重大，可能被滥用，也可能造成严重负面后果，因此公司希望严格控制谁能访问、如何使用。

这是 Dax 对 Anthropic 立场与行为方式的解释。节目没有在这里列出具体封禁事件、合同条款、政策文本或当事人证词，所以不能把它写成一次经核验的限制措施调查。尤其不能进一步替他添加恶意动机；他明确表示，自己相信对方的担忧可能是真诚的。

他的价值排序不同。同样因为技术影响重大，他希望世界各地尽可能多的人能接触它，甚至包括彼此竞争、互有冲突的公司与国家。他认为，长期稳定往往来自力量之间持续的相互约束。少数实体即使一开始动机良好，长期拥有决定全世界使用规则的权力，也很难始终作出可靠判断。

这里包含他愿意承担的代价。他承认，更广泛的可及性会让有恶意的人拿到模型，并可能真的做坏事；他仍认为过度集中的替代方案更差。这是一项政治与伦理取舍，节目并未用实验说明哪一种方案实际造成的总伤害更小。他也把双方目标看作难以同时完全满足，而非简单指责对方不懂开放。

讨论接着区分了常被混为一谈的几层问题。**客户端开源**，让用户与贡献者能够参与工具本身的改进；**模型可换**，让工作流不必绑定一家模型；**开放权重**，则让同一模型可以由不同主体部署和提供服务。开放一个客户端，不等于它调用的模型也开放；能下载权重，也不代表训练与推理所需的资源人人都有。

Dax 主张各层都应存在开放、可自由取得的选项，同时允许专有模型和专有工具继续提供优秀产品。他在这里说的自由可及，并不是计算服务必须免费。

他也不认为道德愿望足以支撑开放模型。更重要的结构性动力是：一些国家无法使用美国公司的模型，大企业不愿把全部支出绑定到少数供应商，Baseten 这样的推理公司则需要开放模型才能开展业务。即使各方出于自身利益，也可能共同维持开放供给。

但训练需要大量资金，硬件可得性又有限。当美国 AI 大公司和大型科技企业吸收大量 GPU 产能，开放项目可能有动力却拿不到资源。长期激励能解释为什么有人会尝试，不能保证什么时候成功、以什么次序成功。

## 第三部分 · 从权重开放到真正能用的模型

### 权重能开放，部署它的硬件却可能买不到 {#gpu-supply}

**原访谈时间：31:11–38:53**

开放权重对推理市场的直接意义，是同一模型可以由许多家公司托管，用户不必只向一家购买服务。Dax 用一百家竞争者作示意，认为这样的竞争才可能推动价格下降。他还认为大型闭源模型公司的 token 销售毛利很高，但节目没有给出财务证据，不宜据此核算它们的利润。

竞争有一个物理前提：新进入者得拿得到硬件、建得起部署能力。Dax 对比说，一家创业公司能融资十亿美元已经很惊人，云巨头却能每年动用数百亿美元。开放推理公司即使产品和团队很好，也未必能在同一规模争夺资源。

他对短缺的担忧，来自合作伙伴及业内熟人的反馈。紧张的似乎不只是 GPU，还包括部署需要的其他硬件与劳动力。各方担心半年后拿不到容量，开始尽可能提前锁定供给；这种囤积又让眼前更紧张。团队试着判断传闻是否夸大，却发现接触的人大多处于囤容量的状态。这是他的行业访谈印象，尚非系统性供给调查。

几个大数字需要分清性质。他提到一个估算：基础设施建设可能需要约一万五千亿美元的借债，时间口头说成未来大约五年，又立即表现出不确定。节目没有给出处，也没有确定预测区间。他还举了一种情境：推理商即使有客户愿意下价值一亿美元的订单，也要先借钱扩建，而借钱本身可能越来越难。后者是解释融资约束的例子，不能当作已披露的客户合同。

主持追问企业如何面对 token 成本翻倍，Dax 特意澄清，自己并没有预测一定翻倍。价格可能涨，可能维持原位，也可能只是没有如预期继续下降。团队当时的做法是多买一些容量，争取覆盖未来约半年的扩张；他承认还在摸索。这不是一条经过验证、适用于所有公司的采购公式。

他也保留了相反的路径。疫情期间纸巾等商品因囤货显得极度短缺，随后供给动员又可能带来过剩。短缺创造利润机会，刺激生产，因而不必永久持续。不过，纸巾或粮食与 GPU 的生产复杂度不同，后者涉及多个国家、资源和政治关系；他希望最终出现更多供给，却不能保证类比成立。

由此引出的创业方法，是少把公司押在精确的短期预测上。Dax 说，一个预测常常需要大约六个假设同时正确，而且在正确时间发生，出错并不奇怪。他们更愿意占据一个有用的产品位置，每天解决用户正在遇到的问题。六个月前，他自己也没想到会进入推理生意、开始关心 GPU。这个经历支持的是跟随真实需要调整，而不是对未来毫无准备。

### 为什么他反感核武器比喻，却又用制衡解释开放？ {#power-balance}

**原访谈时间：38:53–41:56**

被问到 AI 越来越强大、是否应像武器那样限制在少数主体手中，Dax 先反对这个比喻。他认为，把科技公司形容成制造核武器的组织，会吸引公众恐惧和政府审视；其中还夹杂了从业者想把自己想象成曼哈顿计划参与者的心理。在他看来，AI 会非常有用、影响很广，但核武器式表述有所夸张。

随后，他接受这个比喻作为假设继续推演：即使技术如此强大，也不能指望某一个人或少数组织，连续几十年替全世界作出正确决定。他区分两种稳定。一种表面平静，偶尔爆发灾难性的巨变；另一种始终有摩擦、有竞争，让人不舒服，却可能避免一次力量失控造成整体崩塌。

他把核威慑时代多个国家相互牵制，当作后一种结构的类比。部分参与者并不被视为善意行动者，但持续张力限制了各方采取极端行动。他认为开放 AI 也值得从这种分散力量的角度理解。

这一段的逻辑可以解释他的价值立场，却不能证明开放模型的安全结果。他没有比较不同治理方式的事故率，也没有说明核威慑机制如何逐项对应模型传播。读者应把它看成政治历史类比，保留其启发，也保留未完成的论证。

Dax 还说这些并非自己发明的新观点，而与约十年前读《黑天鹅》《Skin in the Game》等书时接触的思想有关。他强调的是：稳定未必看起来整齐，竞争与持续调整可能比一个中心的良好意图更可靠。

### 中美开放模型的反差，与不必重建的工作流 {#open-weights}

**原访谈时间：41:56–48:11**

谈到开放权重的来源，Dax 觉得当时存在一种反差：通常被外界视为更封闭、更自上而下的中国，却在持续发布重要的开放权重模型；美国一些公司反而依赖这些模型发展业务。他一开始说得很绝对，随后补充美国也已有实验室投入，因此不能把这段摘成只有中国在做开放模型。

他的解释依旧是激励，而非道德评价。按他的判断，中国实验室在追赶领先的美国闭源模型，开放权重是获得注意力、让领先者的产品变得更像可替代商品的一种竞争方式。这既能服务自身利益，也可能让其他国家的开发者与推理商受益。

他认为美国早期资金对这种模式理解较慢，不容易看清开放模型怎样做生意；中国出现实例后，投资者有了参照，美国相关融资开始出现，虽然规模仍比不上领先大厂。资源较少也可能迫使团队寻找更高效的训练方法。他称一些中国模型已在更少资金和算力下做出令人印象深刻的结果，但未提供模型、成本与实验条件的成套对照。

对谈中出现了两个容易被当作统计事实的时间差。提问提到曾读到开放模型落后约十八个月、后来缩到约三个月，但没有给出来源和衡量方法。Dax 认可的是差距缩小的体感：自己关注这个领域还不到一年，早先闭源模型发布后似乎能占优约半年；到采访当年的前几个月，两边在相近时间推出新版本，表现却仍比较接近。

他并没有据此宣布开放模型更强，仍认为领先的闭源模型最好。变化在于，对他个人的日常使用而言，开放模型已好到可以经常用，而且不太想念闭源选项；他把这种感受的转折放在当年二月附近。没有具体任务集、成功率与版本清单，就只能保留为体验判断，不能改写成统一榜单。

模型可换由此获得了很实际的价值。领先者不断轮换，同一个模型也未必适合所有任务。如果这周围绕 Claude Code 建工作流，下周又为了另一款模型改用 Codex，用户可能反复重建工具习惯。OpenCode 想保持其余工具环境稳定，只改变所选模型。

Dax 自己通常在两个模型之间切换：一个负责大多数日常任务，另一个处理更长、更大、适合异步运行的工作。他没有在这里提供可照抄的模型组合。他也承认，很多人选定工具就一直用，这是合理的；模型切换能力服务的是有这类需要的人，而不是要求每个人追逐每次更新。

所以，模型可换解决的是选择与迁移成本，开放权重解决的是谁能部署、谁能提供服务，客户端开源解决的是谁能检查和改进工具。三者可以相互支持，却不应被压成一个含混的开放口号。

### 推理生意：最强模型不一定最划算，最便宜托管也未必可用 {#model-economics}

**原访谈时间：48:11–55:12**

OpenCode 开始介入推理服务，并不是因为团队一开始就决定做基础设施。Dax 原以为，用户想用某款模型，随便找一家供应商接入即可。产品上线最初几个月却不断出现愤怒反馈：工具不好用、结果不对。排查后，他们发现有些问题出在用户选到的推理供应商，模型并未被正确服务出来，最终却由 OpenCode 承受差评。

他自己起初也不理解：不都是托管同一个模型，为什么差异会这么大？后来才意识到，新模型不是下载下来、放上硬件就结束。还需要调优，与模型开发方和 Nvidia 协作，并针对负载优化。编程代理的工作负载又不同于其他应用。团队于是开始筛选合作伙伴、反馈问题，把用户导向质量可靠的提供方，并强调自己依靠这些专业伙伴，而非已经掌握全部推理技术。

选择标准的第一项，是部署后保留模型应有的能力。某些服务让模型表现得很差，用户容易误以为模型本身不聪明。第二项是速度：慢模型用久了会习惯，但一旦体验过快的模型，交互感受可能完全不同。他同时承认，价格与速度通常要权衡，便宜并非没有代价。

可用性也很重要，不过他们对推理商有一定容忍：同一模型接多家供应商可以提供替代路径，而推理服务仍在早期，不能假定已经达到经营几十年的云计算服务那样的成熟度。这是他们架构与行业阶段共同形成的取舍，不是说宕机不影响用户。

接着，话题从服务质量转向业务价值。Dax 反对所有任务都必须用最聪明模型的想象。当最强与次强之间差距收窄，而企业开始认真审视 AI 开销时，便宜得多但足够完成任务的模型会有吸引力。他用次优模型便宜十倍作假设，明确保留也许够用、也许不够的可能。对谈还提到企业看到每月百万美元级编程代理支出后开始想优化，但没有公开账单供核对。

一个更具体的案例来自客户 CTO：该公司的营销团队也使用 OpenCode，却总选择 Opus 和很高的思考档位，开销随之增加。CTO 认为这些营销任务不需要如此强的模型，希望提供更便宜、能力接近或够用的选项。节目没说这家公司后来换了什么，也没给降价或质量数据。这个例子说明任务有分档的需要，实际降本还要靠同任务比较。

从这几段可以整理出对读者有用的选择顺序：先确认部署没有破坏能力，再看完成自己任务的质量，接着把等待时间与费用放进实际工作流程衡量，最后问结果值不值得这笔支出。这是对节目判断方式的归纳。原文并未给出可计算的综合公式，也没有提供统一正确率、延迟百分位或模型价格表，不能代替具体业务测试。

Dax 长期看好开放模型获得大部分推理使用量，理由是成本压力和供给竞争，不是断言专有模型会消失。他用 iPhone 的强大公众形象与 Android 的整体份额作类比，说明人们最熟悉的产品未必占据整个市场的多数。但他承认，多数份额还可能很遥远，这本身就是下注。

供给又让价格预测出现两条分支。他转述一位投资人的框架：如果 token 需求指数增长，而 GPU 部署能力只线性增加，价格就有上涨压力。条件不能删掉；指数需求并不由这个比喻自动保证。另一种可能是，各家公司都害怕投入不足而错失市场，倾向多建基础设施，若干年后反而出现过剩、价格下降。他不知道转折时间，只把短期描述为混乱。

## 第四部分 · AI 写快以后，工程还剩什么

### 设计师终于能自己修界面，工程团队却多了一种担心 {#designer-ships}

**原访谈时间：55:12–1:02:14**

当问题转向软件工程师会不会被自动化，Dax 没有从未来能力曲线讲起，而是回到自己的团队：他们做编程代理，也大量使用自己的代理，却发现维护代码库的长期质量变得非常困难。他不是说每一次生成都错，而是说把团队的工作放在一起看，系统容易逐渐出现令人烦恼的变化。

他把工程判断描述为一条光谱。一端是容易完成、但很粗糙的办法，另一端是极其正确、却可能耗时太久的办法，中间还有许多选择。工程师要理解业务、当前目标和约束，才能决定停在哪里。这个困难在 AI 之前就存在；一个起初舒服的代码库，可能因不断选择省事方案，半年后变成大家不愿碰的东西。

编程代理放大的，是人本来就有的短期倾向。过去自己亲手写下丑陋实现，会直接感到不舒服；现在只要让模型去做，结果很快就出现，人可以不仔细看那段实现，却获得任务完成的满足感。生成速度提高了，承担后续成本的心理距离也拉长了。

设计师的例子把收益与代价放在同一件事里。设计师能看到普通工程师没注意到的界面细节，过去需要反复请工程师修改；现在可以自己借助代理修好，产品确实变得更精致。但设计师未必能判断实现是否令整体系统更脆弱，一些代码就这样进入产品，工程团队过后才发现。

Dax 特别强调，这不该归咎于设计师，理解那些系统后果并不是设计师的职责。难题属于工程团队：怎样保留参与能力，又建立能阻止长期腐化的护栏？他没有给出已经解决的流程，反而承认团队还不知道怎样有效工作、岗位该如何调整。编程代理有生产力、他们也喜欢用，与这些问题尚未解决可以同时成立。

那么，什么时候该接受一个临时实现？Dax 承认实现方案要随业务目标取舍，不能总选理论上最完美的一端；这为有意识的权宜实现留下空间。但字幕没有一例明确说明何时批准临时代码，也没有给出一次性脚本、限时实验、后续重写期限或清理责任的标准。这些具体规则还要由团队在自己的项目里试。能够确认的区别只是：理解代价后选择，与因为模型替自己写了就省去判断，并非同一回事。

他建议观察结果，而非工具使用姿态。一个人同时运行七个 Claude Code，并不能说明实际价值；更值得问的是，是否有小团队持续压倒更大的团队，是否出现竞争者因为更会用代理而彻底击败自己。他尚未在自身竞争环境中看到这种权力关系的剧烈重排，所以不愿接受所有夸大的生产力宣称。

这种观察也有边界：没有看到，不等于世界上不存在；他后来明确承认可能有自己尚未见到的变化。就当前团队而言，架构、系统设计，以及过去十到十五年积累的编程技能仍天天派上用场。明年模型会更好的回答，并没有自动解决今天的维护问题。

### 模仿 AI 赢家的样子，不能替代自己的基础能力 {#engineering-craft}

**原访谈时间：1:02:14–1:10:46**

对谈谈到，人手写代码时会仔细思考，使用 AI 时却容易直接接受修改。主持以为 Dax 的团队可能没有陷入这种模式，他立即纠正：他们也在做，他自己也一样。每天只是稍微懒一点，一年后回头看，工作习惯却可能已经变了。

让他感到不安的是，以前从不抱怨的手工操作，现在会显得异常缓慢、琐碎，可其中一些事仍然必须做。他把这种又受益、又受损，必须重新理解自己与工具关系的状态比作某种上瘾体验。这是个人心理感受，不是临床判断，也不是要求放弃 AI。

焦虑又会制造另一种替代品：模仿赢家的外观。人们知道技术变化会产生赢家和输家，却未必知道自己该做什么，于是猜测赢家一定把 AI 用到极致、并行开很多代理、拥有复杂工作流，再照着展示这些行为。Dax 认为这里有两层问题：没人确定未来赢家真长这样；即使长这样，复制表面动作也不会自动复制能力和结果。

他举 Mitchell Hashimoto 为例。HashiCorp 的开发工具曾影响自己的早期职业生涯；对方后来继续打磨精致的产品，也积极使用 AI。Dax 的感受是，自己仍然无法轻易与之竞争，因为对方原本就有强大的编程能力、产品判断和经验。AI 可以帮助这种人把优势继续扩大，不能指望只因自己用 AI 更猛，就突然超越对方。

这个例子承载的是嘉宾对技术品味和基础能力的评价，节目没有提供两人的生产率对照实验。它说明他为何不愿把工具熟练度当作唯一变量：最终选择什么问题、辨认实现好坏、打磨到什么程度，仍取决于使用工具的人。

对谈还提到一个从别处采访转述的设问：如果 AI 写了百分之九十五的代码，剩下百分之五的人类工作是什么？这些比例是讨论用的假设，不是本节目测出的行业现状。Dax 的回答很直接：剩下的部分仍然可能是编程。即使大多数代码由模型生成，一个真正优秀的程序员仍可能在关键处拉开差距。

他也反对所有人将变成代理管理者的笼统说法。自己做过中层管理，知道带真人团队包括激发动力、让人愿意克服困难；对代理下提示，并不需要同样的工作。键盘上输入的内容变了，他工作中真正耗心力的部分，却仍与十年前相似。

对谈谈到的学习焦虑也因此没有被一句 AI 会越来越强消解。若因为期待工具包办一切，就停止学习困难知识，预期没有兑现时会留下能力空缺。Dax 进一步认为，竞争、努力和做困难事情的需要仍会存在。这里既有职业判断，也有他个人的生活观：投入精力本身就是活得有意义的一部分，不应误写成对未来所有岗位的确定预测。

## 第五部分 · 在行业共识之外找机会

### 十六年的公司，想留下的并不只是一笔退出收益 {#stay-in-the-game}

**原访谈时间：1:10:46–1:18:34**

谈创业动力时，Dax 又回到公司已经存在十六年这件事。尽量活下去，是人人都听过的建议，听起来容易，实际却需要在觉得自己什么都做错、几次尝试全部落空时，仍愿意每天继续工作。

他把迅速成功归于能力、运气与时机的某种组合。不是每个人都足够聪明、足够幸运；持续留在场上，可以让自己多获得几次与机会相遇的可能。他见过一些公司一度走得比他们远，后来却消失，而他们仍能继续尝试。这里成立的是增加尝试机会的理由，不能推出只要存活够久就一定成功。

OpenCode 取得进展后，他们的目标也不只是卖掉公司。Dax 想建立一种能持续承载团队兴趣的公司：未来对另一件事产生强烈兴趣，仍可以在同一实体内做。他把 OpenCode 称为自己最后一项开发者工具，希望未来再做的东西能面向更广的人群。但那是什么产品、什么时候开始，他都不知道，甚至可能五年后才发生。这是一项愿景，不能读成已经公布的转型计划。

收购故事说明了他当时的心态。某家公司 CEO 来询问是否愿意加入、接受收购，他把消息发到团队 Discord，大家却继续讨论正在做的工作。主持提问时说的是 Slack，嘉宾叙述中明确换成了 Discord，因此这里采用后者。节目没有披露买方、价格或正式交易条件。

Dax 为同事的反应感到高兴。他刚创业时也把被收购视为理想终点；如今终于找到一个能服务大量用户的机会，立即卖掉，反而像把过去多年想做的事终止了。但他并没有宣誓永不出售，也坦言若有人愿意给出足够高的溢价，自己会考虑。保留这个条件，才不会把一段情绪真诚的故事写成绝对原则。

长期坚持并不意味着盲目坚持每一个功能。被问到众多用户有不同需求，如何决定方向时，他先说团队本身就是程序员，为自己做开发工具，理解问题比较容易。他对不熟悉一个行业、只看到一个空缺就进入的创业方式持谨慎态度；这首先是他的经验判断，并非所有产品都必须只为自己做。

同时，他们会花时间与用户和付费企业交谈。Dax 说，正在准备的新阶段产品，可能会在未来被外界解释成一次准确预言，实际却源于大约三位 CTO 的反馈。三个人说的具体事情不同，团队仔细听后，发现他们在指向同一个问题。

这也是小团队优势里最可辨认的工作：并非把需求单全收下来，而是在贴近使用的基础上识别共同原因。每条反馈都是一个真实数据点，用户却不一定能直接说出问题根源；把不同表述归纳成可解决的问题，仍是产品团队的责任。

### 三十分钟、零现金成本的后院发布视频 {#launch-in-backyard}

**原访谈时间：1:18:34–1:21:36**

谈 Zen 发布时，主持提到那支视频：Dax 在自家后院走路，用手机讲产品。相比大量精心制作的科技发布片，这种形式显得随意，却获得了不错的反馈。

Dax 说，营销已经成为自己在公司的职责。几年前他还认为程序员只管做产品，营销属于别人；后来为了让产品被看见，不得不开始学习。他的方法是长期观察别家公司怎样发布，寻找迅速形成的模仿链：一家先做出新鲜形式，随后很多公司照着做，原本令人惊喜的东西变成惯例。

在他观察到的那一阶段，连很小、很普通的更新都配上大制作视频。他判断观众可能已经疲劳。若别人花一万美元，自己也花一万美元去复制，最好不过拿到相近结果，还可能因为重复而更差。他另提到某些视频可能花了五万美元，却没有相称的公开互动；这些金额是他的推测，不能当作那些公司的实际预算。

于是他选择直接、简短地解释正在做什么、为什么做，避免销售腔。后院散步视频约花三十分钟，现金制作成本自述为零。他说效果很好，但没有给出播放、转化、收入或获客成本数据；零现金支出也不等于没有时间投入，更不意味着所有人都能复制同样的传播效果。

他尤其不希望听众把结论记成低预算必胜。真正重要的是理解当时观众没有明说的感受，再改变预期；下次有效的形式未必仍是后院手机视频。技术品味在这里延伸成传播判断：知道什么已经被用滥，知道产品此刻需要怎样被解释。

### 公开做产品，是把真实工作转化为持续交流 {#build-in-public}

**原访谈时间：1:21:36–1:26:15**

Dax 认可公开构建，但觉得这个词已被表演式模仿弄得有些空洞。对他而言，前提非常朴素：团队每天花至少八小时认真思考、学习和实现东西，结束时就有可以分享的内容——今天做了什么，发现了什么，哪个想法后来证明错了。

他们试着每周分享几次，长期重复。重点不是每篇都把人导向产品，也不是把一句工作记录硬接上购买链接。他觉得读者看得出这种动机差异。真实的工作与学习本身，应该足够成为交流内容。

这种分享首先反过来维持团队动力。谈论自己刚做出的东西让人开心，也吸引兴趣相投的人靠近；有些后来成为同事。公开讲一个问题，还可能收到别人掌握的知识，修正自己的认识。传播、招聘、学习与继续做事的动力，便在长期过程中相互加强。

Dax 说，他们已每周这样做了五六年，很多后来能做成的事情都建立在这层积累之上。这个时间尺度很重要：它不是一条今天发帖、明天增长的技巧。公司代码本来就开放，也使讨论工作的门槛更低。

对新人，他允许寻找榜样，却不相信复制榜样今天的动作就能抵达同一位置。可参考的是想要的结果，具体路径仍需要自己发现。一个人能够持续说出有意思的东西，通常是因为真的做过、学过有意思的事情。

这又通向他对效率执念的反感。如果创始人认为每一分钟都必须直接推进产品，任何绕路都算浪费，生活与工作可能越来越无聊，也更难产生值得分享的新东西。他希望留下一些游走、试探和偶尔古怪的日程，让创造性有空间。这个建议并不取消投入；它接在多年持续工作的经验后面，强调投入不必每一分钟都服从同一种狭窄目标。

对读者的应用，可以从这个前提出发：先看自己有什么真实问题、试验和认识变化值得讲，再考虑发布形式。把公开构建当作反馈与关系的长期来源，比照抄产品链接或某一种视频形式，更接近节目中的做法。

### 结尾没有给出安全路线，而是留下一个需要自己承担的下注 {#asymmetric-bet}

**原访谈时间：1:26:15–1:29:52**

临近结束，对谈谈到许多基本建议其实人人都听过，难的是照着生活。历史上的创造者常有独特、绕路的日程，而非把每一刻都压成标准化效率；Dax 用这种概括支持创始工作需要创造性的看法，并没有给出可复制的名人作息表或研究结果。

主持指出，AI 让很多创始人和工程师焦虑，人们更想从播客中得到一套让自己安心的策略。Dax 理解这种冲动，自己也会如此，但他区分当下感觉正确，与最终真的得到想要的结果。

在他的理解里，创业包含某种非对称下注：可能判断错误，但如果正确，收益会大得多。他用百倍差异作形容，并非承诺创业回报率。真正有价值的位置，往往是其他人忽略、甚至明确认为不对的东西；播客可以谈原则，却不能替某个听众发现那一项具体机会。

OpenCode 对 AI 编程的保守态度，就是他认为自己正在下的一注。他感受到许多同行更强调加速与未来替代，而自己反复讨论维护、判断和当下限制。如果这种立场被事实支持，公司将显得定位合理；如果事实走向另一边，他们也可能错。不能把他的行业印象扩写成所有竞争对手都持同一种观点，更不能因为访谈表达坦诚，就提前判定这笔下注获胜。

回看整场对谈，小团队的机会有一条具体脉络：多年开源经验帮助他们处理适配长尾，自己作为用户帮助识别需要，社区中的实际贡献帮助发现人才，长期公开分享带来反馈与信任，持续存活则让团队等到能力与机会相遇。这里没有一项能脱离条件独立保证成功，AI 生成速度也没有替代这些积累。

可带回自己工作中的，是分清问题的习惯。选择模型时，问任务是否值得那份能力、速度与成本；选择实现时，问谁理解它、谁验证它、谁承担后续维护；评估小团队时，看已经交付的结果及其形成原因。以上是从节目案例整理出的阅读应用，不是嘉宾公布的操作规范。对于首批用户动机、临时代码的可接受界限、模型实测表现与供需转折时间，这份字幕仍留下了真实空白，值得带着问题继续判断。
