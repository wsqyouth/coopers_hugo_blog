## 摘要

设想一次退款问答：如果正确的规则从未进入候选集，重排再准也补不回来；如果系统只取到“支持退款”，漏掉“付款后七日内，且服务尚未开始”，答案就可能丢掉决定性的条件；即使模型准确复述了整条规则，规则已经过期，用户仍会得到错误建议。RAG 的错误需要沿着证据进入系统、形成候选、保留在上下文、被答案使用的过程逐段定位。

这组材料的实用结论是：用同一批问题，分别检查证据覆盖、排序、上下文利用和最终任务完成。检索与生成要分开验收，忠实性与来源有效性也要分开判断。原始 RAG 模型、长上下文研究和 Ragas 指标各自回答了其中一部分问题；把它们组织成诊断流程时，还要固定语料、评判器与比较条件，才能知道一次改动究竟修好了什么。

## 逐段检查证据流 {#核心心智模型逐段检查证据流}

设计 RAG 的实用起点，是逐段检查证据有没有进入系统、进入候选集、保留在上下文中，并被答案正确使用。找到相关文档只是这条链上的一个环节。检索评测回答“材料找得怎样”，生成评测回答“答案如何使用材料”；两者需要分别观察。

分层评测是一种工程组织方式。它让“最后答错了”可以继续拆成具体、可检查的问题。

## 原始论文给出了特定模型设定 {#洞察一原始论文给出了特定模型设定}

原始 RAG 论文中的 RAG，是联合使用参数记忆与外部文档索引的概率模型。检索侧基于 DPR 双编码器，生成侧使用 BART；训练时固定文档编码器与索引，微调查询编码器和生成器。论文把检索到的文档视为隐变量，对不同文档条件下的生成概率进行边缘化。

RAG-Sequence 在整段输出层面对文档求和；RAG-Token 在每个输出 token 的概率计算中对候选文档求和。后者允许不同 token 借助不同文档，但不意味着每生成一个 token 都重新查询整个索引。

当代框架中的 RAG 则是更宽泛的工程模式。LangChain 官方文档区分了固定先检索后生成的 2-step RAG，以及由 agent 决定何时、如何取材的 Agentic RAG；已有数据库也可以直接作为知识入口。实际设计时，应先确定知识来源、控制流程与输出要求，再决定是否需要向量索引、训练检索器或增加 agent 循环。

## 召回与重排各有验收对象 {#洞察二召回与重排各有验收对象}

检索负责形成候选集合，重排负责在这个集合中重新安排优先级。候选中没有的文档，单靠重新排序无法补回来；已经召回但在上下文截取时被挤掉的证据，则需要检查排序和选择策略。

BM25 以词项匹配为核心，稠密检索用向量表示匹配问题和文档，混合检索结合两类结果。BEIR 的跨数据集评测发现，BM25 是有竞争力的基线，部分稠密模型的域外表现会下降；重排在该基准中表现较强，同时有更高计算成本。它支持保留简单基线、按数据分布验证的做法，不能据此给今天所有模型排出统一名次。

推断：如果用户的问题含大量产品编号、专名或精确术语，可以先并列测试 BM25、稠密检索与混合检索；如果有效候选已出现、排序却不理想，再测试重排。不同语言、文档类型和问题分布可能改变结果。

LlamaIndex 官方示例采用“较宽候选集＋较少最终节点”的流程。工程上应分别记录候选数和最终上下文数，检查证据在哪一步丢失，同时测量重排增加的延迟。扩大候选池是一项可验证的改动，不是收益保证。

## 分块决定证据以什么形状出现 {#洞察三分块决定证据以什么形状出现}

分块同时改变可检索单元及其嵌入表示，因此块大小必须与返回数量、上下文预算一起评测。LlamaIndex 文档指出，小块表示通常更聚焦，大块表示可能更概括；其示例在减小块大小时同时增加返回数量。这是理解参数联动的示例，不能直接当成某份语料的最优配置。

设想一段虚构说明：“该操作支持退款。仅适用于付款后七日内，且服务尚未开始的订单。”如果按边界切开两句，系统可能只找到第一句；如果把整章压成一个大块，又可能稀释具体条件。这个例子说明我们应检查的证据形状，未证明某种切分器一定更好。

推断：对带标题、步骤、表格或条件条款的材料，可先比较固定长度切分与尊重文档结构的切分；必要时测试用小块定位、再补充所属段落的方式。最小验证是检查关键条件是否仍完整，并在相同上下文预算下比较最终答案。增加重叠也需要检查重复内容是否占用预算。

元数据承担来源追踪与检索前过滤的职责。应保留文档身份、位置和适用范围；更换嵌入模型后要重新建立相关索引，并保证查询与索引使用相容的表示。实际应用还应确认所用模型是否有分别编码查询和文档的约定。

## 进入上下文的证据仍可能被漏用 {#洞察四进入上下文的证据仍可能被漏用}

上下文可容纳更多文本，并不保证模型能有效利用其中的证据。《Lost in the Middle》在其受测模型和任务中发现，相关信息处于上下文中部时，效果可能下降；开头与结尾往往更容易被利用。这提供了一个值得测试的失败维度，不能外推成所有当前模型必然遵循的定律。

推断：应把候选召回量与最终交给生成器的文本量分开调节。可以在保持证据集合不变时，只改变文档位置、无关材料数量或上下文长度，观察答案是否稳定；这样能减少把生成侧利用失败误归因于召回的机会。

忠实于上下文还需要与来源有效性分别检查。沿用一个虚构例子：检索到了已经过期的退款规则，模型准确复述旧规则，仍可能给用户错误建议。此时答案对所给上下文的忠实性可以很高。推断：版本、生效时间和来源选择应进入数据与检索检查；单看忠实性评分无法完成这项判断。

## 每个指标都要写清比较对象 {#洞察五每个指标都要写清比较对象}

Ragas 应按具体指标、输入与版本使用，不能统一解释为“无需参考答案的质量分”。原始 RAGAS 论文提出无参考答案的 Faithfulness、Answer Relevance 和 Context Relevance；当前官方文档还提供依赖参考答案、参考上下文或文档 ID 的指标及多种 API。

| 观察对象 | 指标或检查方式 | 主要比较什么 | 能回答的问题 |
|---|---|---|---|
| 候选集合 | 有人工相关性标注时的检索 Recall@K | 已召回相关证据与已标注相关证据集合 | 候选阶段漏了多少已知必要材料？ |
| 候选顺序 | 当前 collections API 的 ContextPrecision | 问题、检索上下文、参考答案；判断相关块在排序中的位置 | 有用块是否靠前？ |
| 无参考答案时的上下文比较 | 当前 collections API 的 ContextUtilization | 问题、检索上下文、实际生成答案 | 上下文与这次生成的答案是否相关？ |
| 参考答案的证据覆盖 | 当前 LLM-based ContextRecall | 问题、参考答案、检索上下文；拆解参考答案中的论断 | 检索材料能支持参考答案的哪些部分？ |
| 生成内容的可支持性 | Faithfulness | 生成答案中的论断与检索上下文；当前示例也传入问题 | 答案里的论断有多少得到上下文支持？ |
| 回答是否切题 | 原论文的 Answer Relevance | 从答案反推的问题与原问题的嵌入相似度 | 回答是否围绕提问展开？不直接衡量事实正确性 |
| 最终任务完成 | 本文建议的人工任务验收 | 问题、有效来源、验收标准与答案 | 答案能否用于这个具体任务？ |

**Context Precision 有排序含义。** 官方文档所示 LLM 版本使用类似 average precision 的加权方式，相关块的位置会影响结果。假设只有两个候选，其中一个相关：相关块在首位与末位的得分不同。该指标的分母围绕已返回集合中的相关块，不会告诉你语料中还有多少必要证据根本没被召回。文档中的 IDBasedContextPrecision 则直接按返回 ID 与参考 ID 的交集比例计算，不能混用两种解释。

**Context Recall 必须有参考对象。** LLM 版本把参考答案拆成论断，再检查它们是否被检索上下文支持；ID 版本比较返回 ID 与参考 ID。前者的参照是答案论断，后者的参照是证据 ID，均需记录参考集的构建方式。

**自动评分仍然依赖评判过程的质量。** 原论文在 WikiEval 上与人工偏好比较，并指出较长上下文中的关键句提取存在困难。推断：实际评测应固定评判模型、提示词、指标实现和输入快照，抽查其判定依据；自动分数与人工判断有分歧时，先理解分歧，再决定是否将该指标用于放行。

## 失败表：从可观察症状开始查 {#失败表从可观察症状开始查}

下表是一套工程诊断建议，用于组织排查顺序，各项原因都需要实际记录验证。

| 观察到的症状 | 优先检查 | 最小区分办法 |
|---|---|---|
| 原始文档中有答案，候选集中找不到 | 解析、切分、过滤、索引版本、检索方法 | 从原文定位证据，逐步检查它是否进入索引及候选 |
| 候选中有正确证据，最终上下文没有 | 重排、去重、截取与预算 | 对照候选列表、重排列表和实际 prompt |
| 块里有结论，缺少条件或例外 | 切分边界与上下文补充 | 用含跨边界条件的问题复测 |
| 上下文有足够证据，答案仍漏掉关键信息 | 位置、干扰、生成指令与模型 | 固定证据，改变位置或减少干扰，比较同题答案 |
| 忠实性高，用户仍得到错误建议 | 来源时效、参考答案质量与任务标准 | 回到有效来源核验，检查是否引用过期或不适用材料 |
| 自动分提高，人工体验下降 | 问题分布、指标参照、评判器判定 | 查看逐题变化，抽查评分与任务成功不一致的样本 |

## 最小评测：先形成可解释的对照 {#最小评测先形成可解释的对照}

建议先建立一个可人工检查的小型诊断集，再围绕失败类型做单因素对照。以下是待执行的方案，不含任何已测得结果。

1. **固定任务与语料快照。** 例如先选 30 个问题，覆盖精确术语、语义改写、跨段条件、时效或适用范围、无答案情形。这个数量用于起步排查，不足以证明整体可靠性。为问题记录有效来源、必要证据、答案要点或应当拒答的理由。
2. **建立简单基线。** 比较 BM25、稠密与混合检索时，保持语料、问题和生成设置一致。记录候选证据覆盖，并按问题类型查看结果。
3. **隔离重排收益。** 保持同一批候选，只增加重排；固定最终上下文预算，检查排序、证据保留和额外延迟。另做扩大候选池的实验，避免把两个变量合并。
4. **隔离分块与上下文因素。** 比较切分策略时重新建立各自索引，并说明预算口径；检查证据覆盖时优先依据原文位置，避免切分变化后仍拿旧块 ID 作金标准。测试位置效应时保持证据内容不变。
5. **分层记录结果。** 保存检索集合、最终上下文、生成答案和评分依据；同时看覆盖、排序、忠实性、任务成功、拒答与延迟。抽查自动评判分歧，保留一个未用于调参的检查集。

放行标准应先由应用目标确定。例如知识问答系统可以要求关键条件有证据、答案使用适用版本，并在信息不足时明确说明。具体阈值应由后续样本与人工验收校准。
