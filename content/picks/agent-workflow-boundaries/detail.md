依据厂商工程文章、官方文档和公开研究整理。原文的具体评测结果保留实验设置，迁移建议按工程推断理解。

## 核心心智模型：先决定谁控制，再决定多少人做

**推断：需要跨次恢复的调研可以采用“可恢复的阶段骨架＋阶段内自主研究＋独立核查”，但没有证据表明每次研究都需要多个研究 agent。** 人工确认和跨 run 恢复要求保存状态；多源探索是否值得并行，则要另看任务可分性、上下文损失和成本。三角色串行交接不等于多 agent 并行调研，也不自动获得厂商并行系统的收益。

控制流与执行者数量是两条轴。预定义 workflow 把主要分支和顺序交给代码；自主 agent 让模型根据工具反馈决定下一步。两者都能容纳一个或多个 agent。这里的“单 agent”指一个持续决策主体，可能经历多次模型调用和恢复；“多 run”指执行边界，“多角色”指职责边界，“并行”指时间重叠，这三者不能互换。

图是本场景的设计建议：秘书拥有控制状态，研究员拥有阅读包写入，核查者拥有核查结论，用户拥有授权和采用判断。读取同一事实不要求共同改写同一文件。边界明确后，研究阶段内部仍可按需要使用单 agent、只读子任务或独立搜索分支。

## 洞察一：升级应由失败形态触发

**先修复单 agent 的具体瓶颈，再增加拓扑复杂度，最符合这些材料的共同方向。** 如果流程已知且每步容易验证，固定链路更可预测；如果搜索路线会随发现变化，把路线写死反而限制研究。只有当多个方向可独立探索、局部结果可以被可靠汇总，而且收益足以覆盖通信成本时，才值得增加执行者。

| 来源组 | 官方给出的选择判据 | 状态、检查或完成机制 | 公开证据的限度 |
|---|---|---|---|
| Anthropic | 固定任务用 workflow，开放路径用 agent；2025 调研系统强调广度探索和独立上下文 | 主研究员分工、汇总；原文文件可绕过层层转述；使用结果 rubric 与人工测试 | 有内部调研 eval；尚未对不同的个人调研流程做比较 |
| OpenAI | 先充分使用单 agent；复杂条件逻辑、工具混淆在改善说明后仍失败，再拆分 | manager 把专家当工具；handoff 则转移会话控制；失败阈值及高风险操作可转人工 | 实用指南与 SDK 契约，不是多 agent 统一性能基准 |
| Google／ADK／DeepMind 合作研究 | ADK 提供固定模板、代码图和动态协调等组合；合作论文要求架构匹配任务可分性 | state 与历史事件分工；持久性依赖存储后端 | SDK 功能与论文实验是两类证据；没有“Google 全部系统都如此”的结论 |
| Cognition／Devin | 旧文反对丢失决策上下文和冲突写入；新文支持审查、咨询与受管理委派 | 干净上下文审查，执行者结合全局要求处理反馈；倾向单路写入 | 厂商实践报告；完整内部状态协议和成本分布未披露 |
| LangChain／LangGraph | workflow 为预定路径，agent 动态决策；同一图可混合两者 | checkpoint 保存线程状态，store 保存跨线程数据；interrupt 等待外部输入 | 提供持久化机制，不保证内容正确或外部副作用只发生一次 |
| Cursor | 长周期大型代码实验使用 planner、worker 和周期 judge；平级自协调出现瓶颈 | 共用协调文件的锁方案失败；分工后又删除了阻塞的 integrator | 官方研究经验；不能把代码量或持续运行时间当成功率 |
| Amp | 独立子任务、庞杂中间输出和隔离上下文是 subagent 的使用场景 | 子 agent 接收主 agent 提供的上下文并返回总结；长线程可 handoff 到新线程 | 当前文档说明能力；未披露同预算对照与通用完成判据 |

**推断：一个人工停止点足以要求可靠恢复，却不足以证明需要第二个智能主体。** 例如秘书确认提纲后，同一研究 agent 可以在下一 run 恢复；另设审校者解决的是验证视角。把这两种升级分开，才能知道多花的成本究竟换来了什么。

这些名称并无完全一致的行业边界。Anthropic 的 orchestrator-workers 也列在 workflow 模式下，因为编排结构可识别，而子任务仍动态产生；ADK 的 workflow 更宽泛，包含动态协作。比较时要描述实际控制与数据流，不能只比较产品标签。

## 洞察二：上下文要按职责共享

**“尽量共享上下文”和“让审查者保持干净上下文”存在真实张力，需要按职责解决。** Cognition 2025 年强调共享相关决策和完整轨迹，是为了避免并行行动各自假设；2026 年则发现审查者从 diff 重新调查更有价值，再让执行者结合完整要求过滤反馈。前者保护执行一致性，后者避免审查直接继承实现者的解释框架。新文仍保留对并行写入 swarm 的反对，并没有宣布上下文工程已不重要。

Anthropic 的研究系统主要把信息探索分出去，Cognition 的反例主要针对相互影响的行动。它们能同时成立：分别搜索七家官方资料时，发现结果可独立收集；共同修改一份尚在变化的结论时，术语、范围和判断会互相牵动。Cursor 的多 worker 写同一代码库实验更激进，但其任务规模、角色约束、周期重启和验证环境也不同，不能靠一个成功演示裁定哪种架构普遍优胜。

**推断：适合本流程的是“冷读”和“核查”分成两个阅读动作。** 审校者先只读精读版，测它能否独立讲清楚；随后读取原始请求、原文和证据表，核对事实与范围。核查者不应只拿研究员摘要证明摘要正确，也不必一开始就灌入全部搜索噪声。独立上下文改善发现错误的机会，仍无法消除同模型训练偏差或同源错误。

与此相对，Amp 当前文档允许 Task 子 agent 编辑文件、运行终端，因此“subagent 天生只读”并非通用事实。产品提供写入能力，不代表任意并发写入都有正确的合并语义。

## 洞察三：交接要同时传依据、版本与恢复点

**交接摘要负责导航，持久化产物负责保真，控制状态负责决定下一步。** 混在一段聊天里，接收者就难以区分已批准范围、暂时猜测和已完成事实；只留文件，也无法知道它属于哪次输入、是否可以推进。

| 载体 | 适合传什么 | 失败时会怎样 | 本流程中的对应建议 |
|---|---|---|---|
| 会话上下文／摘要 | 用户意图、决定理由、当前发现 | 压缩可能删除反例或授权条件；旧结论可能污染审查 | 摘要列出关键决定，并指向原请求和确认记录 |
| 结构化 state／checkpoint | 当前阶段、版本、待处理问题、恢复游标 | 内存后端重启丢失；保存状态不等于保存外部副作用 | TASK 维护阶段与指针，明确唯一写入者 |
| 文件／artifact | 原文、报告、代码和大体积结果 | 路径正确但版本过期，或者重写后回执仍指旧内容 | 交接时给产物版本、哈希与来源定位 |
| 阶段回执 | 消费了哪版输入、产出了什么、验证了什么、缺什么 | 自报 complete 可能掩盖语义错误或漏项 | 接收者验证回执所指文件，再裁决状态 |
| 人工确认记录 | 谁对哪个版本授权、允许哪一类动作 | 普通回复被当授权，或旧授权误用到新版本 | 记录真实消息与版本关联，范围变化再裁决 |

OpenAI SDK 的 handoff 有一个易混点：`input_type` 规定的是交接工具参数，例如转交原因，不会替换接收者的主要输入；默认会话历史仍传递，过滤历史要另外设置。应用本地 context 又是另一种载体。因此，“传了结构化 JSON”不等于“已经传完工作状态”。

ADK 的 state 是可序列化键值数据，历史保存在 events；`temp:` 只在本次 invocation 有效，`user:`、`app:` 与会话状态作用域不同。文档要求通过框架跟踪的 context／事件路径更新，直接修改取出的 Session 对象可能绕过记录。LangGraph 则区分线程 checkpoint 和跨线程 store，内存保存器不保证重启恢复。

**推断：持久化之外还需要重复消费的判定。** LangGraph interrupt 恢复会从节点开头再执行，因此暂停前的副作用应幂等、移到批准后或拆成单独节点。迁移到本流程，可用“任务＋阶段＋输入版本”识别同一交付，在再次 assign 或外部写入前检查是否已消费；这是一条设计建议，不是所读厂商内部协议的复刻。批准后执行同样可能因崩溃重试，不能把“放在确认后”当成恰好一次的证明。

## 洞察四：授权、检查与止损是不同的门

**人工授权回答能不能做，自动检查回答条件是否满足，独立核查回答结论是否可靠。** 将三者都叫“闸门”，容易把轻量自动检查变成反复请示，也容易只在交付末尾才发现早已传播的错误。

| 门的目的 | 合适位置 | 合格依据 | 失败后的动作 |
|---|---|---|---|
| 人工授权 | 范围形成、不可逆操作、需用户偏好裁决处 | 明确动作范围及被批准版本 | 保存现场，等待指定主体回答 |
| 机械检查 | 产生可验证中间结果后、进入下游前 | schema、文件覆盖、路径、版本匹配 | 同范围内修复；持续失败再升级 |
| 事实与质量核查 | 报告形成后，交付前 | 回到一手依据核对主要论断、口径、遗漏和反例 | 给可执行修改项，限定返工次数 |
| 预算止损 | 搜索、重试和返工循环内部 | 预算消耗、缺口、继续工作的预期收益 | 缩窄策略或返回明确 partial，不能假装已完成 |

Anthropic 早期模式明确允许中间程序检查，并建议自主执行有最大迭代数；OpenAI 指南也把超过失败阈值列为人工介入触发条件。这直接挑战“闸门只能在不可逆点和交付点”的字面解释。若那句话仅限制昂贵的人为审批，则可兼容；若连自动检查与预算中止也排除，就会增加错误传播成本。

**推断：你现有流程最值得先验证的是独立核查究竟纠正了什么。** 只统计“回执成功”和“目录合规”不能判断核查有无收益。应分别看抓到的事实错误、错误指控、修复轮数、读者理解与总成本，再决定哪些任务值得付出独立角色成本。先有一个临时评判 rubric，再用真实阅读修订；不能等用户读后才首次定义任何成功条件。

## 洞察五：多 agent 的收益必须连同预算一起读

**公开数字支持条件化选型，尚不足以为个人流程承诺速度、质量或成本收益。** 特别要区分比聊天多用多少 token、比单 agent 高多少分、同预算下是否更好，以及代码生成规模。

| 来源与时间 | 实际披露 | 口径与缺项 | 能支持的判断 |
|---|---|---|---|
| Anthropic，2025-06-13 | Opus 4 主导＋Sonnet 4 子 agent 在内部 research eval 相对单 Opus 4 提升 90.2%；agent 约为聊天 4 倍 token，多 agent 约 15 倍 | 未给该内部 eval 完整题集、样本量、绝对分数和同预算对照；倍数均以聊天为基准，不是金额 | 广度研究可以受益，也可能显著增加推理消耗 |
| Google 官方博客，2026-01-28 | 180 个配置、四个基准；可分金融任务相对提升 80.9%，顺序规划下降 39%–70% | 历史博客口径；不能与论文新版混写 | 任务结构会改变架构收益的方向 |
| 合作论文 v3，2026-04-08 | 260 个配置、六个基准、五种架构；金融集中式相对提升 80.8%，顺序规划最差下降 70%；交叉验证 R² 为 0.373／使用任务能力指标时 0.413 | 控制工具、prompt 和计算预算；模型与样本见原论文。SWE 和终端任务各仅 20 例；未对每家模型分别优化 prompt | 提供比厂商演示更可比较的条件性证据，收益仍需在目标任务中验证 |
| Cursor，2026-01-14 | 报告长期运行、并发规模、代码量及部分实验检查结果 | 没有本题可比的单 agent 成本／质量基线 | 暴露协调瓶颈；代码量不能代替完成与采用 |

OpenAI 指南、ADK 和 LangGraph 所选文档、Amp 文档没有给出可横比的实际单位成本。Cognition 后续文章披露了一些审查观察与模型咨询实验，但没有足够样本／控制信息来量化本流程收益。缺失不是零成本。

常见失败可以归为四类。探索预算失控会让系统反复找并不存在的材料；委派不清会让分支重复研究或漏掉问题；总结压缩与并行行动会丢失关键决定；平级协调、等待最慢分支和反复审查又可能吞掉并行节省的时间。**推断：每类失败都应有针对性边界，而不是再加一个泛化监督角色。** 对应措施是明确搜索停止条件、分工范围、原文指针和版本，以及可结束的返工循环。

### 完成证据需要分层解释

**运行结束只代表执行退出，交付完成还要证明内容满足请求。** 各家并没有共同的“done 协议”：SDK 的最终输出／退出条件是运行语义，框架的持久化是恢复能力，厂商 eval 是在指定任务和 rubric 下的结果。对自由文本研究，仍需要核实事实、引用匹配、范围完整和真实读者的使用效果。

| 观察到的证据 | 它证明什么 | 还不能证明什么 |
|---|---|---|
| 模型说完成、工具返回成功 | 声明已发出，或某次调用成功 | 请求整体完成 |
| 文件存在、hash 一致、覆盖检查通过 | 有这个版本，指定源文字被保留 | 译文准确、事实正确、论证有用 |
| 关键论断能回查原文 | 证据链可检查 | 没有遗漏反例或范围外推 |
| 经过校准的 eval／独立复核通过 | 满足给定 rubric 的可观测要求 | 新任务、新模型和实际读者也一样成功 |
| 用户读懂并采用 | 此次交付产生阅读或决策价值 | 长期可复用性、通用架构优势 |

**推断：一个足够小的完成合同是“输入版本＋可读产物＋主要论断的依据＋实际检查＋未解决项”。** 状态只有在接收者核对后推进；用户阅读与采用另作记录。新增角色是否有效，则通过在相近任务和预算下比较来验证。交付验收和读者采纳应分别记录。
