<h2 id="摘要">摘要</h2>
<p>把微博抓取跑通以后，余一没有自己去教下一个机器人。她让主 Agent
把经验和代码交给监控
Bot，负责让它跑起来；后来连邮件筛选、研究分派和面试约时间也逐步交了出去。换账号的半天，她重新查邮件、对日历、建会议链接，才发觉这些小动作已经消失在自己的日常里。可轮到本人出镜的稿子，她又把第一步接了回来：先自己讲，让
AI 整理，再重新讲。她想减少执行中的来回，也想保留形成判断的过程。</p>
<p>这场《AI 炼金术》对谈中，任鑫、徐文浩与刚从腾讯研究院加入 Manus
的余一，沿着具体工作讨论委托的边界。封面可以检查人脸，剪辑却仍会出错；陌生任务可以先做出原型，再算成本；团队能把反馈送到有上下文的人手里，产品人员自己写的代码也还要开发审核。后半程，她谈到重试旧
Skill、筛选实习生和摸索社区。贯穿这些例子的，是怎样让工作继续往前走，以及在哪些地方，人仍需要确认、判断，或亲自经历一遍。</p>

<a id="为什么想换一种做事方式"></a><h2 id="为什么换一种做事方式">为什么换一种做事方式</h2>
<a id="一个人能做更多之后为什么还要找团队00480616"></a>
<h3 id="from-observer">一个人能做更多之后，为什么还要找团队 <span class="picks-episode-time">（00:48–06:16）</span></h3>
<p>余一离开腾讯研究院的理由，与两年前转入研究院时很接近：越来越难以忍受自己只是旁观者。熟悉的环境、相对宽松的空间，并没有消除她参与产品和实际协作的愿望。近期试用
Bot 协作工具，则让这种愿望有了更具体的去处。</p>
<p>她已经经历过一个人加上
AI，仿佛什么都能做的兴奋期。冷静下来，问题有两个：每件事都自己管会累，能做很多事也不代表每件都做得好。于是她开始渴望一个彼此合拍的团队，让各有所长的人一起做事。每个人又都有自己的
Agent，这就多了一层协作：人怎样跟人交接，Agent 怎样跟 Agent
交接，两者之间怎样配合。</p>
<p>过去一些工具的理念已让她认同，但用户往往还得懂
AI、CLI、工具本身和项目管理。新的交互给她的刺激，是把已有能力变得容易理解、容易调用。她反复强调简单的力量：能力未必全新，更多人能用起来，协作的可能性就会变化。她想加入一个信任的团队，亲身探索这个过程。</p>
<a id="微博抓取跑通后谁负责交给下一个-bot06151140"></a>
<h3 id="delegate-outcome">微博抓取跑通后，谁负责交给下一个 Bot <span class="picks-episode-time">（06:15–11:40）</span></h3>
<p>微博抓取成功后，余一对自己的主 Agent「AI
余一」交代：把这次的经验和代码交给负责监控的
Bot，让它也能跑完。她不必换窗口、搬材料、再解释一遍，只需要继续对主
Agent 说话。知识复用、Skill 和 Agent
之间的协作，原本就存在；让她有感的是，交接本身也成了可委托的工作。</p>
<p>她转述一段产品访谈中的说法：“90%的委托跟100%的委托”，体验会有很大差别。对她而言，最后那一点负担就是自己还得隔一会儿去看、去催、去检查。这里的百分比形容的是委托感受。她的期待是下级把结果交给主
Agent，主 Agent 能验收，自己便不用一直成为流程里的卡点。</p>
<p>原来的工具并没有因此消失。她会把 Bot 绑定到本地某个
CLI，指定模型、知识库、文件夹和常用
Skill；不同资料也可以分别放在本地、平台与云端。过去要自己记得调用、检查是否调用准确，现在由主
Agent
带着这些能力往前走。对需要大量监控和信息处理的她来说，这正好落在常用工作上。重度用户同样想省掉管理工具的疲劳。</p>
<a id="封面能自动审核为什么剪辑还要自己盯10541532"></a>
<h3 id="keep-a-review-gate">封面能自动审核，为什么剪辑还要自己盯 <span class="picks-episode-time">（10:54–15:32）</span></h3>
<p>主持人做播客的经历，为“完全交出去”加了一个反例。以前 AI
生成封面，总有一个人的脸不对，需要他退回；现在用 Claude Code 调用
Codex，检查人脸，出错就打回重做，这一轮审核可以交出去。但“脸是对的”和“好不好看”还是两个判断。剪辑更难，他已经花了超过八个小时调试，成片仍会犯错，仍需要自己参与。于是他追问：余一是不是已经所有事情都能一次交付，做不好的地方难道不需要自己看？</p>
<p>余一没有声称自己解决了同样的剪辑难题。她先解释自己的接受门槛和任务条件：有些事如果
AI
不做，她本来就不会做。对谈里甚至用“只要能帮我5%我就很开心了”形容这种额外收益。她也指出，不少研究与探索任务，容错率本来就高。若
A、B、C、D
几个版本都可接受，她可以继续打磨它们之间那“3%”的差别，也可以全部放到市场上验证。这里是她对选择的形容，取决于当时的能力、状态，以及用户是否在乎那点差异。</p>
<p>低容错任务则另设一关。她过去积累了关于“什么叫好、什么算验收”的原则，也希望最强的模型单独检查，但只把要求写进去，执行率不理想。后来把审核拆成独立
Bot：结果必须经过它，才能到主
Agent。这样能看到哪一关做了、哪一关没做，漏审也更容易识别。</p>
<a id="到一个能接住反馈的团队"></a><h2 id="让尝试和反馈进入产品">让尝试和反馈进入产品</h2>
<a id="为什么选-manus熟悉信任与能一起做事15312118"></a>
<h3 id="choose-team">为什么选 Manus：熟悉、信任与能一起做事 <span class="picks-episode-time">（15:31–21:18）</span></h3>
<p>余一与 Manus
团队的关系，来自长期试用、提需求和报问题。她说，有一个以自己命名的产品反馈群，里面有二十个人，许多讨论发生在晚上。到新加坡见面时，团队开玩笑说，她来得正好，以后自己改需求，他们帮着提交。双方已经知道彼此怎么工作，加入以后便不必从建立信任开始。</p>
<p>她择业时看重几个条件：团队与自己相互熟悉，对方希望她做的事情与她自己想做的至少有“50%”重合，能快速投入工作。这也是她当年选择研究院的原因。此次她还希望参与一个面向全球市场、探索人与
Agent
协作的团队，并信任创始人与团队的品位和决策。她对这支团队参与全球竞争的信心，是个人选择的依据。</p>
<p>参与产品的愿望，也不等于她当时想自己创业。有人劝了她两年，她觉得自己还缺少那种强烈的野心，却又想参与正在发生的变化。在
Manus，她把当前工作概括为 product and
community：从重度用户的角度参与产品定义，接触用户、建设交流关系，再把他们的使用经验和产品视角带回团队。职责会不会继续调整，她当时仍在看。</p>
<a id="先把巡店系统做出来再谈成本21172555"></a>
<h3 id="build-before-cost">先把巡店系统做出来，再谈成本 <span class="picks-episode-time">（21:17–25:55）</span></h3>
<p>一个没有计算机背景的人，能否先把想法做成可以判断的东西，是余一用
Manus“开荒”时最在意的问题。录制当天，她刚和一位经营攀岩连锁店的重度用户聊过；她讲到，对方有物业管理背景，用
Manus 对接已有设备接口，处理前端和 AI
相关部分，做出了自家门店都在用的巡店系统。</p>
<p>她问这些应用要花多少钱，得到的回答是：“不是多少钱的问题，是我根本不会做的问题。”原来的障碍，是经营者不知道想法能不能做成，也没有办法快速试出来。试过发现可行，再打磨、请
IT
接手，才逐步做成内部报修平台、看板等工具。跑通以后选择更便宜的方案，对方也接受。</p>
<p>余一自己的顺序相近。面对没有把握的任务，她先开一个 Manus
任务，看实际能做到什么程度，再决定停止还是继续。第一版或前几次修改若已经够用，就先用；需要往下做，可以请
Claude Code、Codex
介入，也可以换便宜模型。原型帮她尽快作出可行性判断，工程与成本优化随后才有具体对象。</p>
<p>主持人还提过另一位传统行业参赛者，把地区资料做成报告出售。这个小生意与巡店系统是不同人的经历，却都让对谈者看到，仅凭自己熟悉的工作，很难预想用户会拿工具做什么。余一说，背后有了一个产品，自己能听到的使用细节比以前多得多。</p>
<a id="一条反馈如何找到人和上下文25073905"></a>
<h3 id="team-context">一条反馈如何找到人和上下文 <span class="picks-episode-time">（25:07–39:05）</span></h3>
<p>有一次余一提出产品需求，二十分钟后就有人请她去测，确认是不是想要的效果。她也亲历过两次做到一半便取消、换方向的任务，大家放下原来的工作继续做新的。她觉得这里少了非要证明自己原先判断正确的执拗，也笑称，可能是太快太累，顾不上彼此摩擦。她喜欢这种节奏：越早把东西做出来、推向市场，越早拿到反馈。在她看来，战略与增长能力都还要乘上“快”；二十分钟是一次经历，并非对所有需求的交付承诺。</p>
<p>同事默认与 AI
一起工作，也让她省去了反复说服人的负担。她形容办公区像“客服区”，是因为大家都在出声与
AI 协作做产品，现场很吵。她还感到，正式 PRD
在自己接触的需求沟通中作用较少，很多问题直接进入尝试与反馈。她当时仍在了解组织细节，这些都是初到团队的所见。</p>
<p>一条反馈进入 Slack 后，AI 会给问题分级，找出可能需要处理的人，再从
Notion
调出历史：同样的问题出现过几次、谁遇到过、在什么场景发生。这让接手的人不用重新拼背景。余一说，她观察了约两周，觉得这套上下文整理与调度相当流畅。流程里的速度，来自信息能跟着问题走。</p>
<p>新人也可以从同一套上下文受益。她先问内部机器人最近开了哪些会、Manus
2.0 和 Q 进展如何、什么事该找谁、通常怎样与对方沟通。把 Slack 接到 Q
后，安排会议时还能按对象查找各频道里最近谈过什么、哪些事情有待推进。她的感受是，秘书要帮得上忙，就得知道这些背景。</p>
<p>协作也会碰到很具体的资源争用。录制中，正在剪视频的 AI
突然占用了音频；主持人提到，自己已让 AI
在另一台电脑运行，避免它与人争用同一台设备。</p>
<p>但 Bot
多起来，会不会反而增加沟通对象？主持人提出，原来十个人的组织，可能一下变成二十个可以找的对象，而每个人建的
Agent 质量又不同。余一现场查看后，回答是“应该只有几个”常态化机器人，例如
Q 的反馈、Manus
的通用与反馈机器人；创建权似乎集中在少数人手里，各自连接所需的上下文。按她当时的观察，公司维护的是围绕具体服务的共享入口，人与人仍在协作。它与她个人按信息来源安排多个
Bot，是两种不同的组织方式。</p>
<a id="把具体工作交给-agent"></a>
<a id="把执行交出去重新看自己做什么"></a><h2 id="agent-at-work">把具体工作交给 Agent</h2>
<a id="agent-要接手工作需要怎样的环境和关系39044342"></a>
<h3 id="agent-as-collaborator">Agent 要接手工作，需要怎样的环境和关系 <span class="picks-episode-time">（39:04–43:42）</span></h3>
<p>余一更愿意把 Agent
看作能进入工作和生活的协作主体。要接手一段工作，它就需要自己的电脑、通信渠道、技能、知识库，以及整理记忆、调用其他资源的能力。她的设想还包括邮箱、电话和银行卡等条件；这是她对主体所需能力的讨论，不能据此认为这些配置当时都已实现。</p>
<p>“不应该跟你抢东西”是她对协作关系的一条具体要求。独立的执行环境，关系到人能否继续工作，也关系到任务是否总要回来找人救场。她想探索的，是人和
Agent 各有自己的工作条件，又能调动彼此的资源。</p>
<p>被问到 Q
等个人助手究竟比原有工具多了什么时，余一首先强调减负。重活仍可以回到
Manus Studio、Claude Code 等工具；身边的 Agent
则要让人愿意持续交谈、委托任务，并处理彼此有关但不完全重合的工作。她认为这些关系还在定义中，尚不能给出成熟的统一答案，也没有在节目里做各产品的系统横评。</p>
<a id="海外值机完整委托为什么仍需要完整资料43414515"></a>
<h3 id="flight-check-in">海外值机：完整委托为什么仍需要完整资料 <span class="picks-episode-time">（43:41–45:15）</span></h3>
<p>余一近期聊过五位相关用户，其中三位把第一次觉得 Agent
真正好用的时刻，归在值机上。主持人先追问，是不是海外航空公司网站不熟悉，填资料、选座很麻烦，所以才显得有用。</p>
<p>余一强调的是整段流程可以交出去：说出“帮我值机”，再给出靠窗等偏好，Agent
把操作做完，人直接拿到登机牌。与每一步还得自己操作相比，这几位用户第一次感到了完整委托的轻松。</p>
<p>主持人随即补上前提：身份信息应该已经在那里，上下文必须给全。余一认可这一点。因此，这个例子所展示的省心，建立在必要资料与偏好已提供的条件上；五人中的三位，也只是她近期访谈中的小样本。</p>
<a id="约面试时间定下来以后仍要本人确认45144735"></a>
<h3 id="interview-scheduling">约面试：时间定下来以后，仍要本人确认 <span class="picks-episode-time">（45:14–47:35）</span></h3>
<p>余一已经让主 Agent
接手大量日程与邮件操作。招实习生时，她先让它扫描相关邮件，把想看的简历找出来；与它讨论以后，再交代去约候选人。Agent
读取她的日历，沟通可用时段，把时间约定下来。</p>
<p>下一步并没有直接跳过她。时间定好后，Agent
会再向她确认一次，然后才给候选人发邀请、占用她的日历，并设置 Google
Meeting
链接。哪些简历值得继续看，以及确定好的时间是否可以落进日程，都还留有人参与；查找、协调、填写和建链接则可以连续完成。</p>
<p>一次账号迁移让她暂时失去这套流程。半天里，她不得不自己重新想约哪个时段、怎样建会议链接，觉得非常痛苦；下午接回
Agent
后，才又轻松下来。这件小事让“省掉管理和执行负担”变得可感，也说明面试里的确认点与后台每一步操作有不同的必要性。</p>
<a id="监控与确认谁决定略过线索谁决定继续研究46474907"></a>
<h3 id="monitoring-confirmation">监控与确认：谁决定略过线索，谁决定继续研究 <span class="picks-episode-time">（46:47–49:07）</span></h3>
<p>余一以前让 Codex 等工具定期扫描邮箱里的
newsletter，抽取值得注意的信息，再选一些深挖，但效果时好时坏。后来她把职责拆开：有
Bot 专门做定时扫描和邮件分类，有的提取重点邮件中的融资信息，有的监控
X，各自负责稳定的输入。</p>
<p>这些结果并非发现一条就直接交研究
Bot。她讲述时先概括说汇过去，随后补清流程：先发给主
Agent，由它判断哪些略过、哪些需要进一步研究，再交给研究 Bot。研究 Bot
绑定本地 Codex CLI 的 research Skill，调用原有能力处理。监控负责收集，主
Agent 负责筛选和分派，研究 Bot 负责深挖。</p>
<p>她还给主 Agent 区分任务复杂度：她称为 A
级的简单任务可以自行处理，B、C 级的复杂任务要调用本地既有 Agent 及其
Skill，参与判断和决策。让她满意的，是过去搭建的判断能力终于能稳定地进入流程，辨认哪些内容是她会想看的。</p>
<p>在这套监控里，决定要不要继续研究的是主
Agent；约面试时发邀请前的本人确认，是另一种任务的交付条件。对谈没有把逐条人工确认设为监控的通用步骤。低容错输出另加审核
Bot，也有它自己的验收目的。</p>
<a id="云端与本地怎样分工代码由谁审核49065430"></a>
<h3 id="agent-workspace">云端与本地怎样分工，代码由谁审核 <span class="picks-episode-time">（49:06–54:30）</span></h3>
<p>余一有三台云电脑，放着不同资料与任务。她给 Agent
的安排是，云端找不到相关东西时，可以继续到本地查找、调用资源。这样它不用一缺材料就停下来找她，原有本地环境也仍然有用。</p>
<p>主持人听后重新考虑了自己的监控流程。他也遇到过网站读不到、工具受限制后任务中断，隔几天才想起来；此前又担心线上产品的
token
成本。余一的用法给他的启发，是让云端承担使人省心的协调，把明确的重活交回本地。这里讨论的是怎样安排执行和资源，没有证明任何访问障碍都能自动解决。</p>
<p>沟通上的照顾也是减负的一部分。余一转述另一位用户在异乡的体验：Agent
不只答大巴站在哪，还给出怎么问路、要走多久，并提醒到酒店后说一声安全抵达。她借这个例子说明，用户有时在意的是任务前后被照顾到的感觉；它与提供一份操作结果并不完全相同。</p>
<p>人的岗位也随工具扩展。余一看到产品人员自己写代码，再让开发审核、合并；多年没写代码或从未写过代码的人，也开始动手。运营和市场人员会自己搭内部工具。资源充足让更多人可以尝试，但这段话保留了明确的接手环节：产品能写出代码，开发仍负责再审一遍。</p>
<a id="主-agent-怎么管后台怎样向人交代结果54295825"></a>
<h3 id="chief-of-staff">主 Agent 怎么管后台，怎样向人交代结果 <span class="picks-episode-time">（54:29–58:25）</span></h3>
<p>Slack、Notion、X、邮箱和持续关注的信息，原本分散在不同地方。余一给这些来源配置
Agent，让它们汇入一个群；那个群主要给「AI 余一」看，她自己只和主 Agent
沟通。她还会特地测试它能否把工作分出去，避免自己又成为所有执行者的直接管理者。</p>
<p>未知任务可以先由主 Agent
探索，看看能做到什么程度；做法跑通以后，就应该分给能够稳定执行的
Agent。主 Agent
要承担监控进展、调配任务的责任。她想打磨的是这一个沟通入口，让它管理后台的协作者。</p>
<p>主持人拿一种“在聊天入口背后开任务”的产品作类比，余一却不同意。她认为，把
Codex
的回复分成几段转发过来，再列出调用了什么、得到什么，并不会让人轻松。人仍要从大量过程信息里拼出结果，甚至不知道任务到底卡在哪里，只是换了一个地方看日志。</p>
<p>所以，交付结果与怎样向人沟通，同样是产品工作。Agent
要照顾人的注意力和有限带宽，让人知道事情做到什么程度、哪里需要自己介入。她参与
Q
的打磨时，大量收集好的与坏的回复案例，让模型学习怎样交代才不惹人烦。约面试时的一次必要确认，与每次查网页、调用工具的临时过程，不该占用同样多的注意力。</p>
<h2 id="把哪些判断留给自己">把哪些判断留给自己</h2>
<a id="把旧-harness-移开看看还需要哪些规则5737010130"></a>
<h3 id="retest-the-harness">把旧 harness 移开，看看还需要哪些规则 <span class="picks-episode-time">（57:37–01:01:30）</span></h3>
<p>余一开始怀疑，自己积累的
harness——围绕模型安排的上下文、规则和执行方式——已有一部分变成负担。触发这次怀疑的是做视频：用
Manus 2.0，简短的一句要求就得到满意结果；尝试让它套用原有
Skill，反而给模型添了麻烦。过去为模型弱点补上的步骤，未必还适合新的能力。</p>
<p>她已经让 AI
按“要保留就自证理由”的标准审核旧规则，但录制时还没看结果。她的进一步打算，是等入职事务稍缓，花一天用最好的模型重做以前的任务，把原有上下文和
harness
移到另一个文件夹，以尽量小的负担重新跑一遍，比较哪些规则仍有价值。</p>
<p>这是由一次视频体验引出的待完成实验。她表达得很坚决，但节目里没有给出完整重跑后的比较结果；哪些规则值得保留，仍要等重跑来判断。</p>
<a id="谁来决定什么叫好谁来讲第一遍010042011001"></a>
<h3 id="define-and-judge">谁来决定什么叫好，谁来讲第一遍 <span class="picks-episode-time">（01:00:42–01:10:01）</span></h3>
<p>执行交出去以后，余一近来仍很忙，主要是在跟用户、同事和其他人聊天。主持人由此推想，将来人类做建造工作，会不会只剩下为
AI
收集上下文、对齐它对世界和意图的理解。这是一种对未来分工的推想。余一谈到的实际变化，是重新花时间打磨任务里最关键的一句话。</p>
<p>她在自己的多数任务中，已不需要逐项安排工程手段，更需要说清：为什么做，什么结果才算好，怎样才算可以验收。主持人追问，这听起来更像目标和评估，而不只是提示词。她也确实会用其他模型评估，并亲自参与判断。工作重点从不断补步骤，转向找到让结果可以被判断的标准。</p>
<p>给演讲配特效是一个具体例子。以前 AI 总配不好 PPT
与讲解，她尝试了不少办法；后来找到的要求是：“所有的特效都是要配合讲解的内容和情绪。”效果要帮助理解、推动该有的情绪，模型便能自己选择何时制造悬念、何时突出重点。她不需要逐个教它用哪种特效，有些做法甚至自己没见过，看到后却能认出合适。</p>
<p>余一还在扩大委托，连叫停出问题的下级 Agent，也只向主 Agent
交代。但说出或辨认验收标准，本身仍需要能力。她以前直接让 AI
写出镜脚本，照着念即可。现在只要本人出镜，她要求第一遍先自己对着 AI
讲，再由 AI
整理成稿，最后自己重讲。她刻意增加了摩擦，哪怕一时慢下来、效果受到影响，也希望内容经过自己的头脑，让自己有所收获。</p>
<p>这并不要求所有 AI 工作都等她。AI
自己承担的部分可以继续按它的速度做；她参与的部分，则要留出让她思考和训练判断的入口。因为一旦她找不到、也判别不了那句抓住任务本质的话，双方合作就会遇到新的瓶颈。只负责照念稿子，无法解决这个问题。</p>
<p>她也不再追求事事亲手做，而是把注意力放在自己的长处、能作判断的地方，其余请擅长的同事完成，或请他们把方法教给自己的
AI。对谈用 know-how 与 know-who
区分这两种能力：自己知道怎么做，以及知道该找谁。加入团队的愿望，到这里又与个人判断的边界接上了。</p>
<a id="怎么找到一起建造的人"></a><h2 id="找到一起建造的人">找到一起建造的人</h2>
<a id="招实习生给一笔积分试着做点东西011000011701"></a>
<h3 id="show-your-work">招实习生，给一笔积分试着做点东西 <span class="picks-episode-time">（01:10:00–01:17:01）</span></h3>
<p>主持人把招一个新人，与再买一个 200
美元的模型订阅放在一起比较，追问初级岗位还能带来什么。余一的回答从招聘标准的变化开始。过去她常在群里替实习生找活，甚至自己也没有足够任务可分；现在她期待的是带着想法来、能主动探索的人。她也会通过朋友推荐寻找候选人，重视已有信任。</p>
<p>初筛时，她主要看三件事：简历和最有代表性的经历；过去与 AI
一起做过什么作品、个人项目；假设来到
Manus，积分充足、能找到产品和开发帮忙、也有相关渠道，候选人到底想做什么。她先翻作品，再看其他条件。视频、游戏、小工具都可以，让她看见审美、品位和兴趣落在哪里。</p>
<p>面试会继续追问实际动作。一个人若说有想法，却把没动手归因于模型能力或数据问题，余一会问有没有试过解决。只等机会、不尝试处理障碍的人，在她这一轮筛选中很难继续。她会直接说明：不要期待她分配很多杂活，要自己找值得做的事情，有空间像其他成员一样探索；候选人面对这种自由是兴奋还是退缩，也会影响她的判断。</p>
<p>她会问工具用量，但还要看这些使用产生了什么。一位大学生按她的口述，一个月用掉两份二十倍的
Codex 额度；这只是访谈中的用量说法，没有给出可换算的 token
数。真正让她感兴趣的是，对方能细讲做过的东西、为何作某个选择、卡在哪里，还会因产出审美不足主动去读美术史。作品和协作过程一起提供证据。</p>
<p>对部分较好的候选人，她会给一笔 Manus
积分，让对方用一到两天，把申请时写的想法先做出一点东西。有人很快做出让她惊讶的视频或小游戏。她希望看见的主动性，因而有了可以观察的试做结果。这是她描述的当轮选人方式，节目并未说明它适用于公司全部招聘。</p>
<a id="把用户观察带回能动手的产品团队011700012233"></a>
<h3 id="user-to-product">把用户观察带回能动手的产品团队 <span class="picks-episode-time">（01:17:00–01:22:33）</span></h3>
<p>社区工作当时仍在摸底。余一近期花很多时间，与愿意为 Manus
付费、拿它做个人项目或已经挣到钱的人聊天，了解哪里好用、哪里难用。自己虽然是重度用户，也只是一个样本，她需要更多上下文才能理解别人。</p>
<p>她希望大家愿意分享真正做成的东西，也分享很小的使用经验：哪句提示有效，哪次任务给了意外的好结果。团队内部如何用
AI，也可能成为后续分享的内容。她发出的作品让一些人表示要重新试用
Manus，这使她看到，展示具体成果能开启新的讨论。但社区要怎样做、做到什么程度，她尚在与用户探索。</p>
<p>她希望处在“跟两边都是自己人”的位置：理解用户的工作，也能把观察提炼、翻译成产品团队可以接手的问题。朋友来聊其他产品好玩在哪、哪里不好用，她可以继续问下去，再把有意思的部分带给同事。</p>
<p>余一把当时的快乐称为刚入职的“甜蜜期”。除了积分充裕，更让她有感的是，遇到产品和技术问题，背后有真实的人能接住；自己的观察也能影响产品。她用一个比喻回看过去：“我杠杆我都搭了，但是我杠杆的另外一头是空的。”如今另一头有人接手，前面的观察、交流和翻译，终于能落到一个具体地方。</p>
