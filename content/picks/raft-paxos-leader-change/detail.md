## 核心心智模型：换主必须继承已经约束住的历史

理解两者的共同起点，是“后来的决定必须尊重先前已经形成的决定”。多数派交集让新一轮处理过程遇到旧历史的见证者，但交集本身还不够：协议还要规定见证者保留什么、后来者如何处理这些信息。Paxos 用承诺和提案选值规则承接历史；Raft 用选举限制、日志匹配和提交规则承接历史。阅读这份材料时，可以始终追问：新领导者凭什么知道自己有权继续写？

比较时应把 Raft 的复制日志与 Paxos 的状态机扩展放在同一层。Paxos Made Simple 先讨论单值共识，最后一节已经讨论多实例、稳定领导者、流水线与重配置；不能把前半篇的单值协议当成 Paxos 工程实现的全部。

| 维度 | Paxos Made Simple 所呈现的路线 | Raft 论文所呈现的路线 | 工程含义 |
|---|---|---|---|
| 设计目标 | 从选值的安全属性推出协议，再把实例组织成状态机 | 以可理解性为主要设计目标，分解选举、复制和安全性，减少状态空间 | 比较协议如何帮助人维持约束，不能直接推出性能排名 |
| 安全性证明 | 借助提案号归纳、跨多数派信息继承，保证更高编号提案保留已选值 | 用日志匹配、选举限制和当前任期提交规则，证明领导者完整性，再推出状态机安全 | 两者都要说明未来为何不能产生冲突决定 |
| 工程实现 | 稳定领导者可复用第一阶段；需要组织实例、补齐空洞并按序执行 | 领导者维护一条日志，修复跟随者后缀；论文另外讨论快照、成员变更和客户端交互 | 实现仍须正确接入持久化、网络和应用层语义 |

## 洞察一：Raft 的区别在于组织方式，Paxos 也能有稳定领导者

Raft 把领导者选举纳入协议核心；Paxos 的基本选值安全性不依赖所有进程先一致承认一个领导者。Raft 的候选者要通过带日志约束的投票，成为某一任期的领导者，再向外复制自己的日志。Paxos 中 proposer、acceptor、learner 是逻辑角色，一个进程可以兼任多个角色；不能据此推断它必然是一个没有领导者的部署架构。

Lamport 在进展讨论中要求选出一个指定提议者，避免多个提议者不断抬高编号、相互抢占；在状态机一节里，这个角色就是稳定领导者。新领导者先处理相关实例的第一阶段，继承已经受到约束的值；对尚未受约束的后续实例，稳定期间可直接发第二阶段。因此，“Paxos 每次写都比 Raft 多一个完整阶段”并不成立。

Raft 选择更强的领导者结构：日志内容由领导者向跟随者流动，新领导者当选时就必须已经包含已提交历史。这样的约束缩小了要解释的状态空间。代价与收益需要结合具体系统判断：可理解性更好不等于容忍更少的正确性条件，也不等于在所有网络布局和负载下更快。

两篇论文都面对非拜占庭故障。消息延迟、丢失、重复以及节点崩溃恢复，不能使已形成的决定相互矛盾；但系统是否还能及时形成新决定，需要足够节点和通信条件。超时帮助恢复进展，不能单靠“超时已经发生”证明另一份历史正确。

## 洞察二：Paxos 的证明把“见过旧值”变成后来提案的约束

Paxos 的安全性关键是后续提案必须继承约束，而不是简单禁止 acceptor 接受第二个值。对同一共识实例，提案包含全序且不重复的编号与一个值；当同一个提案被多数 acceptor 接受，它的值就被选定。不同编号的提案可以被选定，但其值必须相同。

协议的两阶段分别承担两种责任。第一阶段由提议者发出编号 n 的 prepare 请求；响应的 acceptor 承诺以后不接受编号小于 n 的提案，同时报告自己已接受的最高编号提案。提议者收集多数响应后，如果有人报告已接受提案，就必须采用其中编号最高者的值；只有所有响应者都没有已接受提案时，才可自由选值。第二阶段请求接受这个编号和值，acceptor 只能在不违反更高编号承诺时接受。

证明链可以从一个已经选定的提案 (m, v) 开始看。任何后来第一阶段的多数派，都与接受过该提案的多数派相交。交集节点不能既先承诺拒绝编号 m，又随后合法接受 m；它也不能在恢复后忘掉相关信息。按照提案号归纳，若交集节点后来已接受编号更高的提案，这些中间提案也必须携带 v。于是新提议者按最高已接受编号继承值时，不能把已经选定的 v 换成另一个值。论文的 P2、P2b 与 P2c 是对这条推导逐步强化、再落到可执行规则的表达。

这里最容易误解的是：后来者不必先证明旧提案“确实已经被多数接受”。某个值即便只出现在部分响应里，也可能已经被选定，只是决定消息丢失了。协议选择保守继承，避免在无法排除旧决定时另起一个冲突决定。

以三个 acceptor A、B、C 为例：编号 7 的 x 被 A、B 接受后，旧提议者崩溃。新提议者用编号 8 向 B、C prepare，B 报告 (7, x)，C 报告空；假设没有更高已接受提案，它必须继续提出 x。即使客户端没收到旧回复，也不改变选值约束。反过来，若 x 只曾被 A 接受，B、C 均为空，新一轮可以选 y；B、C 对编号 8 的承诺会阻止旧编号 7 再凑成多数。两个分支都说明：客户端感受不到成功，与协议历史能否被改写，是不同问题。

## 洞察三：Raft 的证明把继承责任前移到选举，并严格限制提交

Raft 通过限制谁能当选，确保后续领导者已经拥有已提交日志；再利用日志匹配保证这份历史继续保留。日志项包含 index、term 和命令。若两份日志在同一 index 的 term 相同，其到该位置的前缀也应相同；AppendEntries 的前驱 index/term 检查维持这个不变量，冲突时跟随者按合法领导者的日志修复冲突后缀。

选举的“日志够新”不是只比长度，而是先比较最后一条日志的 term，相同时再比 index。每任期至多投给一个候选者，多数票让同一任期至多选出一个领导者。投票者拒绝日志比自己旧的候选者，把选举与日志历史联系起来。

完整证明还需要提交规则：领导者只有在某位置 N 已被多数复制，且 `log[N].term == currentTerm` 时，才能仅凭这次副本计数直接推进 commitIndex 到 N。这个当前任期条目提交后，前面的旧条目随日志前缀一起间接提交。旧任期条目不会因为换了领导者就改写自己的 term。

论文用反证法证明领导者完整性：假设第一个缺失已提交条目的后续领导者出现在任期 U。它的选举多数派必与原提交多数派相交；交集投票者仍持有该条目。若候选者末条 term 与投票者相同，长度条件结合日志匹配迫使候选者包含该条目；若候选者末条 term 更大，生成该末条记录的中间领导者也应包含旧条目，再由日志匹配得到同样结论。两条路都与“缺失”矛盾。由此加上按 index 顺序执行，才推出不同状态机不会在同一位置执行不同命令。

### 旧任期条目出现在多数节点上，仍可能尚未提交

Raft 的 Figure 8 反例说明：某个旧条目的当前副本数，不能替代上述完整提交规则。下面重述它的关键轨迹，公共前缀从略；x、y 都在 index 2。

| 时刻 | 发生的事 | 可以得出的判断 |
|---|---|---|
| term 2 | S1 把 x 复制到 S1、S2，随后崩溃 | 五节点中仅两个副本，尚未提交 |
| term 3 | S5 获得 S3、S4、S5 的票，在自身追加 term 3 的 y，随后崩溃 | y 也未提交，但其日志末条 term 比 x 更高 |
| term 4 | S1 恢复当选，再把原来 term 2 的 x 复制到 S3 | x 现在在 S1、S2、S3 上；S1 仍不能仅凭此宣布提交 |
| 后续分支 A | S1 再崩溃，S5 恢复，以更高任期参选 | S5 的末条 term 3 比这些节点的 term 2 新，有机会获得多数并用 y 覆盖未提交的 x |
| 后续分支 B | S1 在 term 4 先把一个当前任期新条目复制到多数，再崩溃 | 该条目提交，x 随前缀间接提交；S5 仅带原来日志已无法获得所需多数票 |

这个例子没有展示已提交数据丢失，而是展示为什么不能把未提交数据误认成已提交。Paxos 与 Raft 都保留已经形成的决定，但在携带历史和识别提交的具体机制上采用了不同组织方式。

### 证明的呈现形式不能代替实现验证

论文中的证明针对明确的协议模型，不自动覆盖任意工程实现。Paxos Made Simple 主要用英文推导与提案号归纳阐明安全性；Raft 论文给出不变量和证明概要，并在 §9.2 说明形式规约、机械证明与非形式证明的边界。该节记载的机械证明还依赖未机械核查的不变量，不能概括成“Raft 已被机器完整证明，所以实现不会出错”。这里描述的是论文当时报告的验证范围，不是对今天所有形式化工作的盘点。

## 洞察四：工程实现要把协议约束落实到每次 I/O 和恢复中

共识库只有在宿主正确保存状态、传递消息并按顺序执行时，才可能兑现协议保证。etcd-io/raft 的 README 明确把网络和磁盘 I/O 留给使用者，提供的是可确定性驱动的核心状态机。它是理解实现责任的一个实例，不等于完整的 etcd 服务，也不等于所有 Raft 实现。

| 工程问题 | Paxos 需要落实的责任 | Raft 与所读库文档给出的落点 |
|---|---|---|
| 持久化与崩溃恢复 | acceptor 保留最高承诺及已接受提案，发送响应前保存所需信息；提议者避免重用编号 | 基础协议保存 currentTerm、votedFor、日志；库使用者处理 Ready 中的 Entries、HardState 和 Snapshot，并遵守发送消息前的持久化依赖 |
| 日志组织与恢复 | 每个位置一个实例，可能先决定后面位置；补齐空洞后按顺序执行 | 领导者修复跟随者冲突后缀；选举时日志必须足够新，不能靠当选后随意从落后日志重建历史 |
| 快照与压缩 | 状态机复制实现需要另外设计历史回收与恢复机制；单值协议本身不提供完整方案 | Raft §7 讨论快照与最后包含的 index/term 等元数据，快照必须与状态机和成员信息相配合 |
| 成员变更 | Paxos Made Simple §3 通过状态机决定后续实例由谁参与，并考虑流水线的边界 | Raft 论文 §6 给出 joint consensus；所读库 README 还说明单成员变更应用时机等实现约定，须按具体入口与版本核实 |
| 客户端重试 | 协议选定命令，不自动识别两次请求是同一业务动作 | Raft §8 另外讨论请求序号与响应缓存；库也说明提议未必提交，超时后可能需要重提 |

持久化顺序尤其不能简化成“收到一批更新后立刻把消息发出去”。所读库文档要求：发送前最新 HardState 已持久化，先前 Ready 批次的日志条目已经写入；同一批的条目落盘与发消息存在文档允许的并行空间。将所有 I/O 任意并发，或者反过来声称所有日志总要完全落盘才能发送任何消息，都失去了原文约束的精度。

成员变更也不能仅凭“两个多数派必相交”一语带过。固定成员集合内的多数派交集，并不自动适用于任意新旧配置。Raft 论文采用过渡配置，决策同时满足旧配置和新配置的多数条件；读库的实现说明时，要区分该论文机制、单成员变更路径及其应用时机。本文不据 README 推断 etcd 某个运行版本的全部配置变更行为。

## 洞察五：etcd 的读与超时语义揭示了算法之外的契约

对客户端最有用的保证必须按 API 和选项逐一判断。etcd v3.6 的 API guarantees 声明 KV 操作的持久性及严格可串行化保证，同时明确可选择 `serializable` 读来换取更低延迟，此类读取可能相对 quorum 返回旧数据；Watch 也不承诺线性一致性。

线性一致性要求每次操作可放在“调用到返回之间”的某一点，且遵守已完成操作的实时先后关系。如果一次写已经成功返回，之后才发起的线性一致读不能返回更旧的值；若写与读的执行区间重叠，定义允许按合法的线性化顺序决定读值，并不要求读取在返回时刻之前的每个并发写。官方页面的“最新”表述应按这个定义理解。

安全的只读请求不必每次都写一条 Raft 日志。Raft §8 说明了为什么新领导者需要知道提交边界，以及为什么回复读取前还要确认自己的领导权；所读库文档列出基于 quorum 的安全读取和依赖时钟条件的租约读取路径。由此不能推出“找当前自称领导者的节点本地读一下就一定线性一致”，也不能把“经过共识确认”误解成“每次读取都追加日志”。

写超时则代表客户端不知道结果。etcd 文档明确：超时或连接中断可能使客户端不确定操作是否完成；领导者切换可以重写未提交条目，但已提交写入不会因此丢失。共识保证副本在命令历史上达成一致，不会自动阻止客户端把同一业务动作作为两个新请求提交。请求去重、事务条件与业务幂等如何配合，需要单独定义。

多数节点不可用时，etcd 不能继续接受新写；网络分区时能维持多数派的一侧才有机会继续推进。这是故障下服务能力的边界，不能把“还看到一个旧领导者进程存活”视作它仍能成功提交写入。
