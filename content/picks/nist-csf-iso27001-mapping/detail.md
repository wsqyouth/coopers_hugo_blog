依据公开官方说明、CSF 正文和可访问的映射资料整理。映射中的相关关系按原始来源解释。

## 核心心智模型：用成果组织目标，用管理体系持续实现目标

CSF 2.0 帮助组织描述要达到的网络安全成果；ISO/IEC 27001:2022 规定管理信息安全风险的体系要求，并以 Annex A 提供控制参考。两者之间的映射可以帮助寻找相关要求和控制，实际是否达到目标仍需组织自己的实施与有效性证据。

可以把四层分开理解：**成果说清要达到什么，要求规定体系必须满足什么，控制说明采取哪些措施，证据说明措施实际如何运行。** CSF 与 ISO 都涉及治理与风险，区别在于表达结构和使用方式，不能简单分成“一个管战略、一个管技术”。

下面讨论怎样组合使用两套框架。推断：对需要同时读懂两套体系的人，先保留各自的结构，再连接共同证据，比先合并条目更容易发现遗漏。

## 一、CSF 的结构围绕成果展开，ISO 的结构围绕管理体系展开

CSF 的 Functions、Categories、Subcategories 是同一成果分类的三个层级，Profiles 与 Tiers 是配套使用的不同维度。

CSF 2.0 的现行 Core 有 **6 个功能、22 个类别、106 个子类别**。以下列出全部类别代码；功能定义用中文概括。

| 功能 | 核心问题 | 类别代码与中文导航 | 子类别数 |
|---|---|---|---:|
| GOVERN（GV）治理 | 策略、期望与政策如何建立、传达和监督？ | GV.OC 组织背景；GV.RM 风险管理策略；GV.RR 角色、职责与权限；GV.PO 政策；GV.OV 监督；GV.SC 网络安全供应链风险管理 | 31 |
| IDENTIFY（ID）识别 | 当前资产与风险是否被理解？ | ID.AM 资产管理；ID.RA 风险评估；ID.IM 改进 | 21 |
| PROTECT（PR）保护 | 如何使用防护措施管理风险？ | PR.AA 身份管理、认证与访问控制；PR.AT 意识与培训；PR.DS 数据安全；PR.PS 平台安全；PR.IR 技术基础设施韧性 | 22 |
| DETECT（DE）检测 | 如何发现并分析可能的攻击与失陷？ | DE.CM 持续监控；DE.AE 不利事件分析 | 11 |
| RESPOND（RS）响应 | 发现事件后如何采取行动？ | RS.MA 事件管理；RS.AN 事件分析；RS.CO 事件响应报告与沟通；RS.MI 事件缓解 | 13 |
| RECOVER（RC）恢复 | 如何恢复受影响的资产与运行？ | RC.RP 事件恢复计划执行；RC.CO 事件恢复沟通 | 8 |

六个功能需要协同考虑。治理、识别、保护、检测活动持续开展，响应与恢复能力应随时准备并在事件发生时执行；表格顺序不意味着做完上一项才能开始下一项。Core 的子类别描述成果，具体实现方式需要结合组织决定。

**Profile 把共同语言转成组织自己的当前状态与目标。** Current Profile 描述当前达到或正在尝试达到哪些成果、达到什么程度；Target Profile 选择并优先排序期望成果。比较二者可以形成行动计划。Profile 可以有不同范围，例如整个组织或特定系统。

**Tier 描述风险治理和管理实践的严谨程度。** 四层依次是 Partial、Risk Informed、Repeatable、Adaptive，可译为局部、风险知情、可重复、自适应。它补充风险管理方法；选择更高 Tier 应考虑风险、强制要求与成本收益，不能仅凭某个控制项已实施就宣布组织达到某一 Tier。

ISO/IEC 27001 的管理体系主线可以沿第 4–10 章阅读：

| 章节 | 中文结构导航 |
|---|---|
| 4 | 组织背景 |
| 5 | 领导作用 |
| 6 | 策划 |
| 7 | 支持 |
| 8 | 运行 |
| 9 | 绩效评价 |
| 10 | 改进 |

这些名称帮助读者定位，不替代各章规范内容。IEC 的公开摘要明确，声称符合 27001 时不得排除第 4–10 章的要求。Annex A 是另一层控制参考，不能用完成 Annex A 表格代替管理体系要求。

## 二、Annex A 要用来检查必要控制，不能取代风险判断

ISO/IEC 27001 的控制选择应从组织的风险和需要出发，再用 Annex A 检查是否遗漏必要控制。

27001 的 Annex A 与 27002:2022 控制体系相衔接；27002 提供更详细的控制指导。公开材料说明这套控制有 **93 项、四个主题**：

| 控制主题 | 数量 | 阅读时应关注的维度 |
|---|---:|---|
| 组织（A.5） | 37 | 组织如何安排安全管理 |
| 人员（A.6） | 8 | 与人员相关的安全措施 |
| 物理（A.7） | 14 | 物理环境与资源 |
| 技术（A.8） | 34 | 与信息通信技术相关的措施 |

SoA 是 Statement of Applicability，通常译为适用性声明。SC 27 期刊的专家教育文章解释，其内容包括组织的必要控制、纳入理由、是否实施，以及排除 Annex A 控制的理由。必要控制可以来自其他来源，也可以由组织设计；纳入理由应联系业务背景和风险。

因此，“93 项全部打勾”不是控制选择方法，“不是 Annex A 里的控制”也不是忽略它的理由。这里必须区分两件事：管理体系要求不能任意排除；具体控制是否必要，应有适用性判断和理由。27002 是实施指导，ISO 官网也明确它本身不是独立认证标准。

## 三、NIST 收录了两份不同的映射，版本与提交者必须随表保留

在本次读取日期，NIST OLIR 中两份相关记录均标为 Final、版本均为 1.0.0，但并非同一个映射。

| NIST 记录 | 提交与开发信息 | 发布日期 | 自报覆盖 | 用途 |
|---|---|---|---|---|
| referenceId=154 | developer=Razilio；authority=Non-Owner；Private Sector | 2025-07-18 | comprehensive=No | 同时出现 Mandatory Clause 与 Annex A Controls，作为本文八条示例的主表 |
| referenceId=218 | developer=Independent；联系人 Joerg Pauloweit；authority=Non-Owner | 2026-07-09 | comprehensive=Yes | 摘要说明是 ISO 控制到 CSF 的映射，用于展示提交者之间的差异 |

记录中的 referenceAuthor 指向 ISO/IEC，是被映射标准的作者字段。它不能证明映射本身由 ISO/IEC 编制。两份映射都以 CSF 2.0 为 focal document、ISO/IEC 27001:2022 为 reference document；标题的 “ISO-to-CSF” 描述关系方向，CSF 工具则可以从成果侧展示相关项。

NIST 对非 NIST 提交映射只进行有限的格式符合性测试，不核验其正确性，收录也不代表背书。Final 是目录状态，comprehensive 是该记录的覆盖声明；二者都不能用来证明覆盖了某家组织全部适用风险。

### 六个功能层级可作导航，不能代替逐项分析

功能层映射粒度较粗，适合先定位到哪里继续看。下表忠实概括 referenceId=154 的功能行，保留其局限。

| CSF 功能 | 原表列出的 ISO 管理条款 | 原表列出的 Annex A 控制 |
|---|---|---|
| GV | 6.1、8.1、8.2、8.3 | 5.1 |
| ID | 8.1、8.2、8.3、10.2 | None |
| PR | 8.3 | All applicable controls |
| DE | None | 8.16 |
| RS | None | 5.26 |
| RC | None | 5.29、8.13 |

这里的 None 仅表示该映射行没有列出对应项，不能读成“这个功能无需管理要求或控制”。例如 ID 功能行没有 Annex A 引用，其下 ID.AM-01 却指向 5.9。功能行与子类别行应各自阅读，不能把某一层的空白向其他层传播。

## 四、八条细粒度示例展示的是相关关系，不能直接判定等价

同一个 CSF 成果可能关联多个 ISO 条款或控制；反向索引只是改变查找入口，不会自动产生等价或实施证明。

下表的 ISO 项均来自 referenceId=154。控制列统一加上 A. 前缀区分 Annex A 与正文条款；原单元格使用裸编号。中文成果为概括，完整字段见 NIST 目录中的映射原表。

| CSF 子类别与成果概括 | ISO 正文条款 | Annex A 引用 | 读者应保留的问题 |
|---|---|---|---|
| GV.OC-01：理解组织使命并用于风险管理 | 4.1、6.1、8.1、8.2、8.3 | 空白 | 怎样证明组织使命确实影响了风险决策？ |
| GV.PO-01：建立、沟通并执行风险管理政策 | 5.2 | A.5.1 | 除了存在政策文件，还怎样说明政策得到执行？ |
| ID.AM-01：维护组织管理的硬件清单 | None | A.5.9 | 清单是否覆盖实际管理的硬件并持续更新？ |
| PR.AA-05：定义、管理、执行并复核授权，包含最小权限与职责分离 | None | A.5.1、A.5.3、A.5.14、A.5.15、A.5.16、A.5.17、A.5.18、A.8.2、A.8.3、A.8.5、A.8.18 | 多条引用中，分别由哪些实施活动与证据支持？ |
| DE.CM-01：监控网络和网络服务，发现潜在不利事件 | None | A.8.16 | 监控是否能发现有意义的异常，而不仅是收集数据？ |
| RS.MA-01：宣布事件后与相关第三方协调执行响应计划 | None | A.5.26、A.5.27、A.5.28 | 第三方协调和计划执行分别有什么记录？ |
| RC.RP-01：响应流程启动恢复后，执行恢复部分 | None | A.5.26 | 恢复触发、执行和交接的界面是否清楚？ |
| RC.RP-03：恢复前核验备份及其他恢复资产的完整性 | None | A.8.13 | 除了有备份，是否核验了将要用于恢复的资产？ |

右侧是本文提出的核查问题，不是 ISO 条文翻译或标准规定的唯一证据清单。None 与空白均保持原表含义，不作为对 ISO 全文的否定判断。

### 差异本身就是使用映射的边界

两位提交者对同一成果给出的关系并不总相同：

| 成果 | referenceId=154 | referenceId=218 |
|---|---|---|
| ID.AM-01 | A.5.9 | A.5.9 |
| DE.CM-01 | A.8.16 | A.8.15 |
| RC.RP-01 | A.5.26 | A.5.29 |
| RC.RP-03 | A.8.13 | 空白 |

本次验证了这些差异确实出现在各自单独下载的 NIST 表中；没有取得 ISO 付费全文来裁定哪份解释更完整。对空白的准确结论是“该版本在这个成果行没有映射”，不能推导为“两套标准在此处没有关联”。

反向使用时，可以把主表中 A.5.26 的引用重新索引到 RS.MA-01 与 RC.RP-01。它告诉读者可以从这些成果继续寻找关联，但不说明实施 A.5.26 就足以实现两个完整成果，也不说明这个示例列出了 A.5.26 的全部关系。

## 五、组合使用应共享实施事实，分别保留各自的判断

推断：共同维护实施事实，再分别评估 CSF 成果与 ISO 适用要求，能够减少重复整理证据，同时保留两套体系的区别。

以“备份恢复”为例，CSF 的 PR.DS-11 涉及备份的创建、保护、维护与测试，RC.RP-03 则关注使用恢复资产之前的完整性核验。两者不是同一个时间点的问题。映射把某个成果指向备份相关控制后，还需要检查实际流程覆盖了哪些时点，以及证据能支持什么程度的结论。

最小可行做法是选定一个范围，记录当前和目标成果，再查找相关 ISO 管理要求与控制。对于每个重要关系，记录适用原因、实施负责人和现有证据；缺口回到风险处置和行动优先级。这里不需要先制作一张覆盖所有标准的总表。

### 与我的关联：把熟悉的“需求—实现—验证”拆开看

这份材料与日常评审中的判断方式相连，以下是供读者检验的经验连接，不假定读者已经做过认证项目。

1. **看见一个对应项，先问对应的是什么层级。** “目标关联某项措施”与“措施实现了目标”需要不同证据；阅读映射时可以沿用需求、实现、验证分层的习惯。
2. **复用证据时，保留各自的验收问题。** 同一份资产清单可以服务多个判断，但这不表示它满足各个判断的全部条件。推断：共享事实、分开判断，可以减少把资料齐备误当成果已达成的机会。
3. **挑战“官方站点上的表就等于权威等价表”的直觉。** 本例中两份 Final 映射的检测和恢复条目不同，NIST 又明确限定其核验职责；域名可信与映射解释正确是两项判断。
4. **挑战“控制越多，治理必然越好”的直觉。** SoA 的价值在于解释哪些控制必要、为何必要、是否实施，以及为何排除其他控制；数量本身不能替代这些判断。
