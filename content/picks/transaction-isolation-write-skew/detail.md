## 核心心智模型：隔离要同时回答读、写与共同结果

稳定快照只说明读取使用哪个过去的版本，可串行化还要求所有成功事务能共同排成一个说得通的先后顺序。设两个值班人员 A、B 都在岗，规则是每班至少一人留岗。一个事务读到两人都在，可以批准 A 离岗；另一个也读到两人都在，可以批准 B 离岗。两人改的是不同的行，快照也完全稳定，但两笔都成功会让班次无人值守。这里缺失的是两个决策之间的协调。

串行执行是先完整执行一笔，再执行下一笔；可串行化允许动作交错，只约束成功结果等价于某种串行执行。它保住业务规则的前提是：初始状态满足规则，每笔事务单独执行能维护规则，相关事务都处于相应隔离与协调协议内。数据库不会替应用发现一条从未表达过、串行执行本身也会破坏的规则。

## 洞察 1：四级表是最低承诺，三个读异常不是完整定义

SQL 隔离级别中的“禁止什么”是下限，产品可以提供更强保护，Serializable 另有完整的串行效果要求。下面只用可观察的脏读、重复读取变化、集合变化说明标准层，不把论文后来提出的宽泛现象 P 直接填进同一张表。

| 标准层最低要求（经主材料转述） | 脏读 | 不可重复读 | 幻读 | 非串行化的提交结果 |
| --- | --- | --- | --- | --- |
| Read Uncommitted，RU | 允许 | 允许 | 允许 | 允许 |
| Read Committed，RC | 禁止 | 允许 | 允许 | 允许 |
| Repeatable Read，RR | 禁止 | 禁止 | 允许 | 允许 |
| Serializable | 禁止 | 禁止 | 禁止 | 禁止 |

“允许”不代表每次都会发生。用这张表可以询问产品至少排除了什么，却不能倒过来证明一个实现已经可串行化；尤其不能推理“没有看到前三种读异常，所以就是 Serializable”。

Berenson 等指出，SQL-92 对现象的自然语言描述可作严格或宽泛解释。严格异常 A 需要完整的坏事发生；宽泛现象 P 更早禁止一种危险交互。为读公式，记 `r1[x]` 为 T1 读 x，`w2[x]` 为 T2 写 x，`c1` 为 T1 提交，`a1` 为回滚，`end1` 为 T1 提交或回滚，省略号表示其他动作可夹在中间。

| 单版本分析中的宽泛现象 | 论文的严格异常 | 差别 |
| --- | --- | --- |
| P1：`w1[x] … r2[x] … end1` | A1：`w1[x] … r2[x] … a1、c2`（两者末尾顺序可互换） | P1 在 T1 未结束时就禁止别人读取其写值；A1 还要求写者回滚、读者提交。现代文档说脏读通常不要求写者最终回滚 |
| P2：`r1[x] … w2[x] … end1` | A2：`r1[x] … w2[x] … c2 … r1[x] … c1` | P2 不要求 T1 再读；A2 要求同一项重读并观察到变化 |
| P3：`r1[P] … w2[y∈P] … end1` | A3：`r1[P] … w2[y∈P] … c2 … r1[P] … c1` | P3 不要求重新查询；论文把影响谓词范围的插入、更新、删除都纳入，A3 则关注重查的集合变化 |

这解释了一个常见漏检：事务先读账户 x 的旧余额，另一个事务完成 x→y 转账后，前者再读 y 的新余额，得到不存在于任何完整提交状态的总额。它没有把任何一行读两次，所以“是否重读不一致”这一检查抓不住它。

论文还补出 P0 脏写：`w1[x] … w2[x] … end1`。它指出仅靠原来的三现象表，没有把低级别的脏写保护说完整，并建议所有级别都禁止 P0。论文的改进定义和当前标准转述应分开看，不能把这项批评写成今天所有数据库都会允许脏写。

## 洞察 2：SI 与锁式 RR 不可比，写偏斜暴露快照的缺口

SI 同时提供事务级快照和并发同项写保护，但仍允许事务读彼此要改的行、再写不同的行。论文模型把开始时间戳固定在首次读取之前，事务读取那个时点的已提交版本，并看见自己的修改；提交时若另一个在本事务执行区间内提交的事务写过相同数据项，本事务不能成功提交，这就是 first-committer-wins。具体产品可以更早在写入阶段等待或报错，不能从该模型推出“错误只会发生在 COMMIT”。

贯穿例子的动作如下。这里是假定普通表、普通读取、没有额外锁或跨行规则保护的语义推演；不是实测日志。A、B 用 1 表示在岗，业务不变量为 `A+B≥1`，两笔事务都遵守“读到至少两人在岗才让自己离岗”。

| 顺序 | T1：申请 A 离岗 | T2：申请 B 离岗 | 已提交状态 |
| --- | --- | --- | --- |
| 0 | 尚未开始 | 尚未开始 | A=1，B=1 |
| 1 | 建立快照，读 A=1、B=1，计数 2 | | A=1，B=1 |
| 2 | | 在 T1 提交前建立快照，读 A=1、B=1，计数 2 | A=1，B=1 |
| 3 | 只写 A=0 | | A=1，B=1；A 的新值未提交 |
| 4 | | 只写 B=0 | A=1，B=1；两项新值均未提交 |
| 5 | 提交成功 | | A=0，B=1 |
| 6 | | SI 下写集不相交，可提交 | A=0，B=0，规则破坏 |

每个事务都读到了真实、完整且没有变化的过去。问题在于：T1 的决定依赖 B 仍在岗，T2 的决定依赖 A 仍在岗。若把 T1 排在 T2 之前，T2 应读到计数 1、拒绝离岗；反过来也一样，因此上述两次批准没有串行解释。没有丢失谁的写入，两项写入都保存了，这就是 write skew（写偏斜），区别于覆盖同一行的 lost update。

可以把它画成两条读写反依赖：`T1 →rw T2` 表示 T1 读了 B 的旧版本、T2 随后改 B；`T2 →rw T1` 来自 A。箭头表达若要保留读值所需的先后关系；两条要求形成环。单项写冲突检查只查 A 对 A、B 对 B，捕捉不到这种交叉关系。

下面的比较仅沿用论文对“允许哪些非串行化历史”的分类，箭头从强指向弱；它不是吞吐量图，也不是说不同实现允许的全部执行序列逐项包含。

锁式 RR 长期保持已经读过的数据项读锁，能阻止上述对既有两行的写偏斜，却不持续保护整个谓词范围，新插入匹配行仍可能带来幻读。SI 可以重复查询得到相同旧集合、避免可观察幻读 A3，却容许上面的写偏斜。一个允许另一个禁止的异常，另一个也有相反的反例，所以不能画成 `RC < RR < SI < Serializable` 的单链。

“没有幻读”在此特指 A3 式的重查集合变化；宽泛 P3 还包括读取条件之后的潜在范围写冲突。比如两笔事务各看见某天任务共 7 小时，各插入不同的 1 小时任务，会同时通过“总时长≤8”的检查。SI 让各自重查时仍看不见对方的新行，规则却已被两次提交破坏。多版本推演必须标清读的是哪个版本，不能只按墙钟动作先后套用单版本 P2/P3。

## 洞察 3：异常名称要落到读值和提交顺序

同一个“并发写错”可以来自未提交覆盖、旧值覆盖或跨行决策冲突，修复方式取决于实际序列。下表列出最小教学构造，每行独立、从左到右执行；`r1[x=0]` 明确读到 0，提交或回滚也写出来。

| 异常与初值 | 动作时间线 | 读值、最终结果和规则 |
| --- | --- | --- |
| 脏写 P0；x=y=0；每笔都想把 x、y 写成相同值 | `w1[x=1] → w2[x=2] → w2[y=2] → c2 → w1[y=1] → c1` | T2 覆盖 T1 未提交的 x；最后 x=2、y=1，破坏 x=y。两笔均提交也会错，不必等回滚；若回滚还会产生恢复困难 |
| 脏读；x=0，派生记录 z=0 | `w1[x=10] → r2[x=10] → w2[z=10] → c2 → a1` | T2 用未提交值形成持久输出；最终 x=0、z=10。T2 依据了最终被撤销的数据，满足严格 A1 |
| 不可重复读 A2；x=0 | `r1[x=0] → w2[x=1] → c2 → r1[x=1] → c1` | T1 对同一行的两次读不同，最终 x=1；未必破坏特定业务规则，但不满足重复读取稳定性 |
| 幻读 A3；在岗集合最初仅 {A} | `r1[P]={A} → insert2[B 在岗] → c2 → r1[P]={A,B} → c1` | 同一谓词 P 重查得到不同集合。原来读取的 A 完全可以未变，故单行读保护不足以处理此情形 |
| 丢失更新 P4；x=100；T1 加 30、T2 加 20 | `r1[x=100] → r2[x=100] → w2[x=120] → c2 → w1[x=130] → c1` | T1 用旧读值计算常量覆盖，最终 130；两次增量若都保存应为 150，T2 的增量丢失。第二次写发生在 T2 提交后，所以并非脏写 |
| 读偏斜 A5A；x=y=50，总额 100 | `r1[x=50] → r2[x=50] → w2[x=10] → r2[y=50] → w2[y=90] → c2 → r1[y=90] → c1` | T2 正常转账；最终 10+90=100，T1 却读出 50+90=140。它读的每个值都已提交，但不是同一个数据库时点 |
| 写偏斜 A5B；A=B=1，至少一人在岗 | `r1[A=1,B=1] → r2[A=1,B=1] → w1[A=0] → w2[B=0] → c1 → c2` | 读值稳定且写不同项，最终 0 人；完整推演见上一节 |

把这些异常套到隔离模型时，应保持定义一致。下一张表使用可观察 A2/A3，以及上一表的具体 P4、A5A、A5B 构造；“可”表示模型允许，不是必然发生。锁式 RR 指论文中持有数据项读锁到事务结束、谓词读锁不持续保持的模型。

| 模型或实现 | 脏写 P0 | 脏读 | A2 重读变化 | A3 幻读 | 旧值覆盖 P4 | 两次读取的 A5A | 既有两行的 A5B |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 论文改进 RC | 禁 | 禁 | 可 | 可 | 可 | 可 | 可 |
| 论文锁式 RR | 禁 | 禁 | 禁 | 可 | 禁 | 禁 | 禁 |
| 论文 SI | 禁 | 禁 | 禁 | 禁 | 禁 | 禁 | 可 |
| PostgreSQL 18 RC（普通读取后写常量） | 禁 | 禁 | 可 | 可 | 可 | 可 | 可 |
| PostgreSQL 18 RR | 禁 | 禁 | 禁 | 禁 | 禁 | 禁 | 可 |
| 全部相关事务采用 Serializable | 禁 | 禁 | 禁 | 禁 | 禁 | 禁 | 禁 |

这张表不将论文单版本的宽泛 P2/P3 等同于 A2/A3，也不涵盖所有“读偏斜”的广义用法；这里 A5A 专指表中跨两次读取拼接版本的构造。只读 SI 事务仍可能参与其他更复杂的非串行化历史，不能据此推出“只读事务的结果总有串行解释”。

## 洞察 4：PostgreSQL RR 是 SI，Serializable 在它之上追踪危险依赖

PostgreSQL 18 明确把 Repeatable Read 对应到 SI，并使用 SSI 为 Serializable 补上串行化检查。名称相同不代表和上一节的锁式 RR 行为相同，产品语义应以固定版本文档为准。

| PostgreSQL 18 模式 | 快照与读取 | 并发写及失败语义 |
| --- | --- | --- |
| RU | 实际行为与 RC 相同 | 没有独立的允许脏读实现 |
| RC（默认） | 普通 SELECT 使用该语句开始时的已提交快照；下一语句可换到更新的快照 | 对待更新的已找到目标行，可能等待并发写者；对方提交后可对新行版本重查 WHERE 并应用操作 |
| RR | 快照以事务内第一条非事务控制语句开始时为准；后续普通读取沿用 | 若要更新或锁住的行在该快照后被其他事务实际修改并提交，不能继续基于旧版本修改，需中止重试 |
| Serializable | 保留 RR 的快照行为，并监测读写依赖是否可能导致无串行解释的结果 | 检测危险组合时以 serialization failure 拒绝某笔事务；成功提交的一组相关 Serializable 事务有串行解释 |

`BEGIN` 本身不应机械地视为 RR 快照建立时间；本表按文档第一条非事务控制语句的规则理解。各模式都可以读到自己的先前修改，不能把快照解释为对自己的写入也冻结不变。

RC 的快照规则还不能简化成“任何一条语句始终只看到同一个历史数据库”。普通 SELECT 按语句快照读，而更新命令在冲突目标行上可能接续新版本，其他行仍按原来视图处理，因此复杂查询更新可以产生混合观察。这里最值得区分的两种 SQL 是：

```sql
-- 形式一：应用先 SELECT x=100，再根据旧值传回一个常量
UPDATE counters SET x = 130 WHERE id = 1;

-- 形式二：数据库在目标行的当前可更新版本上计算增量
UPDATE counters SET x = x + 30 WHERE id = 1;
```

推断：按 RC 的目标行等待与重查规则，形式一可发生前述 P4；两笔分别执行 `x=x+20` 和 `x=x+30` 时，后一笔在冲突后用新版本计算，两项增量能保留到 150。这个结论限于预定同一行上的原子增量、没有额外错误；它没有证明含子查询、多行条件、触发器或跨行规则的 UPDATE 都安全。RR 则会拒绝本例中基于旧快照更新已被并发事务改过的同一行，不能把它解释为自动替应用合并两次更新。

SSI 的关键不是给每次读取都加一把阻塞写者的锁，而是记录“哪些写入若先发生会改变先前读取结果”。PostgreSQL 用谓词读锁信息追踪这种依赖，`pg_locks` 可显示为 `SIReadLock`；这些读锁本身不阻塞，因此本身不产生死锁。普通写锁仍可能等待；`SERIALIZABLE READ ONLY DEFERRABLE` 还可能在开始读取前等待安全快照。不能把“谓词读锁不阻塞”扩大成“Serializable 完全不等待”。

发现风险也不等于数据库已经观测到一个完成的环：SSI 可以基于足以造成问题的危险依赖组合中止事务。与写锁式串行化相比，它把部分等待成本换成监测和重试成本；具体工作负载哪个更快，需要测量，不能由级别名字判断。

应用收到序列化失败（SQLSTATE `40001`）后，要从头重试整个事务，包括所有读取和业务判断；只重发最后一条 UPDATE 会复用已经过时的决策。事务尚未成功提交前，不把查询结果当作最终可依赖的业务结果；普通只读 Serializable 事务也可能需要重试，安全快照的 DEFERRABLE 只读事务另有保证。序列生成器是相关边界：sequence 的变化可立即被其他事务看到，回滚也不撤销，不能用它的行为检验普通表的快照规则。

## 洞察 5：工程方案要覆盖决策依赖，而非只锁自己要改的行

维护“每班至少一人在岗”时，必须让两个离岗决策发生协调；只把各自那一行锁住仍没有覆盖规则。推断：对于这一类跨行读取后作决策的流程，若所有参与事务都能采用 Serializable，并实现整笔事务重试，它是清晰的起点；若业务更适合显式串行化，可以把同班次的决策集中到共同锁点。以下是模型推导，尚未在数据库执行。

| 方案 | 在本例如何成立 | 成本与成立条件 |
| --- | --- | --- |
| Serializable + 整笔重试 | 两人都获批准的提交结果无串行解释，数据库不能让这组结果共同成功 | 所有相关读写路径纳入协议；每笔事务串行执行时确实遵守规则；接受监测与重试成本 |
| RC + 每班固定 guard 行的 FOR UPDATE | 所有减员操作先锁同一班次 guard 行，得到锁后，用下一条独立语句重新读人数，再决定是否更新 | guard 必须已存在且所有减员、删岗等路径遵守；锁持有至提交。热点班次排队；多个锁点统一顺序避免死锁 |
| 数据模型把规则落在单行 | 对限定为固定 A/B 两人的模型，可把两人状态放同一班次行，以 NOT NULL 与 CHECK(A OR B) 约束 | 限于该模型；若另有明细表需证明其与该行一致。通用动态名单不能凭这一示意直接解决 |
| 只锁各自人员行，或只提高到 RR | 两笔写不同行，照样可共同批准 | 对本例不足；快照与写集保护未覆盖交叉决策依赖 |

guard 方案中的“先锁、后用另一条语句读”是重要条件：RC 等锁结束后的下一条读取可得到已提交新状态。如果把检查与等锁塞进同一条语句，其读取快照可能在等待前就已确定；换成 RR 后，拿到一个没有被实际更新的 guard 锁也不会自动刷新事务快照，不能照抄这个推导。FOR UPDATE 锁住现有行，不等于锁住所有未来可能匹配查询的行。

原生约束在能表达业务规则时更直接，但 CHECK 不能通用地验证其他行或其他表的数据。用函数在 CHECK 里偷查其他行，也得不到持续正确性保证。UNIQUE、EXCLUDE、FOREIGN KEY 各有明确用途；它们不能凭名称自动表达“动态集合至少一行在岗”。选择方案前先写出不变量，再列所有可能改变它的入口，才能知道同步范围够不够。
