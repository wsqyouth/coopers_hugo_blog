## 核心心智模型：价值来自补缺，靠对照证明

**这些资产有公开实证支持，但没有“写了就更好”的通用保证。** 常驻指令会改变 agent 的行为；Skills 在一些任务上提升很大，在另一些任务上几乎没有增益，甚至干扰正确执行。判断自己的资产是否有用，需要固定模型、运行框架和任务，比较有无资产时的正确性、完成率与成本；“文件被读取、流程被遵守”只是中间指标。

常驻指令测试的是持续加入项目约束的效果；按需 Skill 还多出一个发现与选择环节。若 Skill 同时提供脚本、模板和数据，测到的是整包效果，不能把提升全部归因于 Markdown 的写法。

## 洞察一：指令文件能节省时间，也可能只增加工作

**两项直接对照研究给出不同的效率信号，且都不足以证明任意指令文件都会提高正确率。**

| 研究 | 对照与样本 | 可带走的结果 | 方法可信度与限制 |
|---|---|---|---|
| On the Impact of AGENTS.md，v2 | 10 仓库、124 个 PR 任务；同快照有/无根 AGENTS.md；Codex + gpt-5.2-codex | 运行时间中位数下降 28.64%，输出 token 中位数下降 16.58% | 配对设计；时间和输出 token 的 Wilcoxon 检验显著。只抽查 50 个任务的产出是否非平凡，未全面评估语义或功能正确性；不是“质量不变”的证明。总 token 中位数也没有下降 |
| Evaluating AGENTS.md，v3 | SWE-bench Lite 300 题，加 CTXbench 12 仓库 138 题；四组模型/agent；无文件、LLM 生成文件、开发者提交文件 | LLM 文件的平均成功率变化未显著，成本在两套题上平均增加 20% / 23%；开发者文件成功率平均增加约 2.4 个百分点，相对无文件不显著，且成本增加 | 执行测试判成功，报告显著性；每组任务只采样一次。Python 仓库与 benchmark 测试不能代表所有业务约束 |

前者回答的是特定样本中是否更快、少生成输出；后者同时评估测试通过和推理成本。不能把二者平均成“指令文件总体有效”或“总体无效”。开发者提交的文件也不等于已确认完全由人手写。

## 洞察二：Skills 的增益取决于它补了什么缺口

**最强的正向证据与近零增益的证据可以同时成立，因为它们抽样和测量的对象不同。**

| 研究 | 方法 | 结果 | 解读边界 |
|---|---|---|---|
| SkillsBench，v4 | 87 题、8 领域、18 种模型与框架组合；有/无精选 Skills，同环境每格三次；可执行判定 | 任务宏平均通过率 33.9% → 50.5%，增加 16.6 个百分点 | 评估精选整包与专业任务；过滤流程剔除条件间没有可测分离的低信号任务，不能当成任意安装技能的预期收益。作者也承认缺少等长度等信息控制 |
| SWE-Skills-Bench，v2 | 98 个公开 SWE skills，各 10 条需求，四种配置，共 3,920 个有/无配对；显式调用 Skill | 平均检查通过比例 76.6% → 76.9%；92/98 无统计显著效果，4 项有益、2 项有害 | 这里是需求检查的通过比例，不是全部任务完成率；每需求每配置各跑一次，需求由 Skill 主张反向合成。无显著效果不等于真实效果为零 |
| Cost-Inefficient Behaviors，v3 | 先分析 1,200 条轨迹，再在留出的 Verified-200 与 Pro-100、四种配置上对照成本干预 | 开发者设计规则在 8 个设置中的 6 个稳健降成本，幅度 7.88%–41.73% | 规则预载进 system prompt，不能证明自然触发 Skills 的效果；不是所有格子都改善，部分成功率下降；最大降幅不是均值 |

SWE-Skills-Bench 的有益例子包括补上本来会遗漏的工具链安装；有害例子则是模板指定的位置压过任务明确要求的文件位置。因而有用的可能是被编码的流程缺口，而不是“有一个 SKILL.md”这个形式。

以上主要是受控 benchmark 配对实验；没有把它们包装成对真实开发者开展的大规模随机盲测。盲评分工具的存在，也不等于这些论文的评分都采用人工双盲。

## 洞察三：有害的是具体干扰，长度本身还没有通用阈值

**证据能支持一些明确的失败机制，但不能推出“超过某行数必然有害”。**

| 写法或机制 | 当前证据 | 应如何使用这个结论 |
|---|---|---|
| 模板细节覆盖当前任务约束 | SWE-Skills-Bench 有轨迹案例：应写入 ci/ 的文件被放到模板路径下 | 模板要说明适用条件；任务明确路径与接口应可覆盖示例默认值 |
| 要求额外探索、重复测试或重复阅读 | Evaluating AGENTS.md 观察到步骤和成本增加；其实验未发现成功率显著提升 | 只有与任务验收有关的步骤才适合作为默认要求；步骤更多不能单独算收益 |
| 将一套完整重流程用于轻量任务 | SkillsBench 的负向案例包含昂贵或脆弱流程；其长度/数量分组中，精简内容的增益更大 | 这是特定任务与内容的证据，不是仅改变字数的纯因果实验 |
| “过长一定导致失败” | Evaluating AGENTS.md v3 附录未发现文件长度对其结果的显著影响；SkillsBench 的内容分组存在任务等混杂 | 不设未经验证的通用 token/行数阈值 |
| 重复基础知识、模糊且过宽的触发描述、要求每次先读全套文档 | 三家官方资料建议避免；OpenAI 9 月文章尤其提醒 Astra 上旧约束可能过度 | 属于官方实践建议，不是公开的通用对照效果量 |
| “与模型先验冲突必然有害” | 已有模板与任务冲突案例，但本轮未找到独立操纵“模型先验冲突”的直接实验 | 不把一个可观察的任务冲突，扩大解释为模型内部先验的因果结论 |

Anthropic 与 Cursor 的“500 行以内”是作者实践建议；OpenAI 的 AGENTS.md 字节上限是加载机制。两者都不是随机实验发现的最佳长度。

## 洞察四：官方推荐评估真实运行，而不是给文件打文案分

**官方方法里最值得复用的是基线、触发测试、执行轨迹和回归；各家公开材料的深度不同。**

| 官方一手材料 | 明确建议或能力 | 不能据此声称什么 |
|---|---|---|
| OpenAI：Testing Agent Skills Systematically with Evals | 先定义结果、过程、风格、效率目标；加入显式、隐式、上下文触发与负例；用 codex exec --json 检查真实动作和产物，再补 rubric 评分 | 文中示例不能证明任意 Skill 提高多少成功率 |
| OpenAI：AGENTS.md 说明 | 验证实际生效文件、作用目录、覆盖关系和日志，排查截断 | 加载成功不能证明指令内容有用 |
| OpenAI：Rethinking skills and prompts for GPT-6 Astra（9 月） | 缩短且收窄描述，按需路由参考文档；重新评估旧的强制阅读、测试和停止规则 | 针对具体模型的经验建议没有公开对照样本及效果量 |
| Anthropic：authoring best practices | 先运行无 Skill 任务找失败，建三个评估场景，再写最小指令；在计划使用的模型上测试 | 三个场景是开发起点，不是充分统计样本 |
| Anthropic：skill-creator 3 月更新 | benchmark 记录通过率、时间、token；干净上下文；对有/无 Skill 或两版本进行隐藏组别的比较；优化误触发与漏触发 | “6 个公开技能中 5 个触发改善”是官方小范围自测，文章没有足够细节供判断普遍效果 |
| Anthropic：enterprise 指南 | 以应触发、不应触发、模糊场景覆盖 3–5 个代表查询，并测试单技能与共存回归 | 正例触发率高不能替代负例、共存和质量验证 |
| Cursor：Rules | 聚焦、可执行、限定作用域；引用规范示例，避免复制整套风格指南和命令大全；从重复错误出发补规则 | 本轮查阅的 Rules 页面没有给出 rule 有/无 A/B 测试或统一触发率量化方案，不能替它补出“官方标准” |

这也解释了看似矛盾的旧资料：较早的手册可能只描述手工测试，而后来的 skill-creator 已加入 eval 与 benchmark。工具功能应按具体页面、日期与版本理解。

## 洞察五：用配对试验决定哪些规则值得维护

**建议先验证一项明确的资产，而不是同时替换所有文件后凭感觉比较。** 以下是本报告提出的本地方案，尚未执行，也不是任何厂商规定的统一验收线。

第一步，写一条可被推翻的假设。例如：“这份 Skill 能减少遗漏必要验证的交付，同时不损失功能正确率。”对偏好型资产，可以把团队约定、必要审批与输出格式列为结果要求；这类价值不能只用代码测试通过率衡量。

第二步，固定真实使用的模型版本、运行框架、工具权限、仓库提交、任务输入、预算和环境。每组从干净状态开始，控制缓存与网络条件；给资产记 sha256。先比较有/无这一项资产，其他条件保持相同。如果要区分 AGENTS 与 Skills 的独立和组合效果，再扩成下表，别用“全关 vs 全开”替代归因。

| 条件 | AGENTS | 目标 Skill | 用途 |
|---|---|---|---|
| A | 无 | 无 | 原始基线 |
| B | 有 | 无 | 常驻指令增量 |
| C | 无 | 有 | Skill 增量 |
| D | 有 | 有 | 组合效果与干扰 |

第三步，把“内容有用”与“能被选中”分开测。显式调用验证使用后的收益；自然发现验证描述、可见性及竞争技能的影响。正例、近似负例和模糊请求都要有；正例数量多时，总准确率容易掩盖误触发。触发 precision = 正确触发数 / 全部触发数；recall = 正确触发数 / 应触发数。没有对应分母时不报这个比例。

第四步，先冻结验收，再运行。使用隐藏功能检查与人工审阅评估正确性，记录完整任务是否完成，并另外记录约束遵守。主观质量比较随机排列产物，评分者看不到组别标签；记录执行轨迹验证实际载入、脚本使用和异常。不要只让编写 Skill 的同一上下文自评好坏。

第五步，把成功与代价一起看。记录输入、缓存、输出 token，实际计价、墙钟时间，以及失败、超时与重试。相同任务下逐对算差值，报告改善/退化任务数和分布；成本不能只看成功样本。可补“总成本 / 成功数”，成功数为零时单独说明。

投入可以从 10–20 条真实任务、每条件重复 2–3 次的单项 A/B 开始，即 40–120 次运行。这个数量只是预算建议，不能保证统计功效；先用少量冒烟案例验证评估器可用，再花正式预算。顺序随机或交错，保留未参与调优的任务；样本不足时只报告观察结果与不确定性，避免用一次成功下定论。

最后，每次改资产、升级模型或运行框架时重跑保留集与相邻负例。若收益消失，就考虑删掉、缩小范围或保留为偏好约束；若是脚本带来提升，应继续保留脚本并单测去掉说明文档的效果。执行这些消融时必须继续保留当前任务真正需要的工具能力，避免把缺工具当成无 Skill 的公平基线。
