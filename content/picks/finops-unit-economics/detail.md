## 核心心智模型：让每笔支出经过归属、价值与行动三个问题

FinOps 的核心是把技术支出接到业务结果和行动责任上。只有账单，你知道花了多少；有分摊，你知道由谁解释；有单位经济学，你才能判断花得是否值得；有持续执行和复测，优化才成为经营能力。对工程负责人，最直接的用法是把「要不要扩容、改架构或精细计量」转成有共同口径的取舍。

把框架用到一次实际决策时，成本归属让账单可解释，业务分母让成本可比较，执行结果重新回到基线。三者需要一起工作。

## 洞察一：Inform、Optimize、Operate 是循环，成熟度是另一条轴

三个阶段会持续交替，同一个团队的不同成员也可以处在不同阶段。一个产品已经在执行优化，另一个产品仍在补齐成本归属，这符合框架描述；无需等全公司完成某一阶段再统一进入下一阶段。

| 阶段 | 要回答的问题 | 参与与决策 | 建议留下的工作产物 |
|---|---|---|---|
| Inform：信息透明 | 钱花在哪里，归谁，有什么业务结果？ | 工程提供用量与结果计量，财务核成本口径，业务解释价值 | 分摊后的成本视图、单位指标定义、基线与缺口 |
| Optimize：选择优化 | 哪个改变最有价值？ | 工程评估用量和架构，采购及管理者参与费率和承诺取舍 | 按价值、工作量和风险排序的机会清单 |
| Operate：持续执行 | 谁执行，效果是否兑现？ | 责任团队执行，跨角色复查成本和业务结果 | 行动负责人、验证结果、更新后的规则与基线 |

表中产物是实施建议，官方规定的是各阶段的活动与协作方向。Optimize 同时包含减少不必要资源消耗的用量优化，以及为必要资源争取适当价格的费率优化。便宜的资源如果不需要，仍然可能浪费。

Crawl／Walk／Run 评价的是某项能力的发展程度。Allocation 可以已有稳定自动化，Unit Economics 仍主要使用技术指标；这比给整个组织贴一个成熟度标签更准确。官方还明确提醒：不应把所有能力都做到 Run 当成目标。继续精细化是否值得，应回到它能否改善业务或技术结果。

实践建议：先选一个产品和一个结算周期，走完一次「看清—选择—执行—复测」，再决定哪里值得加自动化。

## 洞察二：单位经济学从定义业务单位开始，公式只是最后一步

一个可信的单位成本，必须让成本和业务结果属于同一范围、时间与质量定义。FinOps Foundation 同时讨论资源效率指标和业务单位指标；前者方便工程控制，后者让产品与财务判断交付价值。

| 指标层 | 示例 | 主要用途 | 容易误判的地方 |
|---|---|---|---|
| 资源效率 | 每 GB、每千次请求、每 token 成本 | 定位技术效率与资源消耗驱动 | 重试和无效调用也可能放大分母 |
| 业务单位 | 每笔成功交易、每个租户、每个已解决工单成本 | 讨论服务成本、产品取舍与价值 | 不同租户或业务类型的服务强度可能不同 |
| 业务价值 | 单位结果对应收入或可说明的价值代理 | 将支出与经营目标连接 | 缺少收入或全成本时，不能直接推出利润 |

建议先写一张指标合同，再建图表：

| 字段 | 本文虚构 SaaS 案例的定义 |
|---|---|
| 用途与所有者 | 工程解释成本驱动，产品定义交易成功，财务批准成本边界 |
| Scope | A、B 两个产品及其列明的共享服务；不把公司全部开支混入 |
| 时间与币种 | 同一自然月、统一时区、美元；财务关账后冻结版本 |
| 成本分子 | 同一确认及摊销口径下的月度云成本；折扣、承诺费用、退款等按该口径处理 |
| 业务分母 | 当月完成并去重的成功交易；失败请求和重试不算新增交易 |
| 数据来源 | 成本明细、资源归属映射、业务成功事件；三者能对上范围和月份 |
| 质量与缺失 | 同时看成功率和服务质量；缺数据保留未知，不当作零；分母为零时不报告有限单位成本 |
| 变更规则 | 定义、分摊规则和业务结构变化都记录版本；必要时重算历史或另起基线 |

平均单位成本的基本形式是 `C / U`。这里 C 是该范围的成本，U 是相同范围的有效业务单位。若只纳入直接云费用，就写「直接云成本/成功交易」；若加入共享服务和其他费用，就说明新的边界。只有云账单时，得出的不是公司全成本利润率。

平均成本也不能代替边际成本。30,000 美元对应 100 万笔交易，只能说明平均每笔 0.03 美元，不能据此承诺新增 10 万笔一定只花 3,000 美元。新增需求可能利用现有容量，也可能触发扩容阶梯；估计增量成本时，要控制业务组合、价格和容量变化，考察相应的 `ΔC / ΔU`。

## 洞察三：分摊规则先决定责任边界，再决定需要多细的计量

成本分摊需要归属策略、元数据策略和共享成本策略共同成立。只要求资源打标签，无法解决「归哪个产品、共享数据库按什么拆、无归属费用谁调查」这些问题。

先决定财务和工程分别需要什么视图：财务可能按成本中心，工程可能按产品和服务，运维还需要环境维度。然后用账户结构、标签、命名和派生元数据连接它们。专属账户可直接归属；共享资源则可能还需要应用计量、可观测数据或管理映射。共享数据库上的一个产品标签，不会自动给出所有租户的真实用量。

建议采用「能直接归属先直接归属，已识别共享池单独处理，未知费用显式保留」的顺序。先分配后汇总，避免同一费用既作为产品直接成本，又作为共享池再次加入。标签缺失可以用明确规则补足，但规则的来源、有效期和负责人需要可追查。

| 共享成本方法 | 适用起点 | 主要代价或偏差 |
|---|---|---|
| 平均分摊 | 受益大致相近，金额较小，追踪收益不高 | 使用很少的产品也承担同额费用 |
| 固定比例 | 各方接受预算或受益约定，需要稳定可解释的规则 | 用量结构变化后可能失真，应定期复查 |
| 按支出比例 | 能获得各方成本，可把它用作共享服务的代理驱动 | 成本与受益不一定同向；折扣变化也会影响份额 |
| 用量驱动 | 共享成本显著，存在可信的资源或业务计量 | 计量及维护有成本，代理指标仍不等于完整因果 |
| 集中承担 | 公共平台有明确中央预算，拆分收益有限 | 产品视图需显式展示未计入的中央费用，避免误读全成本 |

这些方法可以同时使用，不需要把所有共享费用塞进同一种模型。集中承担是已识别、已决定由中央预算负责；未知归属是尚未查清，两者不能混成一个「其他」。FinOps Foundation 明确允许对部分共享费用作出集中预算的知情选择。

Showback 把费用展示给责任团队，帮助解释和优化；chargeback 进一步按约定规则由财务进行内部费用归集或结算。建议先把 showback 的定义与对账做稳定，再判断是否需要 chargeback；算出一个精细比例本身，不代表它已经成为被接受的内部结算规则。

### 同一张虚构账单可以同时校验分摊与单位成本

以下金额全部是教学假设，使用同一月份和美元口径，不代表真实 AWS 价格或客户数据。表内原始成本项互斥；共享计算池按已接受的 CPU 时间代理拆分，A 占 75%，B 占 25%。

| 原始成本项 | 金额 | 本例处理 |
|---|---:|---|
| A 专属资源 | 12,000 | 直接归 A |
| B 专属资源 | 8,000 | 直接归 B |
| 共享计算池 | 6,000 | A 4,500；B 1,500 |
| 中央公共服务 | 2,000 | 已同意由中央承担 |
| 未知归属费用 | 2,000 | 暂列待调查，不强行摊平 |
| 合计 | 30,000 | 全部费用保留在核对范围内 |

分配后，A 为 `12,000 + 4,500 = 16,500`；B 为 `8,000 + 1,500 = 9,500`。核对关系是 `16,500 + 9,500 + 2,000 + 2,000 = 30,000`。中央承担和待调查费用各有位置，不能从总账中消失；分摊操作也没有创造节省。

若 A 有 60 万笔成功交易，B 有 40 万笔，则在本例已分配产品成本边界内：

| 视图 | 计算 | 结果 |
|---|---|---:|
| A 产品 | 16,500 / 600,000 | 0.0275 美元/成功交易 |
| B 产品 | 9,500 / 400,000 | 0.02375 美元/成功交易 |
| 整个范围 | 30,000 / 1,000,000 | 0.03 美元/成功交易 |

产品视图的加权平均是 0.026 美元，还未包含中央与未知费用对应的每笔 0.004 美元。把 0.026 当成整个范围的全成本，会低估 4,000 美元。若以后决定把中央费用也分给产品，需要公布新规则，避免将规则变化误认为效率变化。

本例另有两个有用的管理视图：费用核对覆盖了全部 30,000 美元；未知费用占比为 `2,000 / 30,000 ≈ 6.67%`。两者回答不同问题，不能因为总账对得上，就宣称所有成本已经准确归属。

## 洞察四：总成本与单位成本必须一起解释，质量决定分母有没有价值

总成本上涨可能伴随效率改善，但单位成本下降也可能掩盖业务退化。沿用上例，比较两个互斥的后续情景：

| 情景 | 总成本 | 请求数 | 成功交易数 | 成本/请求 | 成本/成功交易 |
|---|---:|---:|---:|---:|---:|
| 基线月 | 30,000 | 2,000,000 | 1,000,000 | 0.015 | 0.03 |
| 健康增长月 | 36,000 | 不作本例判断 | 1,500,000 | 不作本例判断 | 0.024 |
| 低质量月 | 27,000 | 3,000,000 | 500,000 | 0.009 | 0.054 |

健康增长情景下，支出增加 20%，成功交易增加 50%，平均每笔成本下降 20%。这支持在既定范围内的效率改善判断，但是否继续投入，还要看交易价值、容量风险和预算。

低质量情景下，成本/请求下降 40%，成本/成功交易却上升 80%。请求可能受到重试或其他无效流量影响，仅看请求成本会得到相反判断；本例没有把请求数变化的具体原因当成已证实事实。因此每次成本复查都应同时看有效产出、质量和成本驱动，必要时按产品或客户群分组，避免业务组合变化掩盖差异。

推断：对尚未建立可信业务分母的团队，先用一个能控制的技术指标，再补业务结果，可能比一次性建设全成本模型更有效。前提是明确技术指标的用途和缺口，不能长期把便宜的请求等同于便宜的业务交付。

## 洞察五：AWS 提供实践落点，团队仍需自己定义归属和业务结果

AWS 的成本优化支柱把组织能力、支出与用量认知、资源效率、供需管理和持续优化连接起来。它的设计原则要求衡量业务产出及其交付成本，也要求分析支出归属。这与前面的 FinOps 主线相互支持。

| FinOps 问题 | 本次已读 AWS 材料提供的落点 | 团队需要补上的决定 |
|---|---|---|
| 到底产出了什么？ | COST03-BP04 要求与业务共同定义工作负载结果，选少量高层业务指标；复杂工作负载可分组件定义 | 哪些事件算成功、如何去重、如何处理取消或退款 |
| 这些结果花了多少？ | COST03-BP06 把工作负载成本与用量或业务结果结合，利用账户、标签及应用观测数据，建议按小时分析 | 数据能否对齐，哪些成本直接归属，哪些进入共享池 |
| 为什么低谷时单位成本更高？ | COST03-BP06 解释固定运行的组件和变化的请求率会影响效率 | 保留哪些容量、低谷期间如何满足业务和可靠性要求 |
| 共享容器资源怎么拆？ | COST03-BP06 以 ECS、AWS Batch 的 Split Cost Allocation Data 为具体例子 | 实际服务是否适用、业务归属映射是否可靠、是否值得投入 |
| 改什么以及如何持续？ | 成本优化支柱强调资源、供需及长期优化；设计原则强调组织能力和消费模型 | 选定行动负责人，验证成本与业务质量，再更新基线 |

这里的 AWS 实践与 Foundation 的组织框架互补：前者给出工作负载层的做法，后者提醒跨角色、跨能力持续循环。COST03-BP06 的共享资源例子有明确产品范围，不能据此承诺所有数据库、所有租户或所有容器平台都能自动完成成本归属。

### 起步时只建立能支撑一次决策的最小闭环

建议先让一个产品的账能解释、一个业务单位可信、一个优化行动可验证，再扩大范围。以下是本文整理的实施顺序，不是官方强制阶段门：

1. 工程、产品和财务共同确定 Scope、负责人、成本边界与一个业务结果指标，并留一个技术驱动指标用于解释。
2. 用账户和元数据归集直接成本，列明共享池、中央费用及未知费用，确定规则的有效期和变更负责人。
3. 把分配后成本与同周期业务结果接起来；核对原始费用没有丢失或重复，检查缺失、零分母及质量指标。
4. 在已观察到的驱动因素中选择一项优化，说明预期变化、实施工作量与服务约束；用量优化和费率优化分开评估。
5. 执行后以相同口径复测，解释业务量、价格与规则变化；下一轮只为能改善决策的缺口增加精度或自动化。
