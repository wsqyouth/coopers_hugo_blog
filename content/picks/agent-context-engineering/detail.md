依据厂商一手资料和原精读中的公共示例整理。工程组合是待实际任务验证的设计。

## 核心心智模型：每轮输入都应能回溯到事实

一次模型调用只需要当前任务所需的工作视图，系统还要保留能恢复和纠错的事实记录。Google 工程文章把这种关系描述为持久状态经过处理后形成工作上下文；LangChain 用写入、选择、压缩、隔离归纳可采取的动作。

推断：把两者合起来，最有用的设计问题是“这轮输入从哪里来、为什么选中它、错误时如何找回底本”。压缩负责缩小表示，记忆负责跨时保存，检索负责当前召回，隔离负责限定可见范围；它们可以在同一轮组合。下面的图是本报告的解释性设计，箭头表示信息流，不规定某个 SDK 的固定执行顺序。

## 洞察一：先决定谁保存事实，再决定如何缩短输入

上下文优化首先需要稳定的事实归属，否则每次摘要都会成为无法追查的新底本。Google 的分层设计区分 session、memory、artifacts 与本轮 working context；这提供了组织信息的起点。

推断：在自己的 agent 系统里，可以明确分配三种责任。事件记录保存“谁做过什么、结果是什么”；文件存储保存完整文档或大对象；任务状态保存“现在目标是什么、下一步由谁负责”。模型输入从这些记录中取需要的部分。模型写出的结论则是待核对的判断，不能仅因被写入状态，就升级成事实。

例如一个工具返回大量客户记录时，后续步骤通常只需知道查询条件、匹配数量、文件位置和选中的几条记录。如果把整个返回值放进后续每轮历史，系统就失去了选择机会。如果只留一句“客户有问题”，又失去了恢复证据的机会。建议返回一个可继续读取的句柄，再附小而明确的结果概览。

这里的“事实”也有边界：日志能证明某次工具返回了某个值，不能自动证明外部数据库此刻仍是这个值。建议给易变对象保留时间、版本与查询条件；后续行动涉及当前状态时重新查询。这样可以把“历史记录”和“实时事实”分别处理，避免让持久化替代重新验证。

## 洞察二：压缩必须保住下一步行动所需的约束

压缩是否合格，要看任务能否正确继续。Anthropic 提醒过度压缩会丢失后来才显现重要性的细节，建议先保证相关信息召回，再减少冗余；这比单独追求更短更有指导性。

推断：可以按信息的可恢复性选择三种处理方式。重复且已失效的输出适合裁剪；长讨论中已经形成的决策适合结构化摘要；后续仍可能需要逐项核对的大对象适合外置后按需读取。三种方式不能仅按“哪个省 token 更多”排序。

建议摘要至少保留目标、禁止事项、已确认决策、未解决问题、证据位置和下一步。比如原任务是“只分析失败原因，不修改数据库”，压缩后只写“继续修复失败记录”，就改变了授权边界。这个失败与摘要长短无关，丢失的是动作约束。

当前 ADK 压缩文档列出按 token 与按轮次触发的策略，以及保留近期事件、滑动窗口重叠等配置；同时配置两种策略时，文档说明 token 策略优先。页面提供多个语言示例，不能把某个 Python 参数直接当作所有 SDK 的共同接口。

推断：在应用设计中，触发阈值需要为系统指令、工具定义、下一次较大返回值和模型输出预留余量；仅按轮数触发，可能挡不住一次异常大的结果。语义上也可以选择阶段交接点做摘要，但是否必要应由恢复质量和成本决定。

最小验证方式是做一次恢复演练：给恢复者摘要和证据句柄，让它回答当前目标、尚未满足的条件、允许的下一动作，再抽查一个容易遗漏的限制。若答不出，就说明摘要无法承担交接责任。这里提出的是验证方案，本轮没有运行性能或准确率实验。

## 洞察三：记忆的写入、存储与注入需要分别设计

记忆被保存，并不等于每轮都应进入模型输入。LangChain 当前概念文档区分 thread 范围的短期状态和跨会话、按 namespace 组织的长期记忆，并讨论执行路径内更新与后台更新的取舍。

推断：可以先把记忆当作带出处的候选事实管理。每条记录建议携带适用范围、原始来源、记录时间、当前版本，以及如何替换或撤销。召回时先按任务和访问范围筛选，再判断语义相关性，最后决定是否值得占用本轮输入。

比如“当前环境为测试环境”适合进入这个任务的状态；“所有任务都可直接修改测试环境”却是另一条权限主张，不能从前一句推出。另一个例子是用户临时要求“这次回答简短”，若被当作永久偏好保存，就可能干扰后续需要详细分析的任务。写入时保留作用域，比以后不断追加例外更清楚。

更新策略也取决于一致性需求。建议影响下一步行动的任务状态，在交接前完成持久化；允许延迟生效的偏好归纳，可以交给独立任务处理。采用异步机制时，需要回答消费者如何识别旧版本，以及失败后从哪里恢复，而不只是记录“已经启动后台写入”。

当两条记忆冲突时，建议先呈现冲突和来源，按明确规则判断是否失效；不要只凭向量相似度覆盖旧值。对不能判断的新断言，可以保存为待验证项。这样不会把模型某次自我总结的错误反复当成后续推理依据。

## 洞察四：预先检索和按需检索适合组合

预先检索提供启动速度，按需检索允许根据中途发现改变方向。Anthropic 的文章讨论了保存轻量引用并在运行时加载内容，也给出了预装部分上下文、继续自主探索的混合思路。

推断：建议把已知且稳定的任务约束放在启动输入里，把庞大、变化快、是否需要尚不确定的材料留给工具读取。是否采用 embedding，应该在确定检索对象和查询方式后再判断。

| 本报告建议的入口 | 适用情况 | 主要失败边界 |
|---|---|---|
| 精确路径、ID、关键词查找 | 已知文件名、错误码或对象标识 | 名称不一致时漏检 |
| 语义检索后核对正文 | 用户描述和文档用词不同 | 相似材料未必适用于当前版本 |
| 目录与摘要，再读取选中段落 | 大文档、多级资料库 | 首层摘要可能漏掉关键限定 |
| 少量预装，再按反馈追加查询 | 起始问题明确、调查方向会变化 | 查询循环可能重复或过度展开 |

建议工具同时返回检索条件、来源时间、结果数量和继续读取方式。大结果可分页面或分章节返回；截断时明确说明还有多少未读；重复查询优先复用已读结果的引用。这样，调用者能判断是没有证据，还是证据还没被读到。

例如查“任务为何没有交付”时，先读当前状态和最近一条失败事件，再沿相关的执行 ID 查工具结果。如果直接把全部历史装进去，会提高阅读成本；如果只检索语义最相似的旧事故，则可能把类似问题误当成本次原因。

## 洞察五：隔离越强，交接输入越需要完整

上下文隔离减少无关输入，也会移除任务线索。LangChain 说明隔离可以通过子 agent，也可以通过不直接暴露给模型的 state 字段实现；因此新增角色并非唯一手段。

Google 2025 年工程文章区分工具式 agent 调用和控制权 transfer，并讨论 `include_contents` 的默认模式与 `none` 模式。文中默认模式会传入完整工作内容，不能把其“最小必要上下文”原则理解成默认不继承历史。当前旧多 agent 文档地址已迁至 workflows 概览，未据此确认这些历史参数在当前各 SDK 的行为。

推断：选择交互模式时，先回答“谁持有下一步控制权”。工具式调用适合边界明确、返回后由原协调者继续的子问题；控制权交接适合接手者继续与用户或环境互动的阶段。共享状态则解决多个执行者读写共同事实的问题，需要另行约定字段归属和版本。

建议交接输入包括目标、成功条件、限制、必要证据和可用能力；回传包括结论、证据引用、未解决问题、实际完成动作和产物版本。回传“我检查过了”没有说明检查对象；只回传摘要也可能掩盖证据冲突。协调者应能从回传信息回查所依据的材料。

反例是两个 agent 各拿到一半接口约定，各自生成看似合理的实现，却对同一字段做了不同解释。此时减少共享信息会加重问题。建议先统一接口约束，再分别分配局部任务；若任务一直需要密集共享推理，也可以保持一个上下文，通过外置文件减少大对象输入。

## 三家材料的价值在不同层次

三篇文章适合互相补充，现有证据不足以把它们写成效果排名。

| 材料 | 本报告的阅读判断 | 使用边界 |
|---|---|---|
| Anthropic，2025-09-29 | 适合判断何时检索、压缩、记笔记或拆任务 | 产品例子属于文章时期经验 |
| LangChain，2025-07-02 | 适合检查写入、选择、压缩、隔离是否都有安排 | 分类不等于运行时自动完成所有动作 |
| Google Developers / ADK，2025-12-04 | 适合从持久状态与每轮视图理解上下文流水线 | 架构原则、文章示例与当前 SDK 行为分别核对 |

推断：共同方向是让每步输入服务当前任务。主要差异是讲解视角和框架承载方式，本轮未发现足以证明互不兼容的设计结论。判断哪种组合适合具体应用，仍需要实际任务与恢复验证。

## 最小组合示例：让长调研中断后仍能继续

下面的组合示例把四种方法落到同一条调研流程，所有字段与步骤均为本报告提出的设计。

启动时保存任务合同：问题、已确认范围、停止条件和交付形态。事实记录保存每次取材的 URL、获取时间、结果位置；大正文留在文件中。首轮输入只放合同、来源目录和当前进度。

研究者先按目录选择材料，读取相关章节，把可核实论断与对应位置记入证据表。一次读取太大时，返回章节目录和文件句柄，继续按需展开。阶段结束后把进度摘要写入任务状态，保留未核实问题，而不是只保存“已读完”。

假设需要独立核查某条断言，可以把断言、出处、需判断的条件交给核查者。核查者回传支持、反驳或证据不足，并指出位置；协调者保留相互冲突的结果，不把多数意见当作证明。若无需独立视角，原研究者也可完成局部补读，是否拆分取决于任务收益。

发生中断后，恢复者读取任务状态和最新产物版本，根据未解决问题重新打开相关源文件。若发现来源已变化，补记新版本，并重新评估受影响的论断。恢复验收检查的是约束、证据和下一步是否仍清楚，不要求恢复者重读全部过程。
