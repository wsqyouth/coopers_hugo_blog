## 摘要

一个 Helper 在任务开始 182 秒后才加入，面对的是整队 600 秒的预算。Claude Cookbook 让它第一轮就看到 `[elapsed 182s / 600s]`：用户已经等掉的三分钟，不会因为换了一个执行者而归零。共享时钟把真实等待带进模型的上下文，让 Lead 和 Helper 在继续查证、继续派工或交付答案时拥有同一个时间参照。

教程提供两种引导：用一句时间压力提示表达越早得到正确结果越好，或在时钟行上直接显示总预算。它演示了如何把时间传给每个角色、如何从日志确认传递成功；延迟收益、答案质量和准时完成仍须分别检验。原文最后的限定尤其具体：一两分钟就能做完的任务，若把预算砍半，Claude 可能超时也不放弃任务。预算提示为决策提供信息，运行时的截止、清理和交付条件仍有各自的责任。

## 时间也要进入决策上下文 {#核心心智模型时间也要进入决策上下文}

**这篇文章的核心价值，是让 Agent 在决定“继续查、继续派、还是交卷”时看见团队已经花掉的时间。**运行时拥有真实计时，模型读取计时后自行调整行为；教程提供两种引导：告诉它越早得到正确结果越好，或显示一个总时间预算。

对你最有用的连接，是把“编排跑通了”推进到“投入与产出是否匹配”。但这篇教程只补上了决策所需的信息；质量底线、超时处理和交付责任仍需要单独设计。

**先带走三个判断：**共享的是任务总耗时；时钟在请求边界更新；预算是否被遵守，要靠实验与运行时机制分别回答。下面按这条因果链精读。

## 共享时钟让局部任务服从整体进度 {#洞察一共享时钟让局部任务服从整体进度}

**晚加入的 Helper 应继承团队已经消耗的时间，不能重新获得一份完整预算。**例如团队运行六分钟后再派一个 Helper，如果任务总预算十二分钟，它首先应该看见“已用 360 秒 / 总预算 720 秒”，而不是“已用 0 秒”。

这会改变它面对同一子问题时的决策条件。还剩十分钟，可以多追一条相互矛盾的来源；只剩一分钟，更有理由先交已经核实的发现和未决点。这里描述的是机制可能提供的决策依据，实际行为仍需要观察。

教程用一个任务级的单调时钟计算经过时间，由 Lead 和所有 Helper 共用。计入其中的是等待模型、慢工具和同伴的真实经过时间；它不是各 Agent 的思考用时，也不是把各分支耗时相加。

推断：迁移到跨进程编排时，真正该共享的是“同一个任务起点与截止语义”。不能照搬内存中的共享对象，也不能让每次重启的 run 都重置任务年龄。具体跨机器实现还需处理时钟差异。

## 在调用前追加事实，既及时也保留缓存前缀 {#洞察二在调用前追加事实既及时也保留缓存前缀}

**时钟必须进入下一次模型请求，单独出现在监控台不会影响模型的下一步选择。**教程在首次任务消息之后加入耗时；后续则在最近工具结果的末尾追加。历史时钟保留，下一轮继续追加新内容。

追加位置也影响成本。若每轮都改写开头的系统提示，后面的长上下文就失去了相同前缀；把变化放在末尾，之前的内容仍有机会复用缓存。缓存是否实际命中，还取决于有效期、长度与请求内容，不能由“位置放对”直接推出。

下面是对原机制的重新表达，不是原文代码摘录：

```text
任务启动：
    创建团队计时基准
    选择 基线 / 时间压力 / 显式预算 中的一种模式
    启动 Lead

每个 Agent 的每一轮：
    收集本轮可见的任务结果与同伴消息
    若该模式展示时间：
        从同一团队基准读取经过时间
        在最新消息末尾追加耗时；预算模式同时追加总预算
    把这份上下文发送给模型
    若模型请求工具：并发执行本轮可独立的工具，进入下一轮
    若 Helper 准备结束：
        先处理已经送达的追加指令，再向 Lead 汇报
    若 Lead 给出最终结果：交付，并清理仍在运行的分支
```

**这个时钟在一次请求内部不会继续刷新。**模型正在生成、或服务端工具正在运行时，Harness 没有机会再塞入新时间；要等控制权返回才可更新。推断：单次调用很长的系统，仅增加时钟提示，可能仍然来不及调整策略。

## 压力改变偏好，预算给出参照 {#洞察三压力改变偏好预算给出参照}

**教程把“尽快交出正确结果”和“对照具体时间目标安排工作”做成两个独立配置。**前者适合越早越好的任务；后者适合已有明确等待目标的任务。

| 配置 | 每轮可见的时间 | 首次任务与 Helper 简报中的引导 |
|---|---|---|
| 基线 | 不显示 | 无额外时间引导 |
| 时间压力 | 已经过多少秒 | 避免可避免的耗时，越早得到正确结果越好 |
| 显式预算 | 已用秒数 / 团队总预算 | 不再附加那句压力提示 |

教程拒绝同时打开压力和预算。这是这份示例保持实验配置分开的选择，不是二者在产品里永远不能共存。

**这组三配置可以比较整体策略，却不能单独分离“时钟”和“催促语句”的作用。**因为基线同时没有二者，而压力组同时加入二者。如果未来要证明仅显示时钟就有效，还要加一个“只有时钟”的控制组。这是实验设计上的推断，不是原文给出的实验结果。

预算也不能替用户定义什么叫完成。对一个事实检索任务，先找到可信答案即可停止；对研究阅读包，还要满足主题覆盖、来源核查与可读性。推断：先写清质量底线，时间信号才有可能帮助模型压缩重复劳动，而不是压缩必要步骤。

## 异步协作减少空等，完成责任仍在 Lead {#洞察四异步协作减少空等完成责任仍在-lead}

**时钟提示和异步协作分别处理“如何分配努力”与“如何让独立工作重叠执行”。**教程沿用了消息 Hub：Agent 可以发消息，等待时由事件唤醒；工具返回时也会带回已收到的消息。Helper 完成后把最终报告送到 Lead。

这里有两层并行：不同 Helper 同时工作；同一个 Agent 一轮内的多个工具同时执行。推断：墙钟节省取决于关键路径。如果 Lead 必须等最慢分支，或者派发与汇总本身占了大部分时间，再多分支也未必更快。

教程还保留两个对可靠交付有意义的动作：Helper 正常结束前检查已送达的纠正消息；Lead 收口后取消、等待清理剩余任务。前者减少已到达的修正被忽略，后者给整次运行一个明确结束点。它们并不证明结果已经通过业务验收。

设计编排时，需要确定：哪些分支结果是交付必需，哪些只是补充？推断：这个判据应写进任务合同。否则“Lead 已经回答”和“所有必要工作已经完成”很容易被混为一谈。

## 教程证明线路接通，效果证据要另看 {#洞察五教程证明线路接通效果证据要另看}

**文末示例验证了时钟能到达各 Agent，没有测出某个配置相对基线快多少。**页面展示的是排序知识问答的一次约 9 秒运行，启动四个 Helper；没有真实业务工具，任务工具调用计数为零。这个“零”不包含消息与派发等协调动作，也不代表没有模型调用或成本。

因此，不能从示例读出“多 Agent 必然提速”“预算一定守住”或“质量不受影响”。原文结尾也把多次运行、比较耗时和检查答案质量列为下一步。

**官方的另一页测量提供了更具体的反面证据：加速可以伴随分数损失。**下表摘取其 DRACO 配置内比较；均为 Claude Opus 5.5、medium effort，加入的是压力语句与时钟，而非本文的显式预算组。

| 对比自身无时间引导配置 | 典型任务耗时变化 | 平均评分变化 |
|---|---:|---:|
| 单 Agent 加入压力与时钟 | −47% | −4.1 分 |
| 团队配置加入压力与时钟 | −17% | −1.6 分 |

“典型耗时”是各任务耗时比值的中位数；评分按 0–100 计。该测量每题尝试三次。团队在无引导组的 300 次 DRACO 尝试中仅 5 次启动 Helper，因此团队行主要反映 Lead 单独运行，不能当作充分并行的多 Agent 收益。测量也不是 Cookbook 默认模型的复现。

推断：你应该把这类优化视为质量与等待时间之间的取舍候选；最终是否值得，取决于自己的质量门槛，不能只看时间下降。
